## 2. Next.js July 2026 セキュリティリリース

**URL:** https://nextjs.org/blog/july-2026-security-release

### ① 目的・問題意識

Vercel が新しい**月次セキュリティリリースプログラム**の第1弾として、Next.js の複数の脆弱性を一括修正した。HIGH 4件・MEDIUM 5件の計9件の CVE に対応。

### ② 具体的な脆弱性と技術詳細

**対象バージョン:** v16.2.11（Active LTS）/ v15.5.21（Maintenance LTS）に更新が必要。

#### CVE-2026-64641 — Server Action DoS（HIGH / CVSS 8.2）

- **対象:** App Router + 少なくとも1つの Server Action を持つアプリ
- **問題:** 細工されたリクエストで過剰な CPU 使用が発生し、同プロセスの処理がブロックされる DoS
- **対策:** v16.2.11 / v15.5.21 へ更新

```bash
npm install next@16.2.11
# または
npm install next@15.5.21
```

#### CVE-2026-64642 — Middleware/Proxy バイパス（HIGH / CVSS 8.3）

- **対象:** Turbopack でビルド + `config.i18n.locales` に1つのロケールのみ設定したアプリ
- **問題:** 認証や認可を行うミドルウェア/プロキシをバイパスされる
- **回避策:** ミドルウェアだけでなく、サーバーサイドのデータ取得メソッドでも認可チェックを実施

```javascript
// ミドルウェアだけに頼らず、Page コンポーネントでも認証確認
export async function getServerSideProps({ req }) {
  const session = await getSession(req);
  if (!session) {
    return { redirect: { destination: '/login', permanent: false } };
  }
  return { props: { session } };
}
```

#### CVE-2026-64645 — SSRF via リライト/リダイレクト（HIGH）

- **対象:** 攻撃者が制御できる入力からリライト/リダイレクト先の外部ホスト名を構築するアプリ
- **問題:** Server-Side Request Forgery（SSRF）

#### CVE-2026-64649 — カスタムサーバーでの SSRF（HIGH）

- **対象:** カスタムサーバーを使用した Server Actions
- **問題:** SSRF

#### CVE-2026-64643 — 内部 Server Function エンドポイントの開示（MEDIUM）

- **対象:** `use cache` 関数と共に Server Action を持つ Cache Components
- **問題:** 内部関数識別子（認証情報・PII は含まない）が漏洩

### ③ なぜ効果的か

月次の事前告知型リリースプログラムにより、運用チームがアップグレードを計画しやすくなる。まず告知 → 修正リリース → 詳細公開の順で進めることで、パッチ適用前のゼロデイ悪用を最小化する。

## 4. shadcn/typeset — HTML/Markdown のタイポグラフィシステム

**URL:** https://ui.shadcn.com/docs/changelog/2026-07-typeset

### ① 目的・問題意識

Markdown レンダリングや HTML コンテンツのスタイリングに特化した CSS システム。Tailwind Typography (`@tailwindcss/typography`) の代替として、1つの CSS ファイルで完結するシンプルなアプローチ。

### ② 具体的なコードと技術詳細

**インストール方法:** CLI ではなく、インタラクティブビルダーで `typeset.css` を生成してプロジェクトにコピー。

```css
/* typeset.css を main CSS にインポート（Tailwind の後） */
@import "./typeset.css";
```

**基本的な使い方:**

```jsx
// .typeset クラスで囲むだけ
<div className="typeset typeset-docs">
  <YourMarkdownRenderer>{content}</YourMarkdownRenderer>
</div>
```

**カスタマイズ — 3つのコントロール:**

| CSS 変数 | 役割 | 例 |
|---|---|---|
| `--typeset-size` | 基準フォントサイズ | `15px` |
| `--typeset-leading` | 行間 | `1.75` |
| `--typeset-flow` | 要素間のマージン | `1.5em` |

**複数の Typeset 定義例:**

```css
/* チャット用の Typeset */
.typeset-chat {
  --typeset-leading: 1.6;
  --typeset-flow: 1em;
}

/* ドキュメント用の Typeset */
.typeset-docs {
  --typeset-size: 15px;
  --typeset-leading: 1.75;
  --typeset-flow: 1.5em;
}
```

```jsx
{/* 用途ごとに使い分け */}
<div className="typeset typeset-chat">{message}</div>
<article className="typeset typeset-docs">{page}</article>
```

**スタイル対象の HTML 要素:** 見出し・段落・リスト・テーブル・コード・ブロッククォート・リンク・脚注・MathML・`<details>` など全要素。

**制限事項:** `margin-trim` に依存しており、2026年時点では Safari/WebKit のみ対応。Chrome・Firefox はフォールバックなし。

### ③ なぜ効果的か

CSS ファイルを1つコピーするだけで動作し、npm パッケージへの依存がない。shadcn のデザイントークン（テーマ）に自動追従するため、ダークモードや色変更に対応しやすい。ストリーミングアプリケーション向けに設計されており、コンテンツのフロー中にスタイルが崩れない。

## 6. ReactBench — コーディングエージェント評価ベンチマーク

**URL:** https://github.com/millionco/reactbench / https://www.reactbench.com/

### ① 目的・問題意識

現行の AI ベンチマーク（HumanEval 等）では、テストを通過しても本番品質でない React コードを書くエージェントを識別できない。ReactBench は**本番の React 作業**でエージェントを評価するベンチマーク。

### ② 具体的なコードと技術詳細

**タスク種類:**

1. **Write React**: 実際のマージ済み PR からタスクを抽出。エージェントはリポジトリとイシュー形式の指示を受け取り、参照実装は非公開。
2. **Fix React**: ソースコードのみから React の問題を特定・リファクタリング。

**評価基準:**
- 保留中の振る舞いテスト（held-out behavioral tests）のパス
- **React Doctor** による新規問題の不検出（壊れた Effect、不要な再レンダリング、アクセシビリティ問題、保守性問題）

**実行例:**

```bash
# Harbor フレームワークでタスクを実行
uv run harbor run -p tasks/hello-react --agent claude-code -m anthropic/claude-opus-4-8
```

**規模:**
- 50+ のオープンソース React リポジトリから抽出した 51 タスク
- クリーンルームコンテナ内で実行、エージェントとベリファイアが分離

**2026年7月 リーダーボード:** GPT-5.6 Terra (max) が 53.3%（pass@1）でトップ（全 55 モデル比較）。

### ③ なぜ効果的か

テスト通過だけでなく「本番で壊れないか」という基準を加えることで、実際の開発現場での AI エージェント品質を測定できる。React Doctor の 400+ ルールが品質ゲートとして機能する。

## 7. TSRX / Octane.js — JSX の後継候補

**URL:** https://betterstack.com/community/guides/scaling-nodejs/tsrx-typescript/

### ① 目的・問題意識

JSX は式ベース（expression-based）のため、制御フローに `.map()`・三項演算子などを使わなければならず、ネストが深くなりやすい。TSRX（TypeScript Render Extensions）は**文ベース（statement-based）**のコンポーネント構文で JSX を置き換える TypeScript 超集合言語。Dominic Gannaway（React Hooks の共同開発者、Inferno・Lexical の作者）が開発。

### ② 具体的なコードと技術詳細

**JSX との比較:**

```tsx
// JSX（式ベース）
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map(todo => (
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}
```

```tsx
// TSRX（文ベース）
function TodoList({ todos }) {
  <ul>
    for (const todo of todos) {
      <li key={todo.id}>{todo.text}</li>
    }
  </ul>
}
```

**主な特徴:**
- `return` 文不要
- ネイティブな `if/else`・`for...of`・`switch`・`try/catch` が制御フローに使える
- **フレームワーク非依存:** React・Preact・Solid・Vue・Ripple にコンパイル可能
- `@tsrx/react` / `@tsrx/preact` / `@tsrx/solid` などのプラグインで共通 AST を各ランタイム向けに出力

**Octane.js との関連:**
- Dominic Gannaway が TSRX をベースに開発中のフレームワーク
- React のプログラミングモデルを維持しつつ、**コンパイル時にすべてを処理**するアプローチ
- サイト: https://octanejs.dev/

### ③ なぜ効果的か

文ベースの構文により AI エージェントがコードを生成しやすく、人間にとっても読みやすい。コンパイル先が複数フレームワークであるため、既存の React コードへの段階的な移行パスが存在する。

## 8. GTKX 1.0 RC — React で Linux GTK4 デスクトップアプリを構築

**URL:** https://github.com/gtkx-org/gtkx / https://gtkx.dev/

### ① 目的・問題意識

Linux デスクトップアプリ開発は通常 C/Python + GTK が必要だが、GTKX は React・TypeScript・JSX で GTK4/Adwaita ネイティブアプリを構築できるようにする。

### ② 具体的なコードと技術詳細

**アーキテクチャ:**

```
TypeScript/React コンポーネント
    ↓ React Reconciler
GObject インスタンス（GTK4 ウィジェット）
    ↓ Rust の napi アドオン（libffi 経由）
GTK4 / Adwaita / GLib（ネイティブ）
```

**基本的なカウンターアプリの例:**

```typescript
import * as Gtk from "@gtkx/gi/gtk";
import { GtkApplicationWindow, GtkButton, GtkLabel } from "@gtkx/jsx/gtk";
import { createRoot } from "@gtkx/react";
import { useState } from "react";

const Counter = () => {
  const [count, setCount] = useState(0);
  return (
    <GtkApplicationWindow defaultWidth={400}>
      <GtkLabel>{`Count: ${count}`}</GtkLabel>
      <GtkButton onClicked={() => setCount(c => c + 1)} />
    </GtkApplicationWindow>
  );
};
```

**プロジェクトの作成:**

```bash
npm create gtkx@rc
cd my-app
npm run dev
```

**追加パッケージ:**
- `@gtkx/css` — Emotion スタイルの CSS-in-JS（GTK CSS クラスに変換）
- `@gtkx/animate` — libadwaita 駆動のアニメーションコンポーネント
- `@gtkx/testing` — Testing Library スタイルのテストハーネス
- `@gtkx/mcp` — AI エージェントにライブウィジェットを公開する MCP サーバー

**動作要件:**
- Linux（GTK4 4.20+、Adwaita 1.8+）
- Node.js 24 以上
- ライセンス: MPL-2.0

### ③ なぜ効果的か

React の状態管理・コンポーネントモデル・Fast Refresh をそのまま Linux ネイティブ開発に持ち込める。型定義は GObject-Introspection XML から自動生成されるため、常にネイティブ API と同期されている。

## 9. dx-styles — ゼロランタイム CSS-in-TS

**URL:** https://dx-styles.dev/

### ① 目的・問題意識

styled-components や Emotion などのランタイム CSS-in-JS は React Server Components と相性が悪く、クライアントにランタイムコードを配信してしまう。dx-styles は**ビルド時に CSS を静的抽出**する、Linaria メンテナーによるゼロランタイム CSS-in-TS ライブラリ。

### ② 具体的なコードと技術詳細

**基本的なスタイル定義:**

```typescript
import { recipe } from 'dx-styles';

// ビルド時に CSS クラスに変換される
export const button = recipe({
  base: {
    padding: '8px 16px',
    borderRadius: '4px',
    border: 'none',
    cursor: 'pointer',
  },
  variants: {
    intent: {
      primary: { background: 'var(--color-primary)', color: 'white' },
      secondary: { background: 'var(--color-secondary)', color: 'black' },
    },
    size: {
      sm: { fontSize: '14px', padding: '4px 8px' },
      lg: { fontSize: '18px', padding: '12px 24px' },
    },
  },
});
```

```tsx
// 使用例
<button className={button({ intent: 'primary', size: 'sm' })}>
  送信
</button>
```

**主な特徴:**
- **ゼロランタイム:** CSS はビルド時に静的生成、プロバイダー不要
- **確定的クラス名:** ビルドをまたいでクラス名が変わらない（ハッシュドリフトなし）
- **コンパイル時 RTL:** LTR で記述すれば RTL を自動生成
- **RSC 対応:** プロバイダー不要なので React Server Components でそのまま動作
- **トークンコントラクト:** テーマ規則ではなく TypeScript モジュールでトークンを定義
- **wyw-in-js** プロセッサとして実装

### ③ なぜ効果的か

ランタイムコストゼロで CSS-in-TS の開発体験を維持できる。RSC 環境では従来のランタイム CSS-in-JS は動作しないため、この方向性が 2026 年以降の設計トレンドになっている。

## 10. Oxlint 型対応リンティング 安定版リリース

**URL:** https://oxc.rs/blog/2026-07-22-type-aware-linting-stable

### ① 目的・問題意識

ESLint の型対応ルール（`@typescript-eslint`）は TypeScript の型情報が必要なため遅い。Oxlint は Rust ベースのリンターで高速だが、型対応ルールが欠けていた。`tsgolint`（Go 製）との組み合わせで型対応リンティングが安定版に到達。

### ② 具体的なコードと技術詳細

**アーキテクチャ:**

```
Oxlint（Rust）          tsgolint（Go）
  - ファイル走査         - TypeScript プログラム構築
  - 無視ロジック         - typescript-go を使用
  - 設定管理             - 型対応ルールの実行
  - レポート出力         ↑
         ↓              TypeScript v7.0.2 対応
    結果の統合
```

**設定例（oxlint.json）:**

```json
{
  "typeAware": true,
  "typeCheck": true,
  "rules": {
    "@typescript-eslint/no-floating-promises": "error",
    "@typescript-eslint/no-misused-promises": "error",
    "@typescript-eslint/await-thenable": "error"
  }
}
```

**対応状況:**
- typescript-eslint の 61 の型対応ルールのうち **59 ルールをカバー**
- α版から 16 ルール追加
- ルールごとのタイミング計測、設定改善、パフォーマンス向上

### ③ なぜ効果的か

`no-floating-promises`・`no-misused-promises`・`await-thenable` などの型情報を必要とするルールが、ESLint より高速な Oxlint で利用可能になった。TypeScript v7 の `typescript-go`（Go 実装）を活用することでさらに高速化されている。

## 11. vinext — Cloudflare の Vite ベース Next.js 代替実装

**URL:** https://github.com/cloudflare/vinext / https://vinext.io/

### ① 目的・問題意識

Next.js の API サーフェスは維持しつつ、**Vite ベースのツールチェーン**で動かすことで、ビルド速度・バンドルサイズ・デプロイの柔軟性を改善する。既存の Next.js アプリをほぼ変更なしで移行できることを目指す。

### ② 具体的なコードと技術詳細

**対応機能（API カバレッジ約 94%）:**
- App Router（ネストレイアウト・ローディング状態・エラーバウンダリ・パラレルルート・インターセプトルート）
- Pages Router（`getStaticProps`・`getServerSideProps`・`getStaticPaths`）
- React Server Components + ストリーミング SSR（Suspense）
- Server Actions（FormData 対応）
- ミドルウェア

**パフォーマンス比較（33ルートのテストアプリ）:**

| 指標 | Next.js 16 (Turbopack) | vinext (Rolldown) |
|---|---|---|
| プロダクションビルド時間 | 7.38 秒 | **1.67 秒（4.4倍速）** |
| クライアントバンドル（gzip） | 168.9 KB | **72.9 KB（57%削減）** |

**デプロイ:**

```bash
# Cloudflare Workers への1コマンドデプロイ
npx vinext deploy
```

**開発の背景:**
- 1人のエンジニアが約1週間、AI を活用して開発
- コスト: 約 $1,100 相当の API トークン
- コードの大部分は AI 生成（人間によるレビューは未完了）

### ③ なぜ効果的か

Next.js の API 互換性を維持しながら、Vite 8 + Rolldown の高速なビルドパイプラインを利用できる。Cloudflare Workers へのデプロイが1コマンドで済み、エッジランタイムへの移行障壁を大幅に下げる。
