## 1. State of HTML 2026 の結果公開（トップ記事）

参照: https://2026.stateofhtml.com/en-US/ （Conclusion / Features / Forms / Usage 各ページ）、DEV「State of HTML 2026: built-in elements win, form controls still hurt」

### ① 目的・問題意識
開発者が HTML のどの機能を使い、好み、苦労しているのか、そして AI をどれだけ使っているのかを毎年測る調査。ブラウザ実装の優先度付け（Interop など）にも使われる。

### ② 具体的な内容
- **Popover API の利用率が 40% に到達**。全主要ブラウザで動作するようになった（Baseline）ことが要因とされる。
- **スタイリングが最も難しい要素**: `<input type="date">` などの日付入力、`<select>`、`<datalist>`。
- **`<datalist>`**: 利用率が 30% → 44% に大きく増加した一方、ポジティブ評価は 44% → 34% に低下。理由はスタイリング・アクセシビリティ・ブラウザバグ。
- **ブラウザサポート不足で最も足を引っ張っている機能**: カスタマイズ可能な `<select>`（`appearance: base-select`）。Firefox が未出荷のため。
- **ウィッシュリスト1位**: ソート・フィルタ機能を内蔵したネイティブなデータテーブル。次いでタブ、コンボボックス、スイッチ（トグル）。
- **AI 利用**: HTML 回答者のコードのうち AI 生成の中央値は 50%（State of Devs では 63%、CSS に限ると 13%）。
- **総括（Polypane の Kilian Valkhof）**: 不満の中心は「ブラウザ間で挙動が違う」ことから「ブラウザがまだ追いついていない（未実装）」ことへ移っている。特にモバイル OS が問題点。

参考となるコード（Popover と customizable select の基本形。調査で言及された機能の典型的な使い方）:

```html
<!-- Popover API: JS なしで開閉、light dismiss、トップレイヤー表示 -->
<button popovertarget="menu">メニュー</button>
<div id="menu" popover>
  <a href="/settings">設定</a>
  <a href="/logout">ログアウト</a>
</div>

<!-- Customizable select（Chromium 系のみ。Firefox 未対応が課題） -->
<style>
  select,
  ::picker(select) {
    appearance: base-select;
  }
</style>
<select>
  <button><selectedcontent></selectedcontent></button>
  <option value="a">🍎 Apple</option>
  <option value="b">🍌 Banana</option>
</select>
```

### ③ なぜ重要か
「ネイティブ要素で済むなら JS を書かない」流れが数字で裏付けられた（Popover 40%）。一方、フォーム部品のスタイリングは依然として最大の痛点で、customizable select の全ブラウザ対応が次の焦点になる。

## 2. Chrome 158 安定版リリース

参照: [Chrome 158 Release Notes](https://chromestatus.com/release-notes/158)、[What’s new in Chrome 158 — Web Standards](https://web-standards.dev/news/2026/11/chrome-158/)、GIGAZINE、BigGo

2026-11-17 Stable。主要項目は以下の 3 つ（加えて Android 版 WebHID、204 件の脆弱性修正など）。

### 2-1. `<install>` 要素（HTML だけで Web アプリをインストール）

#### ① 目的・問題意識
PWA のインストール導線はこれまで `beforeinstallprompt` の捕捉など JS 依存で、ブラウザ UI 任せの部分も大きかった。さらに **別オリジンのアプリ** をインストールさせる手段（アプリストア的なページなど）が無かった。

#### ② 技術詳細・コード
- 宣言的な要素で、クリックするとブラウザのインストールプロンプトが出る（サイトが勝手にサイレントインストールすることはできない）。
- 同一オリジンのアプリなら属性なしで現在のページのマニフェストを使用。
- 別オリジンのアプリは `installurl` 属性で指定。対象マニフェストに `id` が無い場合は計算されたマニフェスト ID を `manifestid` に指定する（値は解析後の computed id と一致必須）。
- 未対応ブラウザでは子要素が通常の HTML として描画される＝フォールバックを中に書ける。
- 対象アプリには Web App Manifest が必要。
- WICG では `installurl` 方式は Origin Trial 終了で廃止予定で、新しい「manifest URL 方式」（`manifest` / `id` 属性）に置き換わる見込み（WICG/install-element explainer-manifest-url.md）。

```html
<!-- 同一オリジン: 現在のページのアプリをインストール -->
<install>
  <!-- 未対応ブラウザ向けフォールバック -->
  <a href="/app">Launch Awesome App</a>
</install>

<!-- 別オリジンのアプリをインストール（Microsoft Edge デモより） -->
<install installurl="https://foo.com"
         manifestid="https://foo.com/someid"
         id="install-button">
  <a href="https://foo.com">Open app</a>
</install>
```

#### ③ なぜ効果的か
JS 不要で、ブラウザ自身が信頼できる UI としてボタンを描画するため、なりすましやクリック誘導を防ぎつつインストール率を上げられる。フォールバックも HTML の標準的な挙動で自然に書ける。

### 2-2. メディア状態疑似クラス（`:playing` `:paused` など）

#### ① 目的・問題意識
カスタム動画プレイヤーの再生/停止/バッファ中表示などは、`play`/`pause`/`waiting` イベントを JS で監視してクラスを付け替える必要があった。

#### ② 技術詳細・コード
`<audio>`/`<video>` の状態にマッチする 7 種: `:playing` `:paused` `:seeking` `:buffering` `:stalled` `:muted` `:volume-locked`。
- `:buffering` / `:stalled` は `:playing` の下位状態（バッファ中も `:playing` はマッチする）ので、より具体的なルールを後に書く。

```css
/* 停止中だけ再生アイコンを出す */
.player .play-icon { display: none; }
.player:has(video:paused) .play-icon { display: block; }

/* 再生状態で枠色を変える */
video:paused  { outline: 3px solid gray; }
video:playing { outline: 3px solid green; }

/* バッファ中はスピナー（:playing より後に書く） */
.player .spinner { display: none; }
.player:has(video:buffering) .spinner { display: block; }

/* ミュートバッジ */
.player:has(video:muted) .muted-badge { display: inline-block; }
```

```js
// 未対応ブラウザ向けフォールバック
if (!CSS.supports("selector(:playing)")) {
  const v = document.querySelector("video");
  const sync = () => v.parentElement.classList.toggle("is-playing", !v.paused);
  ["play", "pause"].forEach(e => v.addEventListener(e, sync));
}
```

#### ③ なぜ効果的か
状態とスタイルの同期を JS に任せないので、イベントの取りこぼしによる表示ズレが起きず、コードも減る。`:has()` と組み合わせればプレイヤー全体の UI を CSS だけで切り替えられる。

### 2-3. XSLT の段階的削除開始

#### ① 目的・問題意識
ブラウザ内 XSLT（libxslt）はセキュリティ上のリスクが大きく利用率も極小のため、Chrome が削除を進めている。

#### ② 技術詳細
- Chrome 158 Stable で `XSLTProcessor` と `<?xml-stylesheet?>` 処理命令による変換が停止（Origin Trial / エンタープライズポリシー参加者を除く）。
- 逃げ道（ポリシー/OT）は Chrome 176（2027-08-17 予定）で終了とする情報あり。
- 影響: XSLT で見た目を付けた RSS フィード、サイトマップ表示など。Firefox/Safari は削除未発表。
- 移行: サーバー側／ビルド時に HTML へ変換する、または JS ライブラリ（例: XSLT の JS/WASM ポリフィル）を利用。

```xml
<!-- これが Chrome 158 では変換されなくなる -->
<?xml version="1.0"?>
<?xml-stylesheet type="text/xsl" href="/feed.xsl"?>
<rss version="2.0">...</rss>
```

#### ③ なぜ重要か
RSS やサイトマップを「ブラウザで見たときに整形表示」している既存サイトは表示が素の XML になる。事前に検出・移行が必要。

## 3. jQuery 4.1.0 / 3.8.0 リリース（"Passing the Torch"）

参照: [jQuery 4.1.0 and 3.8.0 Released: Passing the Torch](https://blog.jquery.com/2026/11/17/jquery-4-1-0-and-3-8-0-released-passing-the-torch/)、[GitHub Release 4.1.0](https://github.com/jquery/jquery/releases/tag/4.1.0)

### ① 目的・問題意識
4.x 系を今後の本流とし、3.x 系をメンテナンスのみに移行させる節目のリリース。

### ② 技術詳細
- **4.1.0**（4.x 初のマイナー）
  - jqXHR に `responseURL` フィールド追加（リダイレクト後の最終 URL を取得可能）。
  - カスタム要素を含むフォームのシリアライズ改善。
  - 内部の要素探索を `querySelectorAll` ベースに変更。
  - ページをハングさせうるセレクタ正規表現の修正。
- **3.8.0**（3.x 最後の機能リリース）
  - 上記セレクタ正規表現問題の修正。
  - `hidden="until-found"` のサポート。
  - 4.0 で削除済みの API（jQuery プロトタイプ上の `push` / `sort` / `splice` 等）を正式に非推奨化 → jQuery Migrate が警告を出せるように。
  - 以後 3.x はクリティカルなセキュリティ・バグ修正のみ。

```js
// 4.1: リダイレクト後の URL を取得
$.ajax("/old-path").done((data, status, jqXHR) => {
  console.log(jqXHR.responseURL); // 例: "https://example.com/new-path"
});
```

```html
<!-- 3.8: hidden="until-found" はページ内検索で自動展開される -->
<div id="details" hidden="until-found">折りたたまれた内容</div>
```

また同号では「You Don't Need jQuery」ガイドが大幅更新され、IE 向けフォールバックを現代的なワンライナーに置き換えたことも紹介されている（例: `$(sel)` → `document.querySelectorAll(sel)`、`$.ajax` → `fetch()`、`.addClass` → `el.classList.add()`、`$(el).closest()` → `el.closest()`）。

### ③ なぜ重要か
3.x 利用者は 3.8 + jQuery Migrate で非推奨 API を洗い出してから 4.x へ移行する、という明確なアップグレードパスが示された。

## 4. Top 10 things AI gets wrong in web development（Chrome for Developers）

参照: https://developer.chrome.com/blog/top-10-things-ai-gets-wrong-in-web-dev 、関連: [Modern Web Guidance 1.0](https://developer.chrome.com/blog/modern-web-guidance-v1)

### ① 目的・問題意識
コーディングエージェントは古いパターン（命令的 JS、自作 UI）を生成しがち。Chrome チームが評価で頻出した誤りを 10 項目に整理し、Modern Web Guidance（エージェント向けスキル）でどう正すかを示した。

### ② 各項目（検索で確認できた範囲）

1. **モーダル・ポップオーバー**: fixed 配置のオーバーレイ、クリック外判定、自作フォーカストラップを生成しがち → `<dialog>` / `popover` を使う。
   ```html
   <button commandfor="dlg" command="show-modal">開く</button>
   <dialog id="dlg" closedby="any">
     <p>内容</p>
     <button commandfor="dlg" command="close">閉じる</button>
   </dialog>
   ```
2. **フォームバリデーション**: JS の blur 検証 → CSS `:user-invalid` に。
   ```css
   input:user-invalid { border-color: crimson; }
   ```
3. **パスキー**: WebAuthn の JSON シリアライズヘルパーを使わない、`signalUnknownCredential` を呼ばない（サーバー側で失効したパスキーが残る）。
   ```js
   const options = PublicKeyCredential.parseRequestOptionsFromJSON(json);
   const cred = await navigator.credentials.get({ publicKey: options });
   await fetch("/verify", { method: "POST", body: JSON.stringify(cred.toJSON()) });
   // サーバーが不明なクレデンシャルと判断した場合
   await PublicKeyCredential.signalUnknownCredential({ rpId: "example.com", credentialId });
   ```
4. **ダークモード**: 独自色だけ指定して `color-scheme` を設定しない → スクロールバーやフォーム部品がライトのまま。外部 CSS 読み込み前の白フラッシュ。
   ```html
   <meta name="color-scheme" content="light dark">
   <style>:root { color-scheme: light dark; background: light-dark(#fff, #111); }</style>
   ```
5. **レイアウトシフト**: 画像の width/height は付けるが、Web フォントのスワップ、モバイルのツールバー、クライアントサイド実験、動画の寸法（未ロード時 300×150）を見落とす。
   ```css
   @font-face { font-family: "Brand"; src: url(brand.woff2); font-display: optional; size-adjust: 105%; }
   video { aspect-ratio: 16 / 9; width: 100%; height: auto; }
   .hero { min-height: 100svh; }
   ```
6. **reduced motion への配慮不足**（`prefers-reduced-motion`）。
7. **フォームのオートフィル**（適切な `autocomplete` 属性の欠如）。
8. **タッチジェスチャ**の扱い。
9. **メインスレッドの応答性**（INP、長いタスクの分割: `scheduler.yield()` 等）。
10. **DOM XSS 対策**（`innerHTML` 直書き → Trusted Types / `setHTML()` 等）。

※6〜10 は項目名のみ確認。詳細とコードは原文参照。

### ③ なぜ効果的か
プラットフォームのネイティブ機能を使えば、アクセシビリティ（フォーカス管理、Esc で閉じる）、パフォーマンス、セキュリティが標準で担保され、AI が生成するコード量も減る。Modern Web Guidance を導入すると小型モデルでもネイティブ dialog/popover を使うようになったとの報告もある。

## 5. Charts in HTML and CSS（Keith Cirkel）

参照: https://www.keithcirkel.co.uk/html-graphs/

### ① 目的・問題意識
グラフ描画に JS ライブラリや SVG/Canvas を使わず、HTML の意味的マークアップ（表やリスト、`<meter>`）＋ CSS だけで、棒・列・ヒートマップ・ドーナツ・折れ線・ゲージを描くギャラリー。

### ② 技術詳細
- **棒/列グラフ**: 値でサイズを決めた背景（background-size）でバーを描く。
- **ヒートマップ**: `color-mix()` で値に応じて色を混ぜる。
- **ドーナツ/パイ**: `conic-gradient()` でスライス。
- **ゲージ/メーター**: ネイティブ `<meter>` のバーを隠し、240° の `conic-gradient` を 2 層重ね、`--v` `--max` `--track` カスタムプロパティで値を指定、`radial` マスクで穴を開ける。
- **折れ線**: 各セグメントを細いバーとし、長さを 2 点間の斜辺（`hypot()`）に、角度を `atan2()` で回転。`--y0` `--y1` `--dx` を使用。太さが傾きによらず一定。

再構成した最小例（記事の手法に基づく）:

```html
<ul class="bars">
  <li style="--v: 40">A</li>
  <li style="--v: 75">B</li>
</ul>
<div class="heat" style="--v: .7"></div>
<div class="donut" style="--p: 65"></div>
<span class="seg" style="--y0: 10; --y1: 60; --dx: 50"></span>
```

```css
.bars li {
  background: linear-gradient(steelblue 0 0) no-repeat left / calc(var(--v) * 1%) 100%;
}
.heat {
  background: color-mix(in oklch, crimson calc(var(--v) * 100%), white);
}
.donut {
  aspect-ratio: 1;
  border-radius: 50%;
  background: conic-gradient(teal calc(var(--p) * 1%), #ddd 0);
  mask: radial-gradient(farthest-side, transparent 60%, #000 61%);
}
.seg {
  position: absolute;
  height: 2px;
  width: calc(hypot(var(--dx), var(--y1) - var(--y0)) * 1px);
  transform-origin: left center;
  rotate: atan2(calc(var(--y0) - var(--y1)), var(--dx));
  background: currentColor;
}
```

### ③ なぜ効果的か
データが HTML に残るためスクリーンリーダーや検索に優しく、JS 不要で軽量。最近の CSS 数学関数（`atan2()`、`hypot()`）と `color-mix()` により、以前は不可能だった折れ線やヒートマップも CSS で表現できる。

## 6. Introducing spatial CSS: A developer preview（WebKit）

参照: https://webkit.org/blog/18621/introducing-spatial-css-a-developer-preview/ 、[WebKit explainer](https://github.com/WebKit/explainers/blob/main/css-spatial/explainer.md)、Editor's Draft: drafts.csswg.org/css-spatial-1/

### ① 目的・問題意識
visionOS の Safari で、`<model>` 要素の 3D オブジェクトを複数まとめて配置・相互に関連付けることを、JS や 3D エンジンなしに CSS で実現する提案。

### ② 技術詳細
- 対象: Safari on visionOS 27.3、フラグ「Settings > Apps > Safari > Advanced > Feature flags > CSS Portals」。
- `spatial: portal` で複数の `<model>` を 1 つの共有空間（ポータル）にまとめ、`transform` で配置。
- `portal-action` 属性でシーンをその場で回転（orbit）。`<model>` の `stagemode` 相当を CSS 側で柔軟に設定。
- モデル内の名前付きマーカー（3D エディタの null オブジェクト相当）を `position-anchor: --name#marker` で参照し、DOM 要素やほかのモデルを固定。
- `<model>` は void 要素で入れ子にできないため、モデル同士は `position-context: anchor` を使う。
- `@environment-map`（descriptor: `name`, `format`, `src`）と `environment-map` プロパティで環境光。
- 未対応環境では `spatial` と `inset-front` は無視される（プログレッシブエンハンスメント）。

```html
<div class="scene" portal-action="orbit">
  <model id="board" src="board.usdz"></model>
  <model id="piece" src="piece.usdz"></model>
  <span class="label">ポーン</span>
</div>
```

```css
.scene { spatial: portal; }
#board { anchor-name: --board; }
#piece {
  position-context: anchor;
  position-anchor: --board#octagon-position;
}
.label {
  position: spatial-absolute;
  position-anchor: --piece#nametag;
}
@environment-map studio {
  format: hdr;
  src: url(studio.hdr);
}
.scene { environment-map: studio; }
```
（構文は explainer の断片から再構成。ドラフト段階で変更される可能性あり）

### ③ なぜ効果的か
既存の Anchor Positioning と transform の知識をそのまま 3D 空間に拡張するため、Web 開発者が新しい 3D API を覚えずに空間 UI を作れる。
