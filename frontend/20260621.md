# React Status Issue #478 まとめ

**発行日**: 2026年6月21日頃  
**タイトル**: "facebook/react is out, react/react is in"  
**URL**: https://react.statuscode.com/issues/478

## メインニュース：`facebook/react` → `react/react` へのリポジトリ移行

### ① 目的・問題意識

2025年10月にMetaがReact Foundationの設立意向を発表し、2026年2月24日にLinux Foundation傘下で正式発足した。これにより、長らくMetaの管理下にあった `facebook/react`・`facebook/react-native` 等のGitHubリポジトリが `react` オーガニゼーション（`github.com/react/react`）へ移管された。これが本号のメインニュースである。

### ② 技術詳細

**React Foundation の概要**
- **公式サイト**: https://react.foundation/
- **公式ブログ発表**: https://react.dev/blog/2026/02/24/the-react-foundation
- **Platinum創設メンバー**: Amazon、Callstack、Expo、Huawei、Meta、Microsoft、Software Mansion、Vercel
- **エグゼクティブディレクター**: Seth Webster（元Meta React担当）

**移管済みリポジトリ**
- `react/react`（旧 `facebook/react`）
- `react/react-native`（旧 `facebook/react-native`）
- Yoga、JSX、Metro、React-Strict-DOM、Create-React-App など

**Foundationの計画**
- エコシステムライブラリメンテナーへの資金援助・グラント支給
- 公式Reactグッズストア（収益はメンテナーへ）
- 四半期ごとの透明性レポート
- 「Contributor Status」ページ（ゲーミフィケーション付き）
- React Confの運営引き継ぎ

**タイムライン**
- 2025年10月: Meta、React Foundation設立意向を発表
- 2026年2月24日: React Foundation正式発足
- 2026年Q1-Q2: GitHubリポジトリ移管完了

### ③ なぜ効果的か

ガバナンスをMetaの単一企業から独立した財団に移すことで、特定企業の利害に左右されない長期的なメンテナンスが可能になる。Linux Foundationという実績ある組織の傘下に入ることで、Node.js や OpenJS Foundation に続く成功例として、コミュニティへの信頼性と安定性が向上する。

## 記事2: React Router v8 リリース（June 17, 2026）

**公式ブログ**: https://remix.run/blog/react-router-v8  
**GitHub Discussion**: https://github.com/remix-run/react-router/discussions/14468

### ① 目的・問題意識

年次メジャーリリーススケジューンに移行した React Router の最初のメジャーアップデート。Node.js 20 のEOLタイムラインに合わせて6月をリリース月とした。「Future Flags戦略」により事前に非互換変更を導入してあったため、破壊的変更は最小限。

### ② 技術詳細

**最小動作要件（変更点）**

| 依存関係 | 必要バージョン |
|---|---|
| Node.js | 22.22.0+ |
| React | 19.2.7+ |
| Vite | 7.0.0+ |

**ESM専用（CJSサポート終了）**

```json
// package.json（React Router v8パッケージ）
{
  "type": "module"
}
```

**`react-router-dom` パッケージ廃止**

```js
// v7（旧）
import { Link, NavLink } from 'react-router-dom';

// v8（新）
import { Link } from 'react-router';
import { NavLink } from 'react-router/dom'; // ブラウザ固有ユーティリティ
```

**v7のfuture flagsがすべてデフォルト化**

- `v8_middleware`: ルートレベルのミドルウェアパイプライン
- `v8_viteEnvironmentApi`: ViteのEnvironment APIデカップリング
- `v8_splitRouteModules`: ルートモジュールの分割
- `v8_trailingSlashAwareDataRequests`: データフェッチのトレイリングスラッシュ対応
- `v8_passThroughRequests`: クリーンなリクエストパススルー

**その他の変更**

```js
// metaのloaderData（v8）
export const meta = ({ loaderData }) => [
  { title: loaderData.title }
];
// 旧: data パラメータ → 新: loaderData に名称変更

// Cloudflare dev proxyの変更
// 旧: @react-router/dev/vite/cloudflare
// 新: @cloudflare/vite-plugin（Cloudflare公式Viteプラグイン）
```

**v7からのアップグレード手順**

```bash
# 1. react-router-dom を削除
npm uninstall react-router-dom

# 2. バージョン更新
npm install react-router@8 @react-router/dev@8

# 3. importsの修正
# react-router-dom → react-router / react-router/dom
```

### ③ なぜ効果的か

Future Flags戦略によりメジャーアップグレードの痛みを最小化しつつ、ESM専用・Node.js LTSサポートの明確化により、モダンJavaScriptエコシステムとの整合性が高まった。年次リリーススケジュールにより、開発者は変更を予測しやすくなる。

## 記事3: React CompilerのRust移植（PR #36173）

**PR**: https://github.com/react/react/pull/36173  
**マージ日**: 2026年6月9日（435コミット）  
**実装者**: Joseph Savona（大部分をAIが実装）

### ① 目的・問題意識

ReactコンパイラのコアロジックをTypeScript（Babel）からRustに移植することで、ビルド時間を大幅に短縮する。特に大規模モノレポ・CI環境でのコンパイル速度がボトルネックになっていた。

### ② 技術詳細

**パフォーマンス数値**

| 測定箇所 | 改善率 |
|---|---|
| Babelプラグインとして（シリアライズコスト込み） | **約3倍高速** |
| 変換ロジック単体 | **約10倍高速** |

**アーキテクチャ**

TypeScript版と同一のアーキテクチャを維持：
```
AST → HIR（高水準中間表現）→ CFG/SSA変換 → 最適化済みコード
```

- Babel AST互換の「Rust表現」をパブリックAPIとして使用
- 1,725個のテストフィクスチャを全合格
- TypeScript版と99.9%同一出力（最終的に1803/1803コード出力で合格）

**3つの統合対応**

```toml
# Cargo.toml（OXC統合の例）
[dependencies]
react_compiler_transform = { version = "0.135" }
```

1. **Babel統合**: 既存プロジェクトとの互換性
2. **OXC統合（Rust crate v0.135〜）**: Vite/Rolldown経由で利用可能
3. **SWC統合**: SWC Rust crate v68.1でリリース済み

**エコシステムへの波及**

```js
// vite.config.ts（React Compiler with Rolldown）
export default {
  plugins: [react()],
  transform: {
    reactCompiler: true  // Rolldown PR マージ済み
  }
};
```

- OXCのlint: `react/react-compiler` ルール（実験的）追加。ReactSpectrum・Sanityでx5-6倍高速化を報告
- Rolldown PR: `transform.reactCompiler` オプションを公開（マージ済み）
- oxlint 1.70でReact Compilerルールを追加

**技術的課題と解決**

1. **スコープ解析**: BabelのスコープAPIに依存（将来は独自実装予定）
2. **エラーハンドリング**: 約55個のpanicを`Err(CompilerDiagnostic)`に変換
3. **アリーナベースのAST構造**: Rustの所有権システムに適合させるため採用

### ③ なぜ効果的か

React CompilerがRustに移植されることで、oxlint・SWC・Rolldownなどのモダンなビルドツールチェーンとの統合が自然になる。CI/CDパイプライン全体のビルド時間短縮に直結し、大規模プロジェクトでの採用障壁が下がる。

## 記事4: TanStack Table v9 Beta

**公式ブログ**: https://tanstack.com/blog/tanstack-table-v9-taking-form

### ① 目的・問題意識

React Compilerが安定版になったことで、TanStack Table v8が正しく動作しなくなる問題が発生した。v9では状態管理システムを根本から再設計し、React Compiler互換性を実現した。

### ② 技術詳細

**アーキテクチャの刷新: アトムベース状態管理**

```ts
// v9のイメージ：各機能が独立したアトムスライスを持つ
import { createTable, sortingFeature, paginationFeature } from '@tanstack/table-core';

const table = createTable({
  data,
  columns,
  features: [sortingFeature, paginationFeature], // ツリーシェイキング対応
});
```

**主な変更点**

| 項目 | v8 | v9 |
|---|---|---|
| 状態管理 | モノリシックなstate object | アトムスライス（TanStack Store） |
| React Compiler互換 | × | ○ |
| ツリーシェイキング | 限定的 | 機能をプラグインとしてimport |
| 再レンダリング | 全体 | 購読スライスのみ |

**再利用可能なテーブルフック**

```ts
// v9: createTableHookでカスタムテーブルを定義
const useMyTable = createTableHook({
  features: [sortingFeature, filteringFeature],
  defaultOptions: { pageSize: 20 },
});

// コンポーネントで使用
const { table } = useMyTable({ data, columns });
```

**カスタム機能API**

```ts
const myCustomFeature = createFeature({
  getDefaultOptions: () => ({ myOption: false }),
  onStateChange: (state, nextState) => nextState,
  createTable: (table) => ({
    myCustomMethod: () => { /* ... */ }
  }),
});
```

### ③ なぜ効果的か

TanStack Storeというフレームワーク非依存のリアクティブ基盤を採用することで、React・Vue・Solidなど複数のアダプターから同一の状態を読み書きできる。大規模データグリッドでのメモリ効率とレンダリングパフォーマンスが改善される。

## 記事5: Astro 6.4 / Sätteri（RustベースMarkdown/MDXエンジン）

**公式ブログ**: https://astro.build/blog/astro-640/

### ① 目的・問題意識

Astroのコンテンツビルドで使用していたUnified（JSベースMarkdown/MDXパイプライン）が大規模サイトでビルド時間のボトルネックになっていた。Rustベースの代替エンジンを開発することで抜本的な高速化を実現する。

### ② 技術詳細

**Sätteriの概要**

- Rust製のMarkdown/MDXプロセッサ
- 独自AST仕様・パーサー・シリアライザーを持つゼロベース実装
- npmパッケージ: `@astrojs/markdown-sätteri`

**パフォーマンス比較**

| エンジン | ビルド時間（AstroドキュメントサイトでのAstro公式計測） |
|---|---|
| Unified（JS） | 120秒 |
| Sätteri（Rust） | 55秒（**約54%削減**） |

**設定方法（Astro 6.4）**

```js
// astro.config.mjs
import { defineConfig } from 'astro/config';
import { sätteri } from '@astrojs/markdown-sätteri';

export default defineConfig({
  markdown: {
    // デフォルトは unified() - 既存プロジェクトは変更不要
    processor: sätteri(),
  },
});
```

**制限事項**

- remarkプラグインおよびrehypeプラグインをサポートしない
- 将来のAstroメジャーバージョンでデフォルトプロセッサになる予定

### ③ なぜ効果的か

Rustの低レベル実行速度を活かし、大規模コンテンツサイト（ドキュメントサイト、ブログ等）のビルド時間を半分以下に削減できる。段階的採用が可能（設定1行で切り替え可能）な設計のため、移行リスクが低い。

## 記事6: Motion v12.40 - arc()モーションのサポート

**CHANGELOG**: https://github.com/motiondivision/motion/blob/main/CHANGELOG.md  
**リリース日**: 2026年5月21日

### ① 目的・問題意識

CSSの `offset-path` では静的なパスしか指定できず、動的な曲線アニメーションが困難だった。x/yアニメーションや layouts アニメーションと組み合わせて曲線パスを動的に生成できる `arc()` 関数を追加。

### ② 技術詳細

**arc()の使用例**

```tsx
import { motion, arc } from 'motion/react';

// 要素が弧を描いて移動
<motion.div
  animate={{ x: 200, y: 100 }}
  transition={{
    duration: 1,
    path: arc(), // 直線ではなく弧を描く
  }}
/>
```

**arc()のオプション**

```tsx
// カーブの方向・強度を指定
<motion.div
  animate={{ x: 200, y: 100 }}
  transition={{
    path: arc({ offset: 0.5 }), // 弧の強度調整
  }}
/>
```

- `transition.path: arc()` を指定するだけで有効化
- x/yアニメーション・layoutアニメーションと組み合わせ可能
- 動的なカーブをプログラムで生成できる（CSSの `offset-path` では不可能）

### ③ なぜ効果的か

UIの動きに視覚的な深みを与えるカーブアニメーションを宣言的に実現できる。特にドラッグ＆ドロップや要素の再配置アニメーションに応用すると、UIの洗練度が増す。
