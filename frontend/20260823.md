## 2. TanStack Form v2 Alpha リリース

> ソース: https://tanstack.com/blog/announcing-tanstack-form-v2-alpha

### ① 目的・問題意識

TanStack Form v1 は1年以上運用され多くのフィードバックが集まった。特に「バリデーターの記述が冗長」「同一バリデーターを複数イベントに登録できない」という問題が顕在化。v2 ではバリデーション API を再設計し、より柔軟でタイプセーフなフォーム管理を実現する。

### ② 具体的な技術詳細・コード

**v1 の問題点（同一バリデーターを複数イベントで動かすには重複が必要だった）:**

```typescript
// v1: changeとblurの両方で動かすには、同じバリデーターを2回書く必要があった
const form = useForm({
  defaultValues: { name: '' },
  validators: {
    onChange: mySchema,
    onBlur: mySchema, // 重複
  },
})
```

**v2 の新しいパイプライン方式:**

```typescript
// v2: pipelineで各バリデーターに発火イベントを宣言する
const form = useForm({
  defaultValues: { name: '' },
  validators: [
    {
      run: mySchema,
      triggers: ['change', 'blur'], // 1つのエントリで複数トリガーを指定
    },
  ],
})
```

**bailIfInvalid による短絡評価:**

```typescript
const form = useForm({
  defaultValues: { email: '' },
  validators: [
    {
      run: requiredValidator,
      triggers: ['change'],
      bailIfInvalid: true, // これが失敗したら後続バリデーターはスキップ
    },
    {
      run: emailFormatValidator,
      triggers: ['change'],
    },
  ],
})
```

**サポートスキーマライブラリ（Standard Schema 準拠）:**
- Zod v3.24.0 以上
- Valibot v1.0.0 以上
- ArkType v2.1.20 以上
- Yup v1.7.0 以上

**フォームコンポジション（createFormHook）:**

```typescript
const { useAppForm } = createFormHook({
  fieldContext,
  formContext,
  fieldComponents: {
    TextField,
    SelectField,
  },
  formComponents: {
    SubmitButton,
  },
})
```

**SSR サポート（useActionState との統合）:**

```typescript
const [serverState, formAction] = useActionState(handleFormSubmit, null)

const form = useForm({
  defaultValues: { name: '' },
  initialServerFormState: serverState,
})

return (
  <form action={formAction}>
    {/* ... */}
  </form>
)
```

### ③ なぜ効果的か

パイプライン方式により、各バリデーターの責務（どのイベントで発火するか・エラー時に後続を止めるか）が明示的に宣言でき、重複コードが排除される。Standard Schema 対応でスキーマライブラリを問わず統一的な記法が使える。このアルファは React アダプターに集中しており、Vue・Solid・Angular・Lit も後続リリースで対応予定。

## 3. GTKX — React で Linux ネイティブアプリを構築

> ソース: https://gtkx.dev/ / https://github.com/gtkx-org/gtkx

### ① 目的・問題意識

GTK4 を使った Linux デスクトップアプリの開発は、C/C++/Python での記述が主流で学習コストが高かった。GTKX は React と TypeScript で GTK4 ネイティブアプリを書けるようにするフレームワーク。Electron のようにブラウザエンジンを内包せず、真のネイティブ GTK ウィジェットを使う。

### ② 具体的な技術詳細・コード

GTKX は React reconciler を GTK4 上に実装し、GObject（GTK の基本オブジェクト）をすべて JSX 要素として公開する。

**インストール:**

```bash
npx create-gtkx-app my-app
cd my-app
npm run dev
```

**カウンターアプリの例:**

```typescript
import * as Gtk from "@gtkx/gi/gtk";
import {
  GtkApplication,
  GtkApplicationWindow,
  GtkBox,
  GtkButton,
  GtkLabel,
} from "@gtkx/jsx/gtk";
import { createRoot, quit } from "@gtkx/react";
import { useState } from "react";

const Counter = () => {
  const [count, setCount] = useState(0);
  return (
    <GtkApplicationWindow
      title="Hello GTKX"
      defaultWidth={400}
      defaultHeight={300}
      onCloseRequest={quit}
    >
      <GtkBox
        orientation={Gtk.Orientation.VERTICAL}
        spacing={20}
        marginTop={40}
        marginBottom={40}
        marginStart={40}
        marginEnd={40}
        valign={Gtk.Align.CENTER}
        halign={Gtk.Align.CENTER}
      >
        <GtkLabel cssClasses={["title-1"]}>Welcome to GTKX!</GtkLabel>
        <GtkLabel cssClasses={["title-2"]}>{`Count: ${count}`}</GtkLabel>
        <GtkButton
          label="Increment"
          onClicked={() => setCount((c) => c + 1)}
          cssClasses={["suggested-action", "pill"]}
        />
      </GtkBox>
    </GtkApplicationWindow>
  );
};

const app = new Gtk.Application({ applicationId: "dev.gtkx.counter" });
createRoot(app).render(<Counter />);
app.run([]);
```

**主要機能:**
- **Fast Refresh**: ファイル保存時に実行中のウィンドウをパッチ更新（HMR 相当）
- **CSS-in-JS スタイリング**: `@gtkx/css` パッケージで CSS ライクなスタイリング
- **React Spring アニメーション**: GTK ウィジェットに spring アニメーションを適用
- **型安全**: GIR（GObject Introspection Repository）から全クラス・シグナル・列挙型・プロパティの型定義を自動生成
- **テスト**: Vitest + ヘッドレス Wayland コンポジター上の仮想ディスプレイでテスト実行

**システム要件:**
- Linux + GTK4（4.20以上） + GLib 開発ライブラリ
- Adwaita 1.8 以上
- x64/arm64 glibc Linux 向けプリビルドバイナリあり（他ターゲットは Rust toolchain で自前ビルド）

### ③ なぜ効果的か

React の宣言的 UI モデルと hooks（useState, useEffect など）がそのまま GTK ウィジェット開発に適用できる。ブラウザエンジン不要でネイティブウィジェットを使うため、Electron と比較してメモリ使用量が大幅に少ない。Web 開発者が既存の React 知識でクロスプラットフォーム（Linux）デスクトップアプリを開発できる。

## 4. React Native 0.87 リリース

> ソース: https://reactnative.dev/blog/2026/08/11/react-native-0.87

### ① 目的・問題意識

React Native の TypeScript 型定義がソースコードと乖離していた問題を解決し、Swift Package Manager 対応で iOS 開発の CocoaPods 依存を削減。Metro バンドラーのパフォーマンスも大幅改善。

### ② 具体的な技術詳細・コード

#### Strict TypeScript API がデフォルトに

RN 0.80 でオプトインとして導入された Strict TypeScript API が、0.87 でデフォルトになった。型定義はソースコードから直接生成されるため、型とランタイムのズレが解消。

**旧来の deep import（0.87 で型エラーになる）:**

```typescript
// NG: Libraries/ への deep import は型エラー
import { Animated } from 'react-native/Libraries/Animated/Animated';

// OK: 公開 API から import
import { Animated } from 'react-native';
```

**レガシーモード（0.88 まで利用可能）:**

```json
// tsconfig.json
{
  "compilerOptions": {
    "customConditions": ["react-native-legacy-deep-imports"]
  }
}
```

#### Metro 0.87 アップデート（0.84 → 0.87）

- ソースマップ生成が **2倍高速化**
- メモリ使用量が **半減**（ソースマップのストレージを効率化）
- TypeScript・ESM 形式の設定ファイル（`metro.config.mts`）が安定サポート

**削除された設定形式:**

```yaml
# NG: YAML 設定ファイルはサポート終了
# metro.config.yaml や .es6 拡張子のファイルも非対応に
```

**新しい設定ファイル（ESM/TypeScript 対応）:**

```typescript
// metro.config.mts（安定サポート）
import { getDefaultConfig, mergeConfig } from '@react-native/metro-config';

const config = {};
export default mergeConfig(getDefaultConfig(__dirname), config);
```

#### 実験的 Swift Package Manager サポート

CocoaPods を使わずに Swift Package Manager（SwiftPM）で iOS 依存を管理できる実験的機能。

**有効化:**

```bash
# ios/ ディレクトリで実行
npx react-native spm -- deintegrate
```

- CocoaPods を除去し、Swift パッケージ参照を既存の `.xcodeproj` に注入
- 初回セットアップ後は `pod install` 不要
- Ruby・Bundler・CocoaPods が不要になる
- 復元: `npx react-native spm deinit`

#### Breaking Changes まとめ

| 変更 | 対処法 |
|------|--------|
| `InteractionManager` 削除 | `requestIdleCallback` を使用 |
| `Libraries/` への deep import が型エラー | 公開 API から import するか `react-native-legacy-deep-imports` を設定 |
| `src/private/` への deep import 削除 | 公開 API を使用 |
| YAML Metro 設定ファイル非対応 | `.js`/`.ts`/`.mts` 形式に移行 |
| `.es6` 拡張子の設定ファイル非対応 | 同上 |
| `Modal` の `animated` prop 削除 | `animationType` prop を使用 |

#### 最低ツールチェーン要件の引き上げ

- Node.js: **22** 以上
- Android Gradle Plugin: **9** 以上
- Kotlin: **2.0+**

### ③ なぜ効果的か

Strict TypeScript API により、型とランタイムの乖離がなくなり IDE の補完精度が向上。Metro の高速化・省メモリ化により開発体験が向上。SwiftPM サポートで iOS 開発環境のセットアップがシンプルになり、Ruby/CocoaPods のバージョン管理問題を回避できる。

## 5. Meta が React Compiler を Rust に移植

> ソース: https://www.infoq.com/news/2026/07/meta-react-compiler-rust/  
> PR: https://github.com/react/react/pull/36173

### ① 目的・問題意識

React Compiler（旧称 React Forget）は TypeScript で実装されていたが、Rust ベースのツールチェーン（Turbopack、OXC 等）との統合においてボトルネックになっていた。Rust に移植することで Turbopack への直接統合が可能になり、大幅な速度向上を実現する。

### ② 具体的な技術詳細

- 123,000 行超の TypeScript コードを Rust に移植（大部分は AI を活用、人間エンジニアが監督）
- 1,725 個のテストフィクスチャが全パス、TypeScript 版とほぼバイト単位で一致する中間状態を生成

**パフォーマンス向上:**

| シナリオ | 向上率 |
|----------|--------|
| Babel プラグインとして（TypeScript 版比） | 約 3倍高速 |
| 独立変換ロジック（ベストケース） | 最大 10倍高速 |
| Turbopack にネイティブ統合 | ビルド全体で 40%以上高速化 |
| 実使用（大規模コードベース ~860 コンポーネント） | +71ms（394ms → 465ms）、Babel 版の約 20倍高速 |

**実環境での成果:**
- Instagram・Meta Quest Store で量産運用中
- 初期ページロード最大 12% 向上
- 特定 UI インタラクションが 2.5倍以上高速化
- Sanity Studio で全体レンダリング時間・レイテンシが 20〜30% 削減

### ③ なぜ効果的か

Rust は JIT コンパイルを必要とせず、コンパイル時に最適化されたネイティブコードを生成するため、インタプリタ型の TypeScript よりも圧倒的に高速。Turbopack との同プロセス統合により IPC オーバーヘッドもなくなる。現在は「実験的・WIP」ポートだが、将来的には Next.js 16.4 以降で恩恵を受けられる見込み。

## 6. Bun 1.4 リリース — React Compiler を組み込みサポート

> ソース: https://bun.com/blog/bun-v1.4

### ① 目的・問題意識

これまで React Compiler を Bun プロジェクトに導入するには、Babel プラグインを設定する必要があり手間がかかった。Bun 1.4 では React Compiler をバンドラーにネイティブ統合し、設定なしで高速に利用できるようにする。

### ② 具体的な技術詳細・コード

**CLI フラグ:**

```bash
bun --react-compiler run src/index.tsx
```

**Bun.build API:**

```typescript
await Bun.build({
  entrypoints: ['./src/index.tsx'],
  outdir: './dist',
  reactCompiler: true, // React Compiler を有効化
});
```

**Next.js 16.3 との組み合わせ:**

```bash
bun --bun next build  # Turbopack + React Compiler で自動動作
```

**パフォーマンス比較（約860コンポーネントの大規模コードベース）:**

| 方法 | ビルド時間 |
|------|-----------|
| React Compiler なし | 394 ms |
| Bun 組み込み React Compiler あり | 465 ms（+71ms） |
| Babel プラグイン経由 | 9,150 ms（+9.15s） |

Bun の組み込み実装は Babel プラグインより約 **20倍高速**。

### ③ なぜ効果的か

Bun の組み込み Rust ベーストランスパイラに React Compiler の変換ロジックを直接統合することで、Babel を介さずに最高速でコンパイルできる。設定ファイルの変更なしに既存プロジェクトで試せるため、導入コストが極めて低い。

## 7. Next.js 16.3 — メモリ最適化・Instant Navigations・Turbopack 高速化

> ソース: https://nextjs.org/blog/next-16-3

### ① 目的・問題意識

長時間の開発セッションで発生するメモリリーク（`FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed`）の軽減、ビルド速度の向上、SPA に匹敵するナビゲーション速度の実現。

### ② 具体的な技術詳細・コード

#### Instant Navigations（オプトイン）

```typescript
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    instantNavigations: true,
    partialPrefetching: true, // Partial Prefetching と組み合わせ
  },
}

export default nextConfig
```

SPA と同等のナビゲーション応答速度を実現。Partial Prefetching と組み合わせることで、プリフェッチリクエスト数を削減しながら高速化を達成。

#### メモリ最適化

- 長時間開発セッションで最大 **90% のメモリ削減**
- 変更されていないアーティファクトのキャッシュ再利用でリピートビルドが高速化
- `FATAL ERROR: CALL_AND_RETRY_LAST Allocation failed`（JS ヒープのメモリ不足エラー）が大幅に減少

#### TypeScript 7 対応

```bash
# TypeScript 7 の isolatedDeclarations モードで型チェック
next build --type-check
```

TypeScript 7 の並列型チェック機能により、大規模プロジェクトでの型チェック速度が向上。

#### AI エージェント向けドキュメント

インストール済みバージョンに合わせた AI コーディングエージェント向けドキュメントを提供。エージェントが適切な API を参照できるようにする仕組み。

#### サーバーサイドスループット向上

最大 **22% 多くのリクエストを処理**できるようになった（負荷テスト条件下）。

### ③ なぜ効果的か

Turbopack の増分コンパイルとキャッシュ戦略の改善により、変更されたモジュールのみを再ビルドする効率が上がった。Instant Navigations は RSC ペイロードを事前に準備しておくことで、クリック時のレイテンシをゼロに近づける。メモリ最適化は特に大規模プロジェクトや長時間開発セッションで恩恵が大きい。

## 8. WebMCP / `use-webmcp-tool` — React で AI エージェントにツールを公開

> ソース: https://github.com/GoogleChromeLabs/use-webmcp-tool  
> Chrome ドキュメント: https://developer.chrome.com/docs/ai/webmcp

### ① 目的・問題意識

AI エージェントがウェブアプリを操作する際、DOM スクレイピング・アクセシビリティツリー解析・スクリーンショットを頼りにしていた。WebMCP は Web ページが AI エージェントに直接「ツール」を公開できる W3C 仕様（実験的）。`use-webmcp-tool` は React でこの API を宣言的に扱うための公式フック。

### ② 具体的な技術詳細・コード

**インストール:**

```bash
npm install @googlechromelabs/use-webmcp-tool
```

**基本的な使い方:**

```typescript
import { useWebMcpTool } from '@googlechromelabs/use-webmcp-tool';

function SearchComponent() {
  useWebMcpTool({
    name: 'search',
    description: 'Search the product catalog',
    parameters: {
      type: 'object',
      properties: {
        query: { type: 'string', description: 'Search query' },
      },
      required: ['query'],
    },
    execute: async ({ query }) => {
      const results = await fetchProducts(query);
      return { results };
    },
  });

  return <div>{/* 通常のUIレンダリング */}</div>;
}
```

**動作原理:**
- コンポーネントのマウント時に `document.modelContext.registerTool()` を呼び出してツールを登録
- アンマウント時に `AbortSignal` でツールの登録を解除（自動クリーンアップ）
- WebMCP API が未対応のブラウザでは **no-op にフォールバック**（安全に動作）

**要件:**
- React 18 以上
- ESM 形式、TypeScript 型定義同梱
- ランタイム依存なし

**`webmcp-react`（別プロジェクト）:**

```typescript
import { useMcpTool } from 'webmcp-react';

// Agentcat 社製のより高機能な実装
// SSR セーフ、Strict Mode セーフ、W3C spec 準拠
useMcpTool({
  name: 'addToCart',
  handler: async (params) => addItem(params.productId),
});
```

### ③ なぜ効果的か

DOM を解析するアプローチと比較して、開発者が明示的に公開したツールだけをエージェントが使うため、**予測可能で安全なエージェント統合**が実現できる。React コンポーネントのライフサイクルに連動してツールの登録・解除が自動管理されるため、メモリリークや「消えたはずのツールが残る」問題を防げる。
