## 1. Reactの親ツリーとオーナーツリーのビジュアル記法

**記事:** [A visual notation for React's parent and owner trees](https://julesblom.com/writing/react-visual-notation)
**著者:** Jules Blom

### ① 目的・問題意識

Reactのコンポーネント構造には2種類の階層が存在する。

- **親ツリー（Parent Tree）**: DOMにレンダリングされた結果のネスト構造。ReactDevToolsの「⚛️ Components」タブで見える階層。
- **オーナーツリー（Owner Tree）**: どのコンポーネントのJSXがそのエレメントを生成したか、という生成関係の階層。コード上で書いたJSXがそのまま反映される。

2つのツリーが乖離するのは、JSXをpropsとして渡す場合など。この乖離をコードだけで説明するのは困難であり、視覚的な記法が必要とされていた。

### ② 具体的な技術詳細

**記法の要素:**
- コンポーネントはボックスで表現
- 親ツリーの関係は通常の矢印（実線）で表現
- オーナー関係は破線アーク（dashed arc）で表現
- propsとして渡されるJSXは、オーナーから消費者へのアーク付き移動ドットで表現

**React Trees Playground:**
著者はこの記法を実際に体験できるツールも構築した。

- URL: `julesblom.com/react-trees`
- Reactコードを貼り付けると、親ツリーとオーナーツリーを自動で図示
- `bippy` ライブラリを使用して実行中のReactアプリのファイバーツリーを読み取り

**具体的なユースケース例:**

```jsx
// oJSXをpropsとして渡すパターン
function Layout({ children }) {
  return <div className="layout">{children}</div>;
}

function App() {
  return (
    <Layout>
      <Header />   {/* AppがHeader のオーナー、LayoutがHeaderの親 */}
    </Layout>
  );
}
```

このケースでは:
- 親ツリー: `Layout > Header`
- オーナーツリー: `App > Header`（AppのJSXでHeaderを生成したため）

### ③ なぜ効果的か

- コードだけでは見えないオーナーシップの関係を視覚化できる
- パフォーマンス最適化（レンダリングの伝播）を理解しやすくなる
- propsとしてのJSX受け渡しパターンの教育に役立つ
- 著者の既存シリーズ（データフロー、レンダリングパフォーマンス、Contextプロバイダー）と連動

## 2. Next.js 16.4

**記事:** [Next.js 16.4](https://nextjs.org/blog/next-16-4)
**リリース日:** 2026年10月6日

### ① 目的・問題意識

Next.js 16.4はCache Components（部分的プリレンダリング）を全アプリへの推奨デフォルトとして昇格させ、Turbopackのビルドキャッシュの効率化、React 19.3対応を実現したメジャーな機能リリース。

### ② 具体的な技術詳細

#### Cache Components（`'use cache'`ディレクティブ）

新しい`create-next-app`プロジェクトではデフォルトで有効になった。既存プロジェクトは`next.config.ts`でオプトイン:

```typescript
// next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  experimental: {
    partialPrefetching: true,
  },
}

export default nextConfig
```

**`'use cache'`の使い方:**

```tsx
import { cacheLife, cacheTag } from 'next/cache'

// キャッシュされるサーバーコンポーネント
async function Stats() {
  'use cache'
  cacheLife('hours')  // キャッシュ有効期間
  cacheTag('dashboard-stats')  // タグベースの無効化キー
  
  const data = await fetch('/api/stats').then(r => r.json())
  return <div>{data.value}</div>
}

// ページ構成例
export default function Dashboard() {
  return (
    <>
      <Header />  {/* 静的プリレンダリング */}
      <Stats />   {/* キャッシュされた動的コンテンツ */}
      <Suspense fallback={<Spinner />}>
        <Notifications />  {/* 真に動的なコンテンツ */}
      </Suspense>
    </>
  )
}
```

#### `ensureStatic`ルートセグメント設定

```tsx
// ルートが静的であることをビルド時に検証
export const ensureStatic = 'navigation' // 最も厳格

// 'navigation': ルートへのナビゲーションがリクエスト時にレンダリングしてはいけない
// 'shell': / 'prefetch': より緩い検証レベル
```

`'navigation'`では以下の使用でビルド失敗:
- `cookies()`、`headers()`
- サーバーの`searchParams`
- 5分未満で期限切れになるキャッシュ
- キャッシュされていないデータフェッチ

#### Turbopackの改善

- ディスクキャッシュのサイズを最大20〜25%削減
- 実験的ガベージコレクター: `turbopackGc: true`
- レイジーHMR: 表示していないページのサーバーモジュール変更時に不要な再コンパイルを回避
- 実験的なレイジー動的インポート（`turbopackLazyDynamicImports`）

#### 移行ガイド

| 旧API | 新API |
|-------|-------|
| `unstable_cache()` | `'use cache'`ディレクティブ |
| `revalidate` | `cacheLife({ revalidate: N })` |
| `dynamic = 'force-dynamic'` | 削除（現在デフォルト） |

### ③ なぜ効果的か

- Partial Prerenderingにより、静的・キャッシュ・動的コンテンツを1ルートに混在できる
- `'use cache'`はキャッシュキーを引数と閉包変数から自動生成するため設定が簡単
- Turbopackキャッシュ縮小により開発ビルドが高速化
- `ensureStatic`でビルド時に静的化の誤りを検出できる

## 3. TanStack Charts 1.0

**記事:** [TanStack Charts 1.0](https://tanstack.com/blog/tanstack-charts-1-0)
**リリース日:** 2026年10月5日

### ① 目的・問題意識

ReactのチャートライブラリはCharts.js、Rechartsなど既存ソリューションがあるが、成長に伴いAPIの限界に突き当たることが多い。TanStack Chartsは「グラフィックスの文法（Grammar of Graphics）」に基づき、コンポーザブルなAPIで小さく始めて大きく育てられる設計を目指す。1.0.0で安定版APIコントラクトが確立された。

### ② 具体的な技術詳細

**コンセプト:** Observable Plotに近いAPI設計

**ビルディングブロック:**
- **Data**: データソースの定義
- **Marks**: 描画要素（Line、Bar、Dot等）
- **Channels**: 視覚的チャンネルへのフィールドマッピング
- **Scales**: 軸とスケールの定義
- **Guides**: 軸ラベル・グリッド等のガイド
- **Layers**: 複数Markのレイヤー合成

**インストール:**
```bash
npm install @tanstack/charts @tanstack/react-charts
```

**基本的なラインチャート例:**

```tsx
import { defineChart } from '@tanstack/charts'
import { ChartRoot, LineMark, Axis } from '@tanstack/react-charts'

const myChart = defineChart({
  marks: [
    LineMark({
      data: salesData,
      x: 'date',
      y: 'revenue',
    }),
  ],
  scales: {
    x: { type: 'time' },
    y: { type: 'linear' },
  },
})

export function SalesChart() {
  return (
    <ChartRoot chart={myChart}>
      <Axis orient="bottom" />
      <Axis orient="left" />
    </ChartRoot>
  )
}
```

**SVGとCanvasの混在:**

```tsx
import { DotMark } from '@tanstack/charts/canvas'  // Canvasレンダラー

const myChart = defineChart({
  marks: [
    LineMark({ data, x: 'date', y: 'value' }),  // SVG
    DotMark({ data, x: 'date', y: 'value' }),    // Canvas（大量データ向け）
  ],
})
// ツールチップ・アクセシビリティはSVG/Canvas混在でも動作
```

**バンドルサイズ:** 基本的なReactラインチャートで約32.1 kB (gzip)

**インタラクション:**
- ポインター・キーボードフォーカス対応
- セレクションコールバック
- アクセシブルなHTMLライブリージョンによるツールチップ

### ③ なぜ効果的か

- Grammar of Graphicsにより、単一のAPIでライン・バー・散布図など任意のチャートタイプを組み合わせ可能
- SVGデフォルト + Canvasオプトインで小規模から大規模データまでカバー
- TanStackエコシステム（Query、Table、Router）との統合設計
- エージェント（AI）に「use TanStack Charts」と指示するだけで使えるスキルファイルも同梱

## 4. CoinbaseがReact Nativeから離脱

**記事:** Coinbase is migrating its consumer trading app from React Native to native Swift/Kotlin
**発表日:** 2026年10月1日頃

### ① 目的・問題意識

CoinbaseはReact Nativeで統一モバイルコードベースを運用してきた（2021年の移行）が、ネイティブパフォーマンスの限界、OS新機能へのアクセス遅延、クラッシュ率の問題から、完全ネイティブ（Swift + Kotlin）への移行を決断。

### ② 具体的な技術詳細

- **移行先:** iOSはSwift、AndroidはKotlin
- **規模:** 「会社の歴史上最も重要なクライアントプラットフォームの転換」（求人票より）
- **ツール活用:** AI支援コード生成を活用したグリーンフィールドリライト
- **理由（公式発表より）:**
  - 起動時間の改善
  - クラッシュ率の低下
  - iOS/Androidの新機能への同日アクセス
  - ネイティブOSとの密接な統合

### ③ なぜ効果的か（逆説的な観点）

**React Nativeからネイティブへ戻す理由:**
- フィンテックアプリは生体認証、Push通知、ウィジェットなどOS機能を即日使う必要がある
- クリティカルな金融UIではミリ秒単位のアニメーション品質が問われる
- ネイティブコードベース分離でiOS/Androidの独立したリリースサイクルが可能に

**コミュニティの懸念:**
- iOS/Android別コードベースでの機能パリティ維持の難しさ
- React Nativeでの投資と知識の喪失
- AI支援リライトの信頼性

## 5. Redux Toolkit 2.13

**記事:** [Release v2.13.0 - reduxjs/redux-toolkit](https://github.com/reduxjs/redux-toolkit/releases/tag/v2.13.0)
**リリース日:** 2026年9月下旬

### ① 目的・問題意識

Redux Toolkit 2.13はAPIの変更なしにビルドツールをモダン化し、TypeScript 7サポートを追加したメンテナンス・フィーチャーリリース。RTK QueryのHookオプション型のエクスポートも改善。

### ② 具体的な技術詳細

**ビルドツールの移行:**
- ビルドシステム: `tsup` → `TSDown`
- パッケージマネージャー: Yarn → PNPM
- Linter: ESLint → Oxlint

パッケージのレイアウト・エクスポート定義・公開APIは変更なし。

**TypeScript 7対応:**

RTK QueryのHookオプション型が直接エクスポートされるように:

```typescript
// 以前: Parametersを使って型を抽出する必要があった
type UseQueryOptions = Parameters<typeof useGetPostQuery>[1]

// 2.13以降: 直接インポート可能
import type { UseQueryOptions } from '@reduxjs/toolkit/query/react'
```

**バグ修正:**
- `fetchBaseQuery`の絶対URL処理の修正
- `createAsyncThunk`のabort処理修正
- `createEntityAdapter`の`setAll`における重複IDの処理修正
- ソート済みアダプターの`updateMany`の修正

**ドキュメント統合:**
- ReduxコアのドキュメントサイトにRTK・React Redux・Reselectのドキュメントを統合
- 旧スタンドアロンサイトはリダイレクト

### ③ なぜ効果的か

- ユーザー向けAPIの変更なしにモダンなツールチェーンへの移行を実現
- TypeScript 7をCI対象に追加することで将来の互換性を確保
- Hookオプション型の直接エクスポートで型安全なカスタマイズが容易に

## 6. Paper Shaders がオープンソース化

**記事:** [Paper Shaders - Open Source WebGL2 Shader Library](https://www.mintlify.com/paper-design/shaders/introduction)
**ライセンス:** Apache 2.0

### ① 目的・問題意識

WebGLシェーダーは高品質なビジュアルエフェクト（グラデーション、ノイズ、テクスチャアニメーション等）を提供するが、実装には専門知識が必要でした。Paper Shadersは28種類の高性能WebGL2シェーダーをReactおよびVanilla JSから簡単に利用できるライブラリとしてApache 2.0でオープンソース化。

### ② 具体的な技術詳細

**パッケージ構成:**
```bash
# Vanilla JS版
npm install @paper-design/shaders

# React版
npm install @paper-design/shaders-react
```

**特徴:**
- Three.jsやPIXI等の依存なし。純粋なWebGL2のみ
- 各シェーダーは独立したフラグメントシェーダー文字列として実装
- React 18・19対応

**React での基本使用例:**

```tsx
import { GalaxySpiral } from '@paper-design/shaders-react'

export function Hero() {
  return (
    <GalaxySpiral
      style={{ width: '100%', height: '400px' }}
      speed={0.5}
      colorA="#667eea"
      colorB="#764ba2"
    />
  )
}
```

**シェーダーカテゴリ（全28種）:**
- テクスチャ系（Paper Texture, Cardboard, など）
- アニメーション系（Galaxy Spiral, Waves, など）
- 抽象系（Abstract patterns）

**注意事項:**
- 現在0.0.xバージョニング（破壊的変更あり）
- バージョンのピン留め推奨: `"@paper-design/shaders-react": "0.0.72"`

### ③ なぜ効果的か

- Three.js等の重量級ライブラリ不要で高品質なWebGLエフェクトを利用可能
- Apache 2.0ライセンスで商用プロジェクトに自由に使用可能
- ReactコンポーネントAPIで既存のReactアプリに即座に統合可能

## 7. React CompilerとContextセレクターの関係

**記事:** React Compilerはcontext selectorsを不要にできるか？（複数ブログ・議論）

### ① 目的・問題意識

Reactのコンテキスト（Context）を使う際、プロバイダーの値参照が変わると全コンシューマーが再レンダリングされる。従来、これを防ぐために`use-context-selector`等のサードパーティライブラリを使うか、コンテキストを分割する必要があった。React Compilerの登場でこの問題が解決されるか探っている。

### ② 具体的な技術詳細

**問題のケース:**

```tsx
const ThemeContext = createContext({ theme: 'light', fontSize: 14 })

// ThemeContextのthemeだけ使うコンポーネント
// fontSizeが変わっても再レンダリングされてしまう（問題）
function ThemedButton() {
  const { theme } = useContext(ThemeContext)
  return <button className={theme}>Click</button>
}
```

**現在の回避策:**

```tsx
// 1. コンテキストを分割
const ThemeValueContext = createContext('light')
const FontSizeContext = createContext(14)

// 2. use-context-selectorライブラリを使用
import { useContextSelector } from 'use-context-selector'

function ThemedButton() {
  const theme = useContextSelector(ThemeContext, ctx => ctx.theme)
  return <button className={theme}>Click</button>
}
```

**React Compilerの限界:**

React Compiler（v1.0、2025年10月リリース）は自動メモ化でコンポーネントと値を最適化するが、**コンテキストの基本ルールは変わらない**:
- プロバイダーの値参照が変わると全コンシューマーが再レンダリング
- Compilerはこのコンテキストの伝播メカニズム自体を変えない

### ③ なぜ効果的か（現状の結論）

- React Compilerは多くの手動メモ化を不要にするが、コンテキストのパフォーマンス問題は依然として個別対応が必要
- コンテキストの分割 + Compilerの組み合わせが現在のベストプラクティス
- ネイティブのContext Selectors APIはReact 18時代に実験的に検討されたが、まだ安定版には含まれていない
