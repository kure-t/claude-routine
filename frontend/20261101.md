## 1. TanStack Redact — ブラウザ向け軽量 React 互換ランタイム

**出典:** https://tanstack.com/redact/latest / https://github.com/TanStack/redact / https://tanstack.com/blog/introducing-tanstack-redact

### ① 目的・問題意識

React + ReactDOM の本番バンドルサイズは大きく（gzip 約 69KB）、多くのアプリでランタイム自体が転送量の大きな割合を占める。TanStack Redact は React API と 100% 互換を保ちつつ、同期レンダリングに特化することでバンドルを約 66〜70% 削減する代替ランタイムとして登場した。既存コンポーネントのコードを変更せず、設定ファイルの変更だけで差し替えられる点が最大の特徴。

### ② 具体的なコードと技術詳細

**インストール**

```bash
pnpm add @tanstack/redact
```

**Vite での設定（`vite.config.js`）**

```js
import react from '@vitejs/plugin-react'
import { redact } from '@tanstack/redact/vite'

export default {
  plugins: [
    react(),
    redact(), // React/ReactDOM のインポートを Redact 実装にリダイレクト
  ],
}
```

アプリ側のソースコードは `import React from 'react'` や `import { useState } from 'react'` のままで変更不要。プラグインがビルド時にインポートを差し替える。

**TanStack Start での設定**

```js
import { defineConfig } from '@tanstack/start/config'
import react from '@vitejs/plugin-react'
import { redact } from '@tanstack/redact/vite'

export default defineConfig({
  vite: {
    plugins: [
      react(),
      redact(),
    ],
    ssr: {
      noExternal: true, // SSR 依存もリダイレクト対象に含める
    },
  },
})
```

**Vinext（Cloudflare の Next.js 互換フレームワーク）での設定**

```js
import { vinext } from 'vinext'
import { redact } from '@tanstack/redact/vinext'

export default {
  plugins: [
    vinext(),
    redact(), // Vinext 専用アダプタ
  ],
}
```

**オプション設定**

```js
redact({
  preset: 'nano',         // 'full'（デフォルト）or 'nano'（最小限の機能セット）
  features: {
    transitions: false,   // 個別の機能を無効化してさらに削減
    formActions: false,
  },
})
```

**バンドルサイズ比較（React 19.3.0 対比、gzip）**

| ランタイム | サイズ | 削減率 |
|---|---|---|
| React 19.3.0 | 69,162 bytes | — |
| Redact（Vite デフォルト） | 23,311 bytes | 約 66% 削減 |
| Redact（nano プリセット） | さらに小さい | — |

Vite アプリでの実測では約 70.5% の削減。TanStack Start では約 43% の削減。

**互換性**

サポートされる API:
- JSX、関数コンポーネント、クラスコンポーネント
- `useState`, `useEffect`, `useContext`, `useRef`, `useMemo`, `useCallback`
- `memo`, `lazy`, `Suspense`, `createContext`, `forwardRef`
- `createPortal`、エラーバウンダリ
- ストリーミング SSR、ハイドレーション
- `useTransition`、フォームアクション（ただし制限あり）

**制限事項（React との相違点）:**
- 並行レンダリング（Concurrent Mode）なし → 重い同期レンダリングが UI をブロックする可能性
- `useDeferredValue` の挙動が異なる
- `useOptimistic` の一部動作が異なる
- React DevTools との完全な互換性なし

### ③ なぜ効果的か

Preact（別の軽量 React 互換）より Redact が優れる点は、React 19 の比較的新しい API（Transitions、Form Actions）を保持していること。Redact の思想は「コードを変えず、ランタイムを変える」ことで、段階的な採用を可能にする。バンドルサイズ削減がそのままTTI（Time to Interactive）改善につながるモバイルや低速回線でのユーザー体験向上に直結する。

> バージョン 0.2.0 は 2026年10月26日にリリース。Next.js 15.5/16.0〜16.4、Vinext 1.3 対応も追加済み。

## 2. Design Systems Should Be Fast by Default（Den Odell）

**出典:** https://denodell.com/blog/design-systems-should-be-fast-by-default  
**リポジトリ:** https://github.com/denodell/design-system-performance-tests

### ① 目的・問題意識

React 向けデザインシステム（UI コンポーネントライブラリ）は機能豊富である一方、パフォーマンスが軽視されがちだという問題提起。Den Odell は「デザインシステムはデフォルトで速いべきだ」という観点から、主要 10 ライブラリを同一条件で計測・比較した。

### ② 具体的な技術詳細

**テスト内容:**
1. 249カ国のセレクトボックスを開く（ドロップダウン表示速度）
2. 100個のチェックボックスを一括チェックする（状態更新の速度）

**テスト環境:** Chrome、CPU 4倍スロットリング（低スペック端末のシミュレーション）

**主要結果（ドロップダウン表示速度）:**

| ライブラリ | 表示時間 | 評価 |
|---|---|---|
| Mantine | 84ms | ✅ 100ms 予算内 |
| Ant Design | 134ms | ✅ 100ms 予算内 |
| MUI (Material UI) | 200ms+ | ❌ 予算オーバー |
| React Spectrum | 200ms+ | ❌ 予算オーバー |

**React Spectrum が遅い原因の詳細:**

React Spectrum（Adobe）の内部実装である React Aria が、各オプションを 1 つずつ測定してレイアウトを強制するという問題が判明した。これは「Forced Layout / Layout Thrashing」と呼ばれるアンチパターン。

```
// 問題のあるパターン（概念コード）
for (const option of options) {
  option.offsetHeight // → 都度 DOM レイアウトを強制
  // 処理...
}

// 改善パターン（バッチ読み取り）
const heights = options.map(o => o.offsetHeight) // 一括読み取り
// その後に書き込み処理
```

Den が GitHub にバグレポートを提出し、修正 PR がすでにレビュー中とのこと。

**Ant Design が速い理由:**

Ant Design は仮想スクロール（Virtualization）を採用しており、ビューポートに収まる分だけオプションを DOM に描画し、スクロールに応じて追加レンダリングする。さらにアクセシビリティ（スクリーンリーダー対応）も維持している。

**チェックボックスのパフォーマンス:**

100チェックボックスの一括操作は、テスト対象のすべてのライブラリで大きな遅延は見られなかった。

### ③ なぜ効果的か

デザインシステムの選定においてパフォーマンスを定量的な指標（Google の Core Web Vitals で推奨される 100ms 以内のレスポンス）で評価することで、機能面だけでは見えない差異を可視化できる。特に国際化対応（大量オプションの選択肢）を持つ業務系アプリでは、ライブラリ選定がそのまま UX に直結する。

## 3. React.lazy と Suspense の隠れた 300ms 遅延

**出典:**
- https://github.com/react/react/issues/36569
- https://tabwidgets.com/blog/react-lazy-suspense-delay
- https://github.com/cedarjs/cedar/issues/2611

### ① 目的・問題意識

`React.lazy()` でコード分割したコンポーネントを事前ロード（プリロード）した場合、チャンクの読み込みが既に完了しているにもかかわらず、初回レンダリング時に約 300ms の表示遅延が発生するという挙動の報告。ルーターでのルート遷移や初期描画の体験を損なう。

### ② 具体的なコードと技術詳細

**通常の React.lazy 使用例:**

```jsx
import { lazy, Suspense } from 'react'

const HeavyComponent = lazy(() => import('./HeavyComponent'))

function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <HeavyComponent />
    </Suspense>
  )
}
```

**問題の発生パターン（プリロードしても遅延する）:**

```jsx
// チャンクを事前にロード（たとえばホバー時やルート切替前）
const componentPromise = import('./HeavyComponent')

const HeavyComponent = lazy(() => componentPromise)

// ← この時点でチャンクは読み込み済みのはずだが…
// 実際にレンダリングすると ~300ms の遅延が発生する
```

**なぜ 300ms か:**

React の内部定数 `FALLBACK_THROTTLE_MS = 300` が原因。Suspense は「フォールバックを表示してから次にコンテンツを表示できるまでの最短時間」として 300ms のスロットリングをかけている。これは短命なローディング表示（チラつき）を防ぐためのヒューリスティックだが、プリロード済みでも適用されてしまう。

**React の内部挙動（擬似コード）:**

```
// React が lazy コンポーネントを最初にレンダリングするとき
// 1. import() を呼び出す（初回のみ）
// 2. Promise が返ってくる
// 3. → 既に resolved でも、React はこれを「サスペンド」として扱う
// 4. Suspense のフォールバックを表示
// 5. 300ms 後にコンテンツを表示
```

**GitHub Issue #36569 の報告内容:**

```jsx
// 問題の再現例（React 19.2.6）
const preloaded = import('./SomeComponent') // 事前ロード

const LazyComponent = React.lazy(() => preloaded) // 同じPromiseを渡す

// Suspense にフォールバックなしで囲んだ場合
// → 約 300ms 間、コンテンツが空白になる
function Page() {
  return (
    <Suspense fallback={null}>
      <LazyComponent /> {/* 約 300ms 空白になる */}
    </Suspense>
  )
}
```

**ワークアラウンド 1: 事前 await 後にレンダリング（Cedar プロジェクトの提案）**

```js
// root.render() 前にチャンクを待つ
const timeout = (ms) => new Promise((_, reject) => 
  setTimeout(() => reject(new Error('timeout')), ms)
)

try {
  await Promise.race([import('./App'), timeout(500)])
} catch (e) {
  // タイムアウトは無視して続行
}

root.render(<App />)
```

**ワークアラウンド 2: 同期フォールバックラッパー**

```jsx
// チャンクが既にロード済みの場合は同期的にレンダリング
function SyncLazy({ loader, fallback, children, ...props }) {
  const [Component, setComponent] = useState(null)
  
  useEffect(() => {
    loader().then(mod => setComponent(() => mod.default))
  }, [loader])
  
  if (!Component) return fallback
  return <Component {...props} />
}
```

### ③ なぜ効果的か

この問題を把握することで、ルーターレベルのプリロード戦略（リンクホバー時に `import()` を実行するなど）が期待通りに機能しない理由を説明できる。`React.lazy` の仕様上の制約として認識し、初期描画の遅延を排除するには上記ワークアラウンドや、`React.lazy` を使わない動的インポート管理が必要になる。React チームへのバグレポート（#36569）も上がっており、将来のバージョンでの修正が期待される。
