## 1. Reactの13歳の誕生日 — React Foundation の誕生

### ① 目的・問題意識

React は 2013年5月29日、Jordan Walke と Pete Hunt によって JSConf US（ポートランド）でオープンソース公開された。13年を経てエコシステムが成熟するとともに、Meta 単独のプロジェクトとしてのガバナンスリスクが課題となっていた。特定企業への依存を排し、長期的な持続可能性と中立的なオープンガバナンスを実現するために React Foundation が設立された。

### ② 技術詳細

**React Foundation 設立（2026年2月24日）**

- Linux Foundation の傘下に **React Foundation** を設立
- Meta が React プロジェクト（React / React Native / 周辺ツール）を Foundation へ移管
- 創設プラチナメンバー: Amazon、Callstack、Expo、Huawei、Meta、Microsoft、Software Mansion、Vercel
- 初代エグゼクティブディレクター: Seth Webster
- 技術ガバナンスはボードから独立し、React コントリビューターが引き続き決定権を持つ

**直近の React リリース状況（2026年5月時点）**

| バージョン | リリース日 | 主な内容 |
|---|---|---|
| React 19.0 | 2024年末 | Compiler 正式対応、Server Components、Actions |
| React 19.2 | 2025年10月 | `<Activity>`、`useEffectEvent`、`cacheSignal`、Chrome DevTools連携 |
| React 19.2.6 | 2026年5月6日 | バグ修正・安定化 |

**React Compiler 1.0（2025年10月）**

React Compiler は自動メモ化（automatic memoization）を行うオプティマイジングコンパイラ。`useMemo` / `useCallback` を手動で書かなくても、コンパイル時に最適化が行われる。

```bash
npm install -D babel-plugin-react-compiler
```

```json
// babel.config.json
{
  "plugins": ["babel-plugin-react-compiler"]
}
```

### ③ なぜ効果的か

Foundation 設立により OSS プロジェクトとしての中立性・継続性が担保され、企業ユーザーが安心して採用できるエコシステムが整う。技術的方針は従来通りコアチームが担うため、開発速度に影響しない設計になっている。

## 2. Picture-in-Picture for React Components — フローティングウィンドウにReactコンポーネントを表示

> 参照記事: "How I implemented Picture-in-Picture in React (with full code + tips)"
> URL: https://dev.to/keni_97e44d198c12a5/how-i-implemented-picture-in-picture-in-react-with-full-code-tips-2aj3

### ① 目的・問題意識

従来の Picture-in-Picture API はビデオ要素専用だった。しかし Chrome 116 以降で追加された **Document Picture-in-Picture API** を使うと、任意の HTML / React コンポーネントを「常に最前面に表示されるフローティングウィンドウ」に描画できる。タイマー、チャットウィジェット、音楽プレーヤーなど、ユーザーが別タブに移っても操作し続けたい UI に有用。

### ② 技術詳細

**ブラウザサポート**
- Chrome 116+ / Edge（Chromium）: サポート
- Firefox / Safari: 未サポート（2026年5月時点）

**TypeScript 型拡張（グローバル型定義）**

```typescript
declare global {
  interface Window {
    documentPictureInPicture: {
      requestWindow(options?: {
        width?: number;
        height?: number;
        disallowReturnToOpener?: boolean;
        preferInitialWindowPlacement?: boolean;
      }): Promise<Window>;
    };
  }
}
```

**CSS を PiP ウィンドウにコピーするユーティリティ**

```typescript
function copyStyles(sourceDoc: Document, targetDoc: Document): void {
  // インライン <style> タグをコピー
  Array.from(sourceDoc.styleSheets).forEach((sheet) => {
    try {
      const cssRules = Array.from(sheet.cssRules)
        .map((rule) => rule.cssText)
        .join('');
      const style = targetDoc.createElement('style');
      style.textContent = cssRules;
      targetDoc.head.appendChild(style);
    } catch {
      // クロスオリジンのスタイルシートは <link> でコピー
      if (sheet.href) {
        const link = targetDoc.createElement('link');
        link.rel = 'stylesheet';
        link.href = sheet.href;
        targetDoc.head.appendChild(link);
      }
    }
  });
}
```

**カスタムフック: `useDocumentPiP`**

```typescript
import { useRef, useState, useCallback } from 'react';
import { createRoot, Root } from 'react-dom/client';

interface UseDocumentPiPReturn {
  isSupported: boolean;
  isOpen: boolean;
  openPiP: (
    content: React.ReactNode,
    options?: { width?: number; height?: number }
  ) => Promise<void>;
  closePiP: () => void;
}

export function useDocumentPiP(): UseDocumentPiPReturn {
  const pipWindowRef = useRef<Window | null>(null);
  const rootRef = useRef<Root | null>(null);
  const [isOpen, setIsOpen] = useState(false);

  const isSupported = 'documentPictureInPicture' in window;

  const openPiP = useCallback(
    async (
      content: React.ReactNode,
      options: { width?: number; height?: number } = {}
    ) => {
      if (!isSupported) return;

      const { width = 360, height = 220 } = options;

      // 既存の PiP ウィンドウを閉じる
      pipWindowRef.current?.close();

      const pipWindow = await window.documentPictureInPicture.requestWindow({
        width,
        height,
      });

      pipWindowRef.current = pipWindow;

      // 親ウィンドウのスタイルをコピー
      copyStyles(document, pipWindow.document);

      // React ルートをマウント
      const container = pipWindow.document.createElement('div');
      pipWindow.document.body.appendChild(container);
      rootRef.current = createRoot(container);
      rootRef.current.render(content);

      setIsOpen(true);

      // PiP が閉じられたときの後処理
      pipWindow.addEventListener('pagehide', () => {
        rootRef.current?.unmount();
        rootRef.current = null;
        pipWindowRef.current = null;
        setIsOpen(false);
      });
    },
    [isSupported]
  );

  const closePiP = useCallback(() => {
    pipWindowRef.current?.close();
  }, []);

  return { isSupported, isOpen, openPiP, closePiP };
}
```

**利用例**

```tsx
import { useDocumentPiP } from './useDocumentPiP';

function MusicPlayer() {
  const { isSupported, isOpen, openPiP, closePiP } = useDocumentPiP();

  return (
    <div>
      <audio controls src="/track.mp3" />
      {isSupported && (
        <button
          onClick={() =>
            isOpen
              ? closePiP()
              : openPiP(<MiniPlayer />, { width: 320, height: 180 })
          }
        >
          {isOpen ? 'Close PiP' : 'Open PiP'}
        </button>
      )}
    </div>
  );
}
```

**`createPortal` を使う別アプローチ**

```tsx
import { createPortal } from 'react-dom';

// pipWindow が取得できていれば portal でレンダリングも可能
{pipWindow && createPortal(<MiniPlayer />, pipWindow.document.body)}
```

### ③ なぜ効果的か

- **`createRoot` + `copyStyles`** の組み合わせにより、既存の React コンポーネントをほぼそのまま PiP ウィンドウに移植できる
- ユーザーが別タブ・別ウィンドウに移動しても、フローティングウィンドウは常に前面に表示される
- `pagehide` イベントで確実にアンマウント処理することでメモリリークを防げる

## 3. Building Predictive Text Inputs — AI ゴーストテキスト補完

> 参照ライブラリ: `predictive-textarea` (JensAstrup)
> URL: https://github.com/JensAstrup/predictive-textarea
> 参照記事: https://dev.to/jensastrup/predictive-textarea-with-openai-integration-3bmk

### ① 目的・問題意識

Gmail Smart Compose や GitHub Copilot のように「入力中に薄いゴーストテキストで次の単語を提案し、Tab キーで確定する」体験を、React アプリで手軽に実現したい。AI API（OpenAI / Claude など）と連携し、コンテキストを理解した予測補完をリアルタイムに提供する。

### ② 技術詳細

**インストール**

```bash
npm install predictive-textarea
```

**最小構成**

```tsx
import { PredictiveTextarea } from 'predictive-textarea';

export default function App() {
  return (
    <PredictiveTextarea
      placeholder="Start typing..."
    />
  );
}
```

**OpenAI API を使ったカスタム補完関数**

```tsx
import { PredictiveTextarea } from 'predictive-textarea';
import OpenAI from 'openai';

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

async function fetchCompletion(text: string): Promise<string> {
  const response = await openai.completions.create({
    model: 'gpt-4o-mini',
    prompt: text,
    max_tokens: 20,
    temperature: 0.2,
  });
  return response.choices[0]?.text ?? '';
}

export default function Editor() {
  return (
    <PredictiveTextarea
      getCompletion={fetchCompletion}
      debounceMs={300}      // ユーザーが入力を止めてから300ms後にリクエスト
      cacheSize={100}       // Trieベースのキャッシュに最大100エントリ保持
      placeholder="Write something..."
    />
  );
}
```

**デバウンス設定のトレードオフ**

| `debounceMs` | メリット | デメリット |
|---|---|---|
| 100ms | 応答が速い | API コール数が多い |
| 300ms（デフォルト） | バランス良好 | — |
| 500ms | API コール削減 | やや遅く感じる |

**Trie ベースキャッシュの仕組み**

同じプレフィックスに対するリクエストは重複しないよう Trie 構造でキャッシュ。`cacheSize` を超えた場合は LRU で古いエントリを削除する。

**react-ghost-text（よりシンプルな実装）**

```tsx
import { AutocompleteTextbox } from 'react-ghost-text';

async function getSuggestion(text: string): Promise<string> {
  const res = await fetch('/api/suggest', {
    method: 'POST',
    body: JSON.stringify({ prompt: text }),
    headers: { 'Content-Type': 'application/json' },
  });
  const data = await res.json();
  return data.suggestion;
}

export default function GhostTextDemo() {
  return (
    <AutocompleteTextbox
      getSuggestion={getSuggestion}
      debounce={1000}
      initialValue=""
      onContentChange={(content) => console.log(content)}
    />
  );
}
```

**UX: 補完の受け入れ操作**
- `Tab` キー: 補完テキスト全体を挿入
- `Escape` キー: 補完を却下
- 入力継続: 補完を無視して上書き

### ③ なぜ効果的か

- **デバウンス + Trie キャッシュ** により API コール数を最小化しつつ補完速度を維持
- ゴーストテキスト（薄いグレーで表示）は既存の入力フローを阻害しない、インラインなUX
- `getCompletion` を差し替えるだけで任意の LLM（Claude / Gemini / ローカルモデル）に対応できる柔軟性

## 4. TanStack Start の Deferred Hydration — 非クリティカル領域のハイドレーションを遅延させる

> 公式ドキュメント: https://tanstack.com/start/latest/docs/framework/react/guide/deferred-hydration
> YouTube解説: "Is TanStack Start's Deferred Hydration Revolutionary?" https://www.youtube.com/watch?v=_PB9rHndhU8
> 発表ツイート: https://x.com/tan_stack/status/2056778209690026436

### ① 目的・問題意識

SSR（サーバーサイドレンダリング）によってページの HTML は即座に配信され、表示・SEO に有利だが、クライアント側の **ハイドレーション**（JavaScript のロード・実行・イベントハンドラのアタッチ）はページ全体に対して行われるため、スクロールしても見えないフッターや商品レビューなど「今すぐインタラクティブでなくてよい」領域にもリソースを使ってしまう。これが FID（First Input Delay）や TTI（Time to Interactive）を悪化させる原因となる。

TanStack Start の **Deferred Hydration** は、ハイドレーションのタイミングを境界単位でコントロールし、ビューポート外・アイドル時・ユーザー操作時まで遅延させることができる。

### ② 技術詳細

**インポート**

```tsx
import { Hydrate } from '@tanstack/react-start';
import { idle, interaction, visible } from '@tanstack/react-start/hydration';
```

**基本的な使い方**

```tsx
// ビューポートに入ったときにハイドレーション
export function ReviewsBoundary() {
  return (
    <Hydrate when={visible({ rootMargin: '200px' })}>
      <Reviews />
    </Hydrate>
  );
}
```

**`when` 戦略の種類**

| 戦略 | 説明 | ユースケース |
|---|---|---|
| `visible({ rootMargin })` | 境界がビューポートに近づいたときにハイドレーション | フォールド下のコンテンツ |
| `idle()` | ブラウザのアイドル時間（requestIdleCallback）に実行 | バックグラウンド処理 |
| `interaction()` | ユーザーが境界内をクリック・ホバーしたとき | ツールチップ、ドロップダウン |

**`prefetch` でチャンクを事前ロード**

```tsx
// ビューポートに近づいたらハイドレーション、
// その前のアイドル時間にJSチャンクをプリフェッチ
export function ReviewsBoundary() {
  return (
    <Hydrate
      when={visible({ rootMargin: '200px' })}
      prefetch={idle()}
    >
      <Reviews />
    </Hydrate>
  );
}
```

**組み合わせ例（複数の境界）**

```tsx
export function ProductPage() {
  return (
    <>
      {/* 即時ハイドレーション（クリティカルな領域） */}
      <ProductHero />
      <AddToCartButton />

      {/* ビューポートに入ったらハイドレーション */}
      <Hydrate when={visible({ rootMargin: '200px' })} prefetch={idle()}>
        <ProductReviews />
      </Hydrate>

      {/* ユーザーがインタラクションしたときにハイドレーション */}
      <Hydrate when={interaction()} prefetch={visible({ rootMargin: '1200px' })}>
        <RelatedProducts />
      </Hydrate>

      {/* ブラウザのアイドル時間にハイドレーション */}
      <Hydrate when={idle()}>
        <RecommendationsFooter />
      </Hydrate>
    </>
  );
}
```

**デフォルト動作（コンパイラによるコード分割）**

コンパイラは `<Hydrate>` の子コンポーネントを自動的に別の JavaScript チャンクに分割するため、境界がハイドレーションされるまで そのコードのダウンロードも行われない。

**ネスト構造のルール**

```
親境界が先にハイドレーション → 子境界がハイドレーション可能に
（子境界は親がハイドレーションされるまでハイドレーション不可）
```

**適切なユースケース**

- フォールド下のレビュー、コメント
- 商品詳細の展開セクション
- 関連コンテンツ、レコメンデーション
- 長いマーケティングセクション

**不適切なケース**

- ナビゲーションメニュー（即時インタラクションが必要）
- フォーム（ユーザーがすぐに入力する可能性）
- アクセシビリティ重要コンポーネント

### ③ なぜ効果的か

- **HTML は遅延なく配信・表示・インデックス**されるため SEO への影響ゼロ
- JavaScript の **ロード自体を遅延**（コード分割）するため、初回バンドルサイズを削減
- `prefetch={idle()}` との組み合わせにより、「見えた瞬間には既にチャンクがキャッシュ済み」という体験を実現
- 従来の React の `lazy()` + `Suspense` はローディング状態を表示するが、Deferred Hydration はコンテンツを表示したまま非インタラクティブ状態を維持できる点が異なる
