## 1. The React Compiler at Eighteen Months: The Arc, the Debates, and What's Next

**URL**: https://saschb2b.com/blog/react-compiler-year-in-review

### ① 目的・問題意識

React CompilerはReact Forgetとして内部で開発され、2024年末にReact 19とともに公開ベータに入り、2025年10月にv1.0に到達した。  
それまで開発者は `useMemo`・`useCallback`・`React.memo` を手動で書き続けるという作業を強いられており、それが誤用・過剰使用・バグの温床となっていた。Compilerはビルド時に自動メモ化を行うことでこれを解消する。

### ② 具体的な技術詳細

コンパイラはコンポーネントのコードを静的解析し、フック呼び出し単位ではなく**リアクティブスコープ単位**でキャッシュ境界を挿入する。手動で書くよりも細粒度のメモ化が実現される。

**Before（手動メモ化）**:
```jsx
const MyComponent = React.memo(({ items, filter }) => {
  const filtered = useMemo(
    () => items.filter(item => item.type === filter),
    [items, filter]
  );
  const handleClick = useCallback((id) => {
    onSelect(id);
  }, [onSelect]);

  return <List items={filtered} onItemClick={handleClick} />;
});
```

**After（コンパイラが自動生成するイメージ）**:
```jsx
// 開発者が書くコード（手動メモ化不要）
const MyComponent = ({ items, filter }) => {
  const filtered = items.filter(item => item.type === filter);
  const handleClick = (id) => { onSelect(id); };
  return <List items={filtered} onItemClick={handleClick} />;
};
// コンパイラがリアクティブスコープを解析して自動でキャッシュ境界を挿入
```

**採用状況**:
- Next.js、Expo、TanStack Start、Viteベースのフレームワークがデフォルトで有効化
- Sanity Studioでは1,411コンポーネント中1,231でコンパイル成功、全体のレンダリング時間・レイテンシを20〜30%削減

**コンパイラが対処できないパターン（4つの主要ケース）**:
1. **変異（Mutation）**: propsやstateを直接変更するパターン
2. **非純粋なコンポーネント**: レンダリングごとに異なる副作用を持つもの
3. **古いライブラリの互換性**: React Compilerと互換性のないライブラリ
4. **複雑な条件分岐**: コンパイラが静的解析で追跡できないケース

### ③ なぜ効果的か

- 手動のメモ化ミス（依存配列の漏れなど）がなくなる
- コードレビューで「なぜ再レンダリングしているか」系のバグが激減
- 新しいメモ化が蓄積されなくなりコードベースが整理される

## 2. GTKX: The React Framework for Linux

**URL**: https://gtkx.dev / https://github.com/gtkx-org/gtkx

### ① 目的・問題意識

LinuxのGTK4デスクトップアプリケーションをReact + TypeScriptで書けるようにするフレームワーク。  
従来のElectronはWebViewベースでオーバーヘッドが大きく、ネイティブのGTKウィジェットを使えなかった。GKTXはReactのReconcilerを使ってGTK4ウィジェットを直接JSXで操作できる。

### ② 具体的なコード・技術詳細

**プロジェクト作成**:
```bash
npm create gtkx
cd my-app
npm run dev
```

**基本コード（カウンターアプリ）**:
```jsx
import * as Gtk from "@gtkx/gi/gtk";
import {
  GtkApplicationWindow,
  GtkBox,
  GtkButton,
  GtkLabel
} from "@gtkx/jsx/gtk";
import { createRoot, quit } from "@gtkx/react";
import { useState } from "react";

const Counter = () => {
  const [count, setCount] = useState(0);
  return (
    <GtkApplicationWindow
      title="Hello GTKX"
      defaultWidth={400}
      defaultHeight={300}
      onCloseRequest={quit}
    >
      <GtkBox
        orientation={Gtk.Orientation.VERTICAL}
        spacing={20}
        marginTop={40}
        marginBottom={40}
        marginStart={40}
        marginEnd={40}
        valign={Gtk.Align.CENTER}
        halign={Gtk.Align.CENTER}
      >
        <GtkLabel cssClasses={["title-1"]}>Welcome to GTKX!</GtkLabel>
        <GtkLabel cssClasses={["title-2"]}>{`Count: ${count}`}</GtkLabel>
        <GtkButton
          label="Increment"
          onClicked={() => setCount((c) => c + 1)}
          cssClasses={["suggested-action", "pill"]}
        />
      </GtkBox>
    </GtkApplicationWindow>
  );
};

createRoot(<Counter />);
```

**技術的な仕組み**:
- RustコアがlibffiでシステムのGTK4ライブラリを直接呼び出す
- GObject-IntrospecionデータからTypeScriptバインディングを自動生成（型安全）
- Node.js 24+ で動作し、npmパッケージがそのまま使える
- CSS-in-JS、react-i18next、React Springアニメーション対応
- Fast Refresh（ホットリロード）対応の開発サーバー内蔵

**必要環境**:
- Linux（GTK4 4.20+、Adwaita 1.8+）
- Node.js 24+

### ③ なぜ効果的か

Web開発者のReactスキルをそのままLinuxデスクトップ開発に転用できる。ElectronのようなWebView経由ではなく、本物のGTKウィジェットを使うためネイティブアプリとして動作する。react-native-gtk4（先代プロジェクト）は非推奨となりGKTXへの移行が推奨されている。

## 3. TanStack Form v2 Alpha: Validator Pipeline & Schema Forms

**URL**: https://tanstack.com/blog/announcing-tanstack-form-v2-alpha

### ① 目的・問題意識

TanStack Form v1ではバリデーターがイベント（`onChange`/`onBlur`）単位のオブジェクトで管理されていた。これは単純なケースでは機能したが、1つのバリデーターを複数トリガーで動かしたい、または同一トリガーで複数バリデーターを走らせたい場合に使いにくかった。

### ② 具体的なコード・技術詳細

**v1（イベントキー方式）**:
```ts
validators: {
  onChange: mySchema,
  onBlur: otherValidator,
}
```

**v2（パイプライン方式）**:
```ts
validators: [
  {
    run: mySchema,
    triggers: ['change', 'blur'],
  },
  {
    run: otherValidator,
    triggers: ['submit'],
  }
]
```

**Standard Schema（Zodとの統合例）**:
```ts
import { z } from 'zod';

const userSchema = z.object({
  age: z.number().gte(13, 'You must be 13 to make an account'),
});

const form = useForm({
  validators: [
    { run: userSchema, triggers: ['change', 'blur'] }
  ],
});
```

**SSR（TanStack Start）**:
```ts
// サーバー・クライアント共通のformOptions
const opts = formOptions({
  defaultValues: { firstName: '', age: 0 }
});
```

**v2の主な変更点**:
- バリデーターパイプラインに移行
- Zodを含むStandard Schema仕様対応
- より安全なフォーム合成（Safer form composition）
- シンプルなSSR
- Reactフォーカスのアルファ（他アダプタは後続）

**アルファ版の既知制限**:
- フォーム状態の永続化機能（セーブ・リストア）は未実装
- `handleSubmit`からの追加データ渡し機能（v1の複数サブミットアクション対応）は未実装

### ③ なぜ効果的か

パイプライン方式にすることで、バリデーションロジックがトリガーに依存せず単体でテスト・再利用しやすくなる。また、Standard Schemaに対応することでZod/Yup/Valibotなどのスキーマ定義を直接使えるため、既存のバリデーション資産をそのまま流用できる。

## 4. React Native 0.87: Strict TypeScript API、Metro更新、Swift Package Manager対応

**URL**: https://reactnative.dev/blog/2026/08/11/react-native-0.87

### ① 目的・問題意識

React Native v1.0に向けた地ならし。長年の型定義とソースコードのズレを解消し、開発ツールの速度とメモリ効率を改善する。またiOSのCocoaPods依存から脱却するための布石としてSwift Package Managerへの対応を実験的に追加。

### ② 具体的な技術詳細

**Strict TypeScript API（デフォルト化）**:
- 型がReact Nativeのソースコードから直接生成されるように変更
- 型とコードの乖離が解消され、カバレッジ・精度が向上
- v0.86以前の型で動いていた一部コードは型エラーが出る場合あり

**Metro 0.84 → 0.87 の変更**:
```
- ソースマップ生成が2倍高速化（React Native DevToolsのロードが速くなる）
- メモリ使用量が半減（ソースマップのストレージ最適化による）
- TypeScriptおよびESM設定ファイル（.tsおよびES Module形式のメトロ設定）が安定サポート
- 廃止: .es6 拡張子サポート、YAML形式の設定ファイル
```

**Swift Package Manager（実験的）**:
- CocoaPodsはデフォルトのままでサポート継続
- オプトインで追加可能な形で実験的サポートを提供

**最低ツールチェーン要件の引き上げ**:
```
Node.js: 22以上
Android Gradle Plugin: 9以上
Kotlin: 2.0以上
```

### ③ なぜ効果的か

型がソースコードから自動生成されることで型の正確性が保証され、IDEの補完品質が向上する。Metro高速化によって開発中のデバッグ体験が改善される。Swift Package Manager対応はCocoaPods代替への移行を段階的に進めるための重要な一歩。

## 6. Preact 11.0.0-rc.0: React 19互換のモダンプリミティブ

**URL**: https://github.com/preactjs/preact/releases/tag/11.0.0-rc.0

### ① 目的・問題意識

React 19で追加された `use()`・`useEffectEvent()`・`createPortal()` のコアへの統合など、モダンなReact APIとの互換性を確保しつつ、バンドルサイズを削減しレンダリング効率を向上させる。

### ② 具体的な技術詳細

**新しいAPI（compat経由）**:
```jsx
// use() フック - PromiseとContextのアンラップ
import { use } from 'preact/compat';
const data = use(somePromise);

// useEffectEvent() - 最新の値をキャプチャするイベントハンドラ
import { useEffectEvent } from 'preact/compat';
const onTickEvent = useEffectEvent(() => {
  sendAnalytics(latestCount);
});

// createPortal() - コアに統合
import { createPortal } from 'preact';
const modal = createPortal(<Modal />, document.body);
```

**パフォーマンス改善**:
- 子要素の移動計算に**最長増加部分列（LIS）アルゴリズム**を採用（最小DOM操作を実現）
- `flushSync` 内のバッチ更新処理を最適化
- `insertBefore` の代わりに `moveBefore` API（利用可能な場合）を優先使用

**その他の変更**:
- レポートするReactバージョンを19.0.0に更新（互換性マーカー）
- モダンなビルドセットアップの導入
- ユーザー提供のstyleオブジェクトの変更（ミューテーション）を防止

### ③ なぜ効果的か

PreactはReactの軽量代替として3KBのランタイムを維持しながら、React 19の最新APIとの互換性を保つことで、バンドルサイズ最適化が重要な環境（エッジ、組み込みUI等）でのReact 19コードの実行を可能にする。LISアルゴリズム採用でリスト再描画のDOMオペレーション数が最小化される。

## 9. Effect v4 RC: TypeScript向け関数型プログラミングフレームワーク

**URL**: https://github.com/Effect-TS/effect

### ① 目的・問題意識

TypeScriptで非同期・並行・リアクティブなプログラムを型安全かつ関数型的に構築するための包括的なフレームワーク。副作用管理・エラー処理・依存性注入を強力な型システムで表現する。

### ② 具体的な技術詳細

**要件**:
```
TypeScript: 5.9以上（TypeScript 7推奨）
tsconfig.json: "strict": true 必須
```

**v4の特徴**:
- Reactバインディングが初めて一級サポート（first-class）に昇格
- `@effect/react` パッケージとして提供
- RC版（リリース候補）として全v4パッケージが `rc` タグでnpmに公開
- SolidJS・Vue向けバインディングも提供

**Reactとの統合イメージ**:
```ts
import { Effect } from 'effect';
import { useEffect } from '@effect/react';

// Effectを直接Reactフックで扱える
const MyComponent = () => {
  const result = useEffect(
    Effect.gen(function* () {
      const data = yield* fetchData();
      return data;
    })
  );
  return <div>{result}</div>;
};
```

### ③ なぜ効果的か

Effect v4でReactバインディングが正式サポートになったことで、EffectのEffect System（エラー処理・依存性注入・並行処理の型安全な管理）をReactコンポーネントで直接利用できるようになった。関数型プログラミングの恩恵（型安全な副作用管理、合成可能な処理）をReactアプリに取り込みたいチームに適している。
