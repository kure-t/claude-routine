## 1. Reverse Engineering ChatGPT Web: How OpenAI Built for a Billion Users

**出典**: [performance.dev/chatgpt](https://performance.dev/chatgpt)

### ① 目的・問題意識

ChatGPT は月間数十億リクエストを処理する世界最大規模のReactアプリの一つ。「なぜChatGPTはあれほど速いのか？」という問いに答えるため、公開バンドルを逆解析しフロントエンドアーキテクチャを徹底解剖した記事。ページを開いて入力できるまでのTTI（Time to Interactive）を最小化することを最優先設計目標としている。

### ② 技術詳細

#### フレームワーク遍歴
- 2024年: **Next.js → Remix** に移行
- Remix v2 が React Router v7 にマージされたタイミングで **React Router v7（framework mode）** に自然移行

#### スタック全体像

| カテゴリ | 採用技術 |
|---|---|
| フレームワーク | React Router v7 (framework mode) |
| スタイリング | Tailwind CSS v4（デザイントークン層の上にコンパイル、ルートごとに分割） |
| UIプリミティブ | Radix UI |
| テキスト入力（コンポーザー） | ProseMirror |
| サーバーデータ取得 | TanStack Query（サーバーシード） |
| Webフォント | なし（ゼロ） |

#### コード分割と起動最適化
```
Boot = 160 content-hashed chunks
       staged around「入力できる瞬間」
```

- バンドルは **160個のコンテンツハッシュ付きチャンク** に分割
- サーバーのブートストラップ設定に以下のようなフラグが存在:
  ```js
  deferStartupImportsUntilComposerTTFI: true
  // コンポーザー（チャット入力欄）がインタラクティブになるまで
  // スタートアップのインポートを遅延させる
  ```
- ページ全体はエッジからSSRされ、**100ms以下でストリーミング開始**

#### フィーチャーフラグ
- ページの読み込み方法を含む全ての意思決定が **556個のサーバー評価フラグ** 背後に存在
- A/Bテストや段階的ロールアウトが全機能に適用されている

#### Tailwind v4 × デザイントークン
```css
/* デザイントークン層: CSS変数として定義 */
:root {
  --token-text-primary: #0d0d0d;
  --token-bg-surface: #ffffff;
  --token-brand-primary: #10a37f;
}

/* Tailwind v4でCSS変数を活用 */
.composer {
  color: var(--token-text-primary);
  background: var(--token-bg-surface);
}
```

Tailwind v4では全デザイントークンがCSS変数として自動公開されるため、`token-*` クラスがデザインシステムのセマンティックレイヤーとして機能する。

### ③ なぜ効果的か

「最もメインストリームなフロントエンドスタック」を採用しながら、全てのデフォルトを疑い計測した結果が高速性の源泉。Webフォントを排除し、チャンクをユーザーが「入力できる瞬間」に合わせてステージングし、556のフラグで全体を制御する設計は、巨大スケールのプロダクトに必要な観測可能性と最適化の両立を実現している。

## 2. Vercel acquires Better Auth to accelerate open source auth

**出典**: [vercel.com/blog/vercel-acquires-better-auth](https://vercel.com/blog/vercel-acquires-better-auth) / [better-auth.com/blog/better-auth-joins-vercel](https://better-auth.com/blog/better-auth-joins-vercel)

### ① 目的・問題意識

AIエージェントが急増する中、「エージェント自身のアイデンティティ管理」という新しい認証課題が浮上。従来の認証ライブラリはユーザー向けに設計されており、エージェントがスコープ付きで取り消し可能なトークンを持つ仕組みがなかった。Vercelは、週470万npm DLを誇るBetter Auth（TypeScript製OSSライブラリ）を買収し、エージェント認証（Agent Auth）の構築を加速させる。

### ② 技術詳細

**Better Authの基本機能:**
```typescript
// Better Auth 基本セットアップ例
import { betterAuth } from 'better-auth';
import { Pool } from 'pg';

export const auth = betterAuth({
  database: new Pool({ connectionString: process.env.DATABASE_URL }),
  emailAndPassword: { enabled: true },
  socialProviders: {
    github: {
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
    },
  },
});
```

**Agent Auth（開発中）:**
```typescript
// エージェント向け: スコープ付き・取り消し可能なアイデンティティ
import { agentAuth } from 'better-auth/agent';

const agentToken = await agentAuth.createToken({
  agentId: 'summarizer-agent-v1',
  scopes: ['read:documents', 'write:summaries'],
  userId: currentUser.id, // ユーザーが単一の制御点
  expiresIn: '1h',
  revocable: true,
});
```

**主要事実:**
- 2024年9月に最初のリリース
- 2025年に$5Mシード調達（Peak XV Partners、Y Combinator、P1 Ventures、Chapter One）
- 2026年7月7日にVercel買収発表
- **MITライセンスは継続**、オープンソースのまま
- 850名以上のコントリビューター
- フレームワーク非依存（Next.js、Remix、SvelteKit など）

### ③ なぜ効果的か

AIエージェントが「ユーザーに代わって」タスクを実行する世界では、エージェントが自身のスコープ付きアイデンティティを持ち、ユーザーがそれを一元的に管理・取り消しできる仕組みが必須。Better AuthはすでにTypeScriptエコシステムで最もシンプルな認証ライブラリとして定評があり、これをVercelのインフラ・デプロイエコシステムと組み合わせることで、Agent Authの業界標準を狙う。

## 3. vinext 1.0 Beta — Next.js on Vite, deploy anywhere

**出典**: [github.com/cloudflare/vinext](https://github.com/cloudflare/vinext) / [blog.cloudflare.com/vinext/](https://blog.cloudflare.com/vinext/)

### ① 目的・問題意識

Next.jsのビルドはTurbopackでも遅く、バンドルサイズが大きい。また、Cloudflare Workers へのデプロイが困難。vinextは「Next.jsのAPIをViteで再実装」することで、既存のNext.jsコードを変更なしにCloudflare Workersへデプロイできるようにし、かつビルド速度・バンドルサイズを大幅改善することを目的とする。CloudflareがAI支援で1週間で開発。

### ② 技術詳細

**インストール・セットアップ:**
```bash
# 新規プロジェクト
pnpm create vinext-app@latest my-app

# 既存Next.jsプロジェクトの移行
npx vinext init

# 手動インストール
npm install vinext
npm install -D vite @vitejs/plugin-react
```

**Cloudflareバインディングへのアクセス（サーバーコンポーネント）:**
```typescript
// Cloudflare D1, KV, R2 などへ直接アクセス
import { env } from "cloudflare:workers";

export default async function Page() {
  // D1データベースへのクエリ
  const result = await env.DB.prepare("SELECT * FROM posts").all();
  // KVストレージへのアクセス
  const value = await env.KV.get("my-key");
  
  return <div>{JSON.stringify(result)}</div>;
}
```

**デプロイ:**
```bash
# Cloudflare Workersへ1コマンドデプロイ
npx @vinext/cloudflare deploy
```

**対応機能（Next.js 16 API 94%をカバー）:**
- App Router + Pages Router
- React Server Components、Server Actions
- ミドルウェア、ルートハンドラー
- ISR（Incremental Static Regeneration）
- 静的エクスポート
- `next/image`、`next/link`、`next/font` など

**ベンチマーク（33ルートのテストアプリ）:**

| 指標 | Next.js 16 (Turbopack) | vinext |
|---|---|---|
| ビルド時間 | 7.38秒 | **1.67秒（4.4×高速）** |
| クライアントバンドル | 168.9 KB (gzip) | **72.9 KB（57%削減）** |
| Next.js 16 API カバレッジ | 100% | **~94%** |

**テスト品質:**
- Vitestテスト: 1,700件以上
- Playwright E2Eテスト: 380件（Next.js本家のテストスイートより移植）

### ③ なぜ効果的か

Vite 8の**Rolldownバンドラー**（Rust製）、**Oxc**（Rust製トランスパイラ）、**Lightning CSS**を組み合わせることで、JavaScriptベースのNext.jsビルドパイプラインを大幅に高速化。CloudflareのViteプラグインとのネイティブ統合により、D1・R2・KV・Durable ObjectsなどCloudflareの全サービスに`cloudflare:workers`インポートで直接アクセスできる。ただし実験的ステータスであり、本番利用は慎重な評価が必要。

## 4. Base UI is Now the Default in shadcn/ui

**出典**: [ui.shadcn.com/docs/changelog/2026-07-base-ui-default](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)

### ① 目的・問題意識

shadcn/uiは2023年のローンチからRadix UIをベースとしてきたが、RadixはWorkOSチームによる小規模なメンテナンス体制。一方、Radixの元開発者たちが設立したMUI社が「Base UI」を開発中であり、専任エンジニアによる活発な開発が続いている。shadcnはBase UIを新デフォルトに切り替えることで、長期的な安定性を確保する。

### ② 技術詳細

**CLIの変化:**
```bash
# 従来（Radix UI ベース）
npx shadcn init

# 新デフォルト（Base UI ベース）
npx shadcn init  # 自動的にBase UIが選択される

# Radixを使い続ける場合
npx shadcn init -b radix
```

**Base UIコンポーネントの例（Dialog）:**
```tsx
import * as Dialog from '@base-ui-components/react/dialog';

export function MyDialog() {
  return (
    <Dialog.Root>
      <Dialog.Trigger>Open Dialog</Dialog.Trigger>
      <Dialog.Portal>
        <Dialog.Backdrop className="fixed inset-0 bg-black/50" />
        <Dialog.Popup className="fixed top-1/2 left-1/2 -translate-x-1/2 -translate-y-1/2 bg-white rounded-lg p-6">
          <Dialog.Title>Title</Dialog.Title>
          <Dialog.Description>Description</Dialog.Description>
          <Dialog.Close>Close</Dialog.Close>
        </Dialog.Popup>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

**重要な互換性ポイント:**
- Radixは**廃止されない**（引き続きサポート継続）
- 新規コンポーネントは両ライブラリ向けにリリース
- Base UIにしか存在しないコンポーネントも一部存在
- shadcn 4.13でCLIが両ライブラリを正式サポート

**Radix → Base UI の主な違い:**

| 観点 | Radix UI | Base UI |
|---|---|---|
| 開発主体 | WorkOS（小規模チーム） | MUI（専任エンジニア） |
| アクセシビリティ | WAI-ARIA準拠 | WAI-ARIA準拠（改良版） |
| スタイリング | スタイルなし（ヘッドレス） | スタイルなし（ヘッドレス） |
| TypeScript | 対応 | より厳密な型定義 |
| 長期安定性 | 不確実 | 高（MUIの主力投資） |

### ③ なぜ効果的か

Radixを作ったチームがBase UIを作っているため、設計哲学は継承しつつ「最初の経験から学んだ改善」が盛り込まれている。MUIという大きな組織のバッキングがあることで、長期的なメンテナンスが保証される。移行コストをゼロに近づけるCLIの `-b radix` オプションで既存ユーザーへの配慮も完璧。

## 5. Takumi 2.0 — JSX/HTMLをブラウザなしで画像に変換

**出典**: [takumi.kane.tw](https://takumi.kane.tw/) / [github.com/kane50613/takumi](https://github.com/kane50613/takumi)

### ① 目的・問題意識

OG画像やソーシャルカードの生成に、従来はheadless Chromiumが必要で300MB以上のRAMとコールドスタートのオーバーヘッドがあった。Vercelの`next/og`（Satoribased）の代替として、**Rustエンジン**でJSX/HTMLを直接画像に変換するライブラリ。ブラウザプロセスをゼロにする。

### ② 技術詳細

**インストール:**
```bash
npm install takumi-js
```

**基本的な使い方（next/ogドロップイン代替）:**
```tsx
// app/og/route.tsx
import { ImageResponse } from 'takumi-js';

export async function GET() {
  return new ImageResponse(
    (
      <div
        style={{
          display: 'flex',
          fontSize: 60,
          color: 'black',
          background: 'white',
          width: '100%',
          height: '100%',
          padding: '50px 200px',
          textAlign: 'center',
          justifyContent: 'center',
          alignItems: 'center',
        }}
      >
        Hello, World!
      </div>
    ),
    {
      width: 1200,
      height: 630,
    }
  );
}
```

**対応出力フォーマット:**
- PNG、JPEG、**WebP**（Satori非対応）
- SVG
- アニメーション（GIF/APNG）

**追加機能（Satoriにはない）:**
- 可変フォント（Variable Fonts）
- RTL（右から左）テキスト
- インラインレイアウト
- WOFF2フォント
- より高いCSS互換性

**ランタイム自動選択:**
```ts
// takumi-jsがランタイムを自動検出
// - Node.js: ネイティブRustバイナリ（最速）
// - Cloudflare Workers / Vercel Edge / Deno: WebAssembly
// - ブラウザ: WebAssembly
import { renderToImage } from 'takumi-js';

const image = await renderToImage(<MyCard />, { width: 1200, height: 630 });
```

**パフォーマンス比較:**

| 方式 | RAM使用量 | コールドスタート |
|---|---|---|
| headless Chromium | ~300 MB | ブラウザ起動時間 | 
| Takumi (Rust native) | 関数呼び出しのみ | ほぼゼロ |

### ③ なぜ効果的か

Rust製の単一バイナリがCSSパース→レイアウト計算→テキストシェーピング→レイヤー合成→エンコードを全て内部で行うため、外部プロセスへの依存がゼロ。Node.jsではネイティブバイナリ、エッジ環境ではWASMに自動切り替えするため、デプロイ環境を意識せずに使える。`next/og`との完全なドロップイン互換により、既存コードの移行コストが最小。

## 6. Next.js RFC: WebSocket Support in App Router Route Handlers

**出典**: [github.com/vercel/next.js/discussions/95514](https://github.com/vercel/next.js/discussions/95514)

### ① 目的・問題意識

Next.js App RouterのRoute Handlerは従来HTTPのみ対応で、WebSocketを使うには別のサーバー（Express等）を立てる必要があった。RFCでは`NextResponse.upgrade()`を使ったファーストクラスのWebSocketサポートを提案。Vercelがインフラ側でWebSocketサポートを追加したことに合わせた動き。

### ② 技術詳細

**提案されたAPI（`NextResponse.upgrade()`）:**
```ts
// app/ws/route.ts
import { NextRequest, NextResponse } from 'next/server';

export function GET(request: NextRequest) {
  // HTTPをWebSocketにアップグレード
  const { socket, response } = NextResponse.upgrade(request);

  socket.onopen = () => {
    socket.send('Connected!');
  };

  socket.onmessage = (event) => {
    // メッセージの処理
    const data = JSON.parse(event.data);
    socket.send(JSON.stringify({ echo: data }));
  };

  socket.onclose = () => {
    console.log('Client disconnected');
  };

  return response;
}
```

**重要な制約:**
- `NextResponse.upgrade()` はApp Route Handlersのみで有効
- このRouteは**動的**としてマークされ、キャッシュ不可
- 条件付きで呼び出すとリバリデーション時にランタイムエラー
- プロセスシャットダウン時に接続はclose code 1001で閉じられる
- ベースはCrossWSライブラリ

**動作対象:**
- Vercelデプロイ（WebSocketインフラ側で対応済み）
- セルフホスト環境
- 互換デプロイアダプター（対応アダプターのみ）

### ③ なぜ効果的か

通常のRoute Handlerと同じパターン（cookies、headers、early return）でWebSocket認証・処理が書けるため、別のAPIを学ぶ必要がない。ハンドシェイクごとに1回実行するモデルにより、ロジックの見通しが良い。CrossWSベースにより移植性が高い。

## 7. Paper Shaders — ゼロ依存のCanvasシェーダーライブラリ（オープンソース化）

**出典**: [shaders.paper.design](https://shaders.paper.design) / [github.com/paper-design/shaders](https://github.com/paper-design/shaders)

### ① 目的・問題意識

ウェブサイトの背景やヒーローセクションに豊かなビジュアルエフェクト（メッシュグラデーション、ハーフトーン、ドットアニメーション等）を追加したいが、従来はThree.jsなど重いライブラリが必要だった。Paper ShadersはCanvas + WebGLを使ったゼロ依存・軽量シェーダーライブラリで、2026年7月にApache 2.0ライセンスで完全OSSとなった。

### ② 技術詳細

**インストール:**
```bash
# React版
npm install @paper-design/shaders-react

# Vanilla JS版
npm install @paper-design/shaders
```

**Reactでの使用例（メッシュグラデーション）:**
```tsx
import { MeshGradient, DotOrbit } from '@paper-design/shaders-react';

// メッシュグラデーション背景
function HeroSection() {
  return (
    <div style={{ position: 'relative' }}>
      <MeshGradient
        colors={['#5100ff', '#00ff80', '#ffcc00', '#ea00ff']}
        distortion={1}
        swirl={0.8}
        speed={0.2}
        style={{ width: '100%', height: '100vh' }}
      />
      <div style={{ position: 'absolute', inset: 0 }}>
        <h1>コンテンツ</h1>
      </div>
    </div>
  );
}

// ドットオービットアニメーション
function AnimatedBackground() {
  return (
    <DotOrbit
      speed={0.5}
      dotSize={3}
      color="#ffffff"
      style={{ width: 400, height: 400 }}
    />
  );
}
```

**利用可能なシェーダー（30種類以上）:**
- `MeshGradient` — 流動するメッシュグラデーション
- `DotOrbit` — 軌道を描くドットアニメーション
- `HalftoneFilter` — ハーフトーンフィルター
- `NoiseTexture` — ノイズテクスチャ
- 他多数

**設計の特徴:**
- ゼロ依存（外部ライブラリ不要）
- npmインストール またはPaperデザインツールでビジュアルデザイン
- 全設定はコードにエクスポート可能
- バージョン 0.0.x のため依存関係のバージョン固定を推奨

### ③ なぜ効果的か

WebGL シェーダーを直接記述することなく、Reactコンポーネントとして宣言的に扱えるため、デザイナーとエンジニアの両方がPaperデザインツールで視覚的にパラメータを調整してコードにエクスポートするワークフローが成立する。ゼロ依存のため既存プロジェクトへの追加コストが極めて低い。OSSとなったことで商用利用も制限なし。

## 8. Kotlin Multiplatform vs React Native — 同じアプリを両方で作った

**出典**: [swmansion.com/blog/we-built-the-same-app-in-kmp-and-react-native-here-s-what-we-found/](https://swmansion.com/blog/we-built-the-same-app-in-kmp-and-react-native-here-s-what-we-found/)

### ① 目的・問題意識

クロスプラットフォームモバイル開発の主要選択肢となったKMP（Kotlin Multiplatform）とReact Nativeを、**同一仕様のアプリを実際に作って計測**することで客観的に比較。Software Mansionのエンジニアが行ったベンチマーク研究。

### ② 技術詳細

**テストアプリ:** SpaceXの最近のロケット打ち上げ一覧表示アプリ

#### アプリサイズ

| プラットフォーム | React Native | KMP |
|---|---|---|
| Android（インストールサイズ） | 大（~8×） | **小（~8×小さい）** |
| iOS（ダウンロードサイズ） | わずかに小 | わずかに大（~1.3MB差） |

**理由:**
- Android: R8はKotlinバイトコードに直接作用→積極的にツリーシェイク。React NativeはJSバンドルがHermesエンジンの別アーティファクトとなりR8が届かない
- iOS: React NativeはUIKitにレンダリングを委譲するためメモリ効率が高い。KMPはSkia Rendererを常時メモリに保持

#### 起動時間（TTID: Time to Initial Display）

**Android（Pixel 7 / Motorola Edge 60）:**
```
React Native: 250-280ms（JSエンジン+ブリッジ+JSバンドルのロード必要）
KMP:          大幅に高速（Skia Renderer初期化がボトルネックだが軽量）

Huawei P40 Lite（低スペック）:
React Native: 600ms超
KMP:          高速
```

**iOS（iPhone 16 / 17）:**
```
TTID差: わずか20-28ms（ほぼ同等）

TTFD（Time to First Draw）:
React Native: iPhone 16で93ms速い、iPhone 17で6ms速い
KMP:          iPhone 13 miniで170ms速い（KMPが優位な唯一のデバイス）
```

#### メモリ使用量
- **iOS**: React NativeがKMPの3-4×少ない（UIKitにレンダリング委譲のため）
- **Android**: KMPが優位

#### 開発者体験の比較

| 観点 | React Native | KMP |
|---|---|---|
| 開発者プール | 大（JavaScript最大言語） | 小（Kotlin特有） |
| 型安全性 | TypeScript（良好） | Kotlin（ネイティブ型安全） |
| デバッグ | JSデバッガ | ネイティブデバッグツール |
| コード共有率 | Discordで98%（実証済み） | 高い（理論上） |
| クラッシュフリー率 | Discordで99.9%（実証済み） | データ少 |

### ③ なぜ効果的か

「完璧なフレームワーク」は存在せず、**プラットフォームと用途によってプロファイルが異なる**：

- **Android中心・バンドルサイズ優先**: KMP
- **iOS中心・メモリ効率優先**: React Native
- **カスタムUI・独自デザインシステム**: どちらもネイティブビュー優位性が消えるため判断基準が変わる
- **開発者採用・スケール**: React Native（JavaScriptエコシステムの広さ）
