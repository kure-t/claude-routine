## 1. Edge が CSS mixins（ネイティブ CSS ミックスイン）のサポートに着手

**記事タイトル**: Edge gets started on CSS mixins
**関連一次情報**:
- [CSS Custom Functions and Mixins Module Level 1 (W3C Draft)](https://drafts.csswg.org/css-mixins/)
- [CSS custom functions and mixins - MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Custom_functions_and_mixins)
- [CSS Mixins are ready for experimentation! - nerdy.dev (Adam Argyle)](https://nerdy.dev/css-mixins-ready-for-experimentation)
- [Chrome Platform Status: CSS Custom Functions](https://chromestatus.com/feature/5179721933651968)

### ① 目的・問題意識

CSS には長年「再利用可能なスタイルの塊を、引数付きで定義して使い回す」手段がネイティブに存在せず、開発者は Sass の `@mixin` / `@include` のようなプリプロセッサに依存してきた。これには次の課題があった。

- プリプロセッサはビルドステップを必要とし、開発サイクルにコンパイル時間が挟まる
- CSS Custom Properties（`--foo`）は値の再利用はできても、**プロパティの集合（ルールセット）や引数付きロジックの再利用**はできない
- 2015 年頃に一度提案された `@apply`（カスタムプロパティに波括弧ブロックを詰めて再利用する仕組み）は、引数を渡せない・仕様上の技術的問題があるとして CSSWG により事実上撤回された経緯がある

これに対し、CSS Working Group は 2024〜2025 年にかけて **CSS Custom Functions and Mixins Module Level 1** という新仕様を策定した。これは「関数（`@function`、値を1つ返す）」と「ミックスイン（`@mixin`、ルールセットや宣言群を返す）」を明確に分離し、いずれも型チェック付きの引数とデフォルト値、`@media` などを使った条件分岐ロジックをサポートする。Frontend Focus #749 が報じているのは、この新しいネイティブミックスインの実装を **Microsoft Edge（Chromium）が Canary チャンネルで開始した**という進捗ニュースである（先行して Chrome Canary ではフラグ付きで実験可能になっていた）。

### ② 具体的な技術詳細とコード例

#### ミックスインの基本定義と呼び出し

```css
/* @mixin: 引数を型付きで受け取り、宣言の集合を返す */
@mixin --gradient-linear(
  --color-1 type(color),
  --color-2 type(color): blue,   /* デフォルト値を指定可能 */
  --angle   type(angle): 45deg
) {
  background: linear-gradient(var(--angle), var(--color-1), var(--color-2));
}

/* @apply: ルールの中でミックスインを適用し、引数を名前付きで渡す */
.hero {
  @apply --gradient-linear(--color-1: red, --angle: 90deg);
  /* --color-2 は未指定なのでデフォルトの blue が使われる */
}
```

#### `@contents` によるスロット（呼び出し側の宣言を差し込む）

```css
@mixin --card(--padding: 1rem) {
  padding: var(--padding);
  border-radius: 8px;
  @contents; /* 呼び出し側が渡した追加の宣言をここに展開する */
}

.card {
  @apply --card(--padding: 2rem) {
    box-shadow: 0 2px 8px rgba(0, 0, 0, .1);
  }
}
```

#### `@function` との役割分担

同モジュールで既に一部ブラウザに実装済みの `@function` は「値を1つ返す（CSS の計算機）」、`@mixin` は「ルールセットを返す（CSS のテンプレート）」という役割分担になっている。

```css
/* @function: 単一の値を返す（先行して Chrome で Ship 済み） */
@function --half-opacity() {
  result: 0.5;
}

h2 {
  opacity: --half-opacity();
}
```

#### 現状のブラウザ実装状況

- Chrome Canary: `--enable-features=CSSMixins` フラグを付けて起動すると有効化できる（例: `open -a "Google Chrome Canary" --args --enable-features=CSSMixins`）。引数付き構文はまだ発展途上。
- Microsoft Edge（Chromium ベース）: 今回の Issue #749 で報じられた通り、Canary チャンネルでの実装作業に着手（Chromium 共有エンジンのため Chrome の実装進捗と連動する）。
- MDN の時点の記載では「CSS mixins are not currently supported in any browser（安定版では未対応）」であり、あくまで実験段階。

### ③ なぜそれが効果的か

| 観点 | 内容 |
|------|------|
| **ビルドレス** | Sass 等のプリプロセッサなしに、ブラウザが直接パース・実行するためコンパイルステップが不要になる |
| **型安全性** | `type(color)` のような型指定により、不正な値の混入をパース時点で検出できる（Sass にはない利点） |
| **旧 `@apply` 提案との違い** | 2015年の `@apply` は引数を渡せずルックアップテーブル止まりだったが、新仕様は引数・デフォルト値・`@contents` スロット・条件分岐に対応し、Sass ミックスインとほぼ同等の表現力を持つ |
| **段階的な脱プリプロセッサ** | `@function`（値の再利用）と `@mixin`（ルールの再利用）が揃うことで、Sass に依存していたデザインシステムをネイティブ CSS へ移行しやすくなる |
| **複数ブラウザでの並行実装** | Chrome に続き Edge が実装に着手したことで、Interop の観点から実運用投入までの距離が近づく（ただし現時点では本番投入は時期尚早） |

## 2. 「フロントエンドはこの20年で何が起きたか」— 複雑化したツールチェーンの読み解き方

**記事タイトル**: The Descent — What Happened to the Frontend While You Weren't Watching
**著者**: David Poblador i Garcia
**URL**: [https://davidpoblador.com/deep-dives/what-happened-to-the-frontend/](https://davidpoblador.com/deep-dives/what-happened-to-the-frontend/)

### ① 目的・問題意識

2008年頃、フロントエンド開発は「HTML ファイルを書いて FTP でアップロードする」だけで完結していた。しかし iPhone 登場以降の約20年で、フロントエンドは以下のような複雑さを積み上げてきた。

- 初心者向けチュートリアルの最初の一歩で、いきなり16個もの見慣れないツール（その半分が「速い」を意味する日本語由来の名前 — Vite（速い）、Turbopack、Rspack、Swc 等）が登場する
- 単純なお問い合わせフォームをレンダリングするだけの `npm install` が、アポロ誘導コンピュータの搭載コード量を超えるパッケージをダウンロードする
- 現場を離れていたエンジニアが復帰すると、ツールチェーン全体が別物になっている「浦島太郎」状態に陥る

本記事はこの「圧倒される複雑さ」に対し、**全てを学び直す必要はなく、本当に土台（load-bearing）となっている2割を理解すれば、残り8割はオプションの選択肢として割り切ってよい**という整理の仕方を提示するのが狙いである。技術トレンド記事ではなく、20年間の変遷を振り返りながら「何が本質的な変化で、何が単なる流行だったか」を切り分ける読み物（エッセイ／回顧録）である。

### ② 具体的な内容（技術詳細）

コードサンプルを提示する記事ではなく、フロントエンドの歴史的変遷を時系列でたどるナラティブ記事だが、扱われている技術的トピックは以下の通り。

- **ビルドツールの世代交代**: Babel（JavaScript 製トランスパイラ）から SWC（Rust 製）への主要フレームワーク内部での置き換え。Vite がその上に位置し、開発時は即時起動、本番ビルドでは最適化されたバンドルを生成するデフォルトツールとして定着した
- **「Rust で書き直したら50倍速くなった」というカンファレンスの決まり文句**: SWC、Rspack、Turbopack など、Rust/ネイティブ実装への移行が各所で繰り返し語られてきた経緯
- **揺り戻し（Pendulum Swing）**: 20年に及ぶビルドツール・バンドラー全盛期を経て、業界は「サーバーで HTML をレンダリングし、JavaScript をほぼ出荷しない」という、FTP でアップロードしていた時代に近い思想へ回帰しつつある、というテーゼ。すなわち「Web プラットフォームと戦うのではなく、それを使う」という方向性
- **AI とフロントエンドの融合**: UI バリエーションの生成やコンテンツの動的な適応など、AI の入出力を前提としたシステム設計がフロントエンド開発の「通常運転」の一部になりつつあるという指摘

### ③ なぜそれが効果的か

- 「新しいツールを全部追いかけなければならない」という燃え尽き感（ツール疲れ）に対し、**土台となる2割とオプションの8割を区別する**という具体的なフィルタリング基準を与えている
- 歴史的経緯（なぜ Babel → SWC のような置き換えが起きたか、なぜバンドラーが必要になったか）を理解することで、個々のツールを暗記するのではなく「なぜそれが存在するのか」という一次原理から捉え直せる
- サーバーレンダリング回帰や AI 統合といった直近のトレンドを、20年スパンの文脈に位置づけることで、単なる一過性の流行ではなく歴史的な振り子運動として理解しやすくなる

## 3. Safari MCP サーバー — AI コーディングエージェント向けのブラウザ検査基盤

**記事タイトル**: Introducing the Safari MCP server for web developers
**URL**: [https://webkit.org/blog/18136/introducing-the-safari-mcp-server-for-web-developers/](https://webkit.org/blog/18136/introducing-the-safari-mcp-server-for-web-developers/)
**関連報道**: [9to5Mac](https://9to5mac.com/2026/07/01/safaris-new-mcp-server-lets-coding-agents-inspect-and-debug-websites/) / [MacRumors](https://www.macrumors.com/2026/07/01/apple-releases-safari-technology-preview-247/) / [Search Engine Journal](https://www.searchenginejournal.com/safaris-mcp-server/581487/)

### ① 目的・問題意識

AI コーディングエージェント（Claude など）にウェブサイトのデバッグやテストを任せる際、これまでは Selenium や Playwright のような汎用ブラウザ自動化フレームワークをエージェント側で組み合わせる必要があり、以下の課題があった。

- エージェントが実際にブラウザ内で何が起きているか（DOM の実際の状態、コンソールログ、ネットワークリクエスト）を直接「見る」手段がなく、静的なソースコード解析に頼りがちだった
- ブラウザ自動化の「のり付けコード」をエージェント側・開発者側で個別に用意する必要があった
- Safari／WebKit 固有の挙動・バグはサードパーティのブラウザ自動化ツールでは再現しづらいケースがあった

Apple はこの課題に対し、**Safari Technology Preview 247** で公式の **Safari MCP サーバー**を導入した。これは Model Context Protocol（MCP、Anthropic が策定し、その後 Linux Foundation の Agentic AI Foundation に寄贈されたオープン標準）に準拠したサーバーで、MCP 互換のどのクライアント（Claude Code、Claude Desktop 等）からでも Safari に接続できる。

### ② 具体的な技術詳細とコード例

**提供元・対応環境**: Safari Technology Preview 247（macOS 専用。Safari MCP サーバー自体も macOS のみで動作）

**エージェントが利用できる機能（MCP ツールとして公開）**:
- ページの DOM 検査
- コンソールログの取得
- ネットワークリクエストの検査
- スクリーンショットの取得
- ページ上の要素とのインタラクション（クリック、フォーム入力など）

**`.mcp.json` での設定例**（Claude Code 等の MCP クライアントから接続する場合）:

```json
{
  "mcpServers": {
    "safari-mcp-stp": {
      "command": "/Applications/Safari Technology Preview.app/Contents/MacOS/safaridriver",
      "args": ["--mcp"]
    }
  }
}
```

> 補足: Claude Code の CLI は `~/.claude/settings.json` の `mcpServers` フィールドを読み込まない（それは Claude Desktop 用のフォーマット）。`.mcp.json` に上記のスニペットを追加するか、`claude mcp add` コマンドで登録する必要がある。設定ファイルはセッション開始時に読み込まれるため、編集後はセッションの再起動が必要。

**接続確認**:

```bash
claude mcp list
# => mcp-safari — ✓ Connected
```

**想定ユースケース**（報道内容より）:
- ウェブサイトのデバッグ
- Safari 互換性テスト
- パフォーマンス分析（Core Web Vitals の診断など、SEO 観点での活用も報じられている）
- アクセシビリティチェック
- UI 状態の検証

### ③ なぜそれが効果的か

- エージェントと実ブラウザの間の「のり付けコード」レイヤーを取り除き、DOM／ネットワーク／コンソールという**実際のレンダリング結果に基づく一次情報（ground truth）**をエージェントに直接与えられる
- MCP という共通プロトコルに準拠しているため、Claude をはじめとする任意の MCP 対応クライアントから同じインターフェースで接続でき、ツールごとに個別の連携実装を書く必要がない
- サードパーティ製の Playwright ラッパー等と異なり、WebKit 開発元による**ファーストパーティ実装**であるため、Safari 固有のクセ・バグを含めて忠実に再現でき、Safari 限定の不具合調査に特に有効
- スクリーンショットやコンソール・ネットワークの取得までを1つの MCP サーバーで完結できるため、エージェントが自律的に「変更 → 確認 → 修正」のデバッグループを回しやすくなる

## 4. CSS Anchor Positioning 入門 — JS 不要のツールチップ配置

**記事タイトル**: Let's hang! An intro to CSS Anchor Positioning with basic examples
**URL**: [https://utilitybend.com/blog/lets-hang-an-intro-to-css-anchor-positioning-with-basic-examples](https://utilitybend.com/blog/lets-hang-an-intro-to-css-anchor-positioning-with-basic-examples)
**参考一次情報**: [MDN: Using CSS anchor positioning](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning/Using) / [W3C: CSS Anchor Positioning Module Level 1](https://www.w3.org/TR/css-anchor-position-1/)

### ① 目的・問題意識

これまで、トリガー要素（ボタンなど）に対してツールチップやポップオーバー、ドロップダウンメニューを「隣接した位置に」表示するには JavaScript が不可欠だった。

- Floating UI、Popper.js、Tippy.js のようなライブラリで座標計算を行う必要があった
- ビューポート端でのオーバーフロー検出と、はみ出した場合に表示方向を反転させる「flip」処理を自前で実装する必要があった
- スクロールやリサイズのたびに再計算するためのイベントリスナーを張る必要があり、パフォーマンスコストが発生していた

**CSS Anchor Positioning API** はこのギャップを埋め、「この要素を、あの要素を基準にこう配置する」という宣言をスタイルシートだけで完結させる。2026年時点で Baseline 2026 ステータスに到達しており、Chrome 125+、Firefox 132+、Safari 18.2+ で利用可能になっている。

### ② 具体的な技術詳細とコード例

要素をアンカー位置指定するには「関連付け（association）」「配置方法（position）」「位置（location）」の3要素が必要になる。

**1. アンカー要素の定義（`anchor-name`）**

```css
.trigger {
  anchor-name: --my-anchor;
}
```

**2. 位置指定対象の要素をアンカーに紐づける（`position-anchor`）**

```css
.tooltip {
  position: absolute;           /* anchor 指定には position: absolute/fixed が必須 */
  position-anchor: --my-anchor;
  top: anchor(bottom);          /* アンカーの下端を基準に配置 */
  left: anchor(center);
  justify-self: anchor-center;  /* 中央揃え */
  margin-top: 8px;
}
```

**3. アンカー関数による相対配置のバリエーション**

```css
/* アンカーの右側に配置 */
.tooltip-right {
  position-anchor: --my-anchor;
  left: anchor(right);
  align-self: anchor-center;
  margin-left: 10px;
}

/* アンカーの上側に配置 */
.tooltip-top {
  position-anchor: --my-anchor;
  bottom: anchor(top);
}
```

**4. ビューポート端での自動反転（`position-try-fallbacks`）**

```css
.tooltip {
  position-anchor: --my-anchor;
  top: anchor(bottom);
  position-try-fallbacks: flip-block, flip-inline;
  /* 画面端でツールチップが見切れる場合、自動的に上下・左右を反転する */
}
```

複数のアンカー名をカンマ区切りで1要素に割り当てることも可能（`anchor-name: --anchor1, --anchor2;`）で、1つのアンカーに対して複数の被配置要素を紐づけられる。

### ③ なぜそれが効果的か

| 観点 | 内容 |
|------|------|
| **JS 完全排除** | Floating UI 等のライブラリなしに、ツールチップ・ポップオーバーの位置決めがスタイルシートのみで完結する |
| **ネイティブな再計算** | スクロールやリサイズ時の位置再計算をブラウザのレンダリングエンジンが直接行うため、JS のイベントリスナーによるオーバーヘッドがなくなる |
| **宣言的な衝突回避** | `position-try-fallbacks` により、これまで Popper.js の "flip" モディファイアが命令的に行っていたビューポート端でのフリップ処理を宣言的に記述できる |
| **Baseline 到達による実用性** | 主要3ブラウザ（Chrome/Firefox/Safari）で Baseline 2026 に達しているため、ポリフィルなしでの本番投入が現実的な選択肢になっている |

## まとめ

Issue #749 では、**CSS のネイティブ機能拡張（mixins、anchor positioning）**と、**AI エージェント連携基盤の整備（Safari MCP サーバー）**という2つの潮流に加え、**20年というスパンでのフロントエンド全体の振り返り**という読み物が取り上げられていた。CSS 側は「プリプロセッサ・JS ライブラリに頼らずネイティブでどこまでできるか」という脱ツール依存の流れ、MCP 側は「AI エージェントが実ブラウザの一次情報に直接アクセスできるようにする」というエージェント連携の流れとして捉えられる。
