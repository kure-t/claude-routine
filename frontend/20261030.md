## 1. TanStack Redact — ブラウザ向けの軽量 React ランタイム

**参照:** https://tanstack.com/blog/introducing-tanstack-redact

### ① 目的・問題意識

React アプリは React + React DOM のバンドルサイズ（gzip で約 69.2 KB）を常に抱えることになる。TanStack Redact は「アプリケーションコードを一行も変えずに、ブラウザに送る JavaScript を減らす」ことを目的とした **React の代替ランタイム**。Tanner Linsley が自社サイト（tanstack.com）で使い始め、他チームも本番投入した実績をもとに OSS として公開された。

### ② 技術詳細

**基本コンセプト:**
- React 100% API 互換の「論理的な射影（logical projection）」として実装
- ブラウザ側の React / React DOM をビルド時にスワップするだけ（ソースコードは変更不要）
- レンダリングは **同期的**（React の Time Slicing / Concurrent 機能は含まない）

**バンドルサイズ比較（gzip）:**

| ビルド | React | Redact | 削減率 |
|--------|-------|--------|--------|
| Vite (デフォルト) | 69.2 KB | 23.3 KB | -66.3% |
| TanStack Start | 109.3 KB | 62.3 KB | -43.0% |
| Vinext | 〜 | 〜 | -最大 70.5% |

**セットアップ（Vite の例）:**

```bash
pnpm add --save-exact @tanstack/redact
```

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import redact from '@tanstack/redact/vite'

export default defineConfig({
  plugins: [
    react(),
    redact(), // react() の後に追加するだけ
  ],
})
```

**Next.js / Vinext との組み合わせ:**
- サーバーサイドは引き続き React でレンダリング
- ブラウザの Hydration・クライアントレンダリングのみ Redact に切り替わる

**トレードオフ:**

| 機能 | React | Redact |
|------|-------|--------|
| バンドルサイズ | 大 | 小 |
| 同期レンダリング | △ (Time Slicing あり) | ○ |
| Time Slicing / Concurrent | ○ | ✗ |
| useTransition | ○ | 限定的 |
| useOptimistic | ○ | 未対応 |
| Suspense retry | ○ | 遅い (+124.8%) |
| Preact との比較 | 大きい | 中間（より多くの React 動作をサポート） |

**ユーザー報告の注意点:**
一部のユーザーが「Redact に切り替えたら re-render の CPU コストが約 2 倍になった」と報告。バンドルサイズが小さくなっても、ランタイムパフォーマンスが必ずしも向上するわけではない。

### ③ なぜ効果的か

- ビルド設定に 1 行追加するだけで既存の React コードが動作し、送信 JS を最大 66% 削減できる
- Preact よりもモダンな React の挙動（Transitions、Form Actions）を保持しつつ軽量化
- TanStack Start / Vite / Vinext / Next.js 全て対応（v0.2.0 以降）

## 2. Design Systems Should Be Fast by Default — デザインシステムのパフォーマンス比較

**参照:** https://denodell.com/blog/design-systems-should-be-fast-by-default  
**再現リポジトリ:** https://github.com/denodell/design-system-performance-tests

### ① 目的・問題意識

Den Odell が「主要な React デザインシステムはデフォルトでどれくらい速いのか？」を検証。多くの開発チームがデザインシステムを選ぶ際にパフォーマンスを無視しがちだという問題意識から、実際の操作シナリオでベンチマークを実施した。

### ② 技術詳細

**テスト方法:**
- 249 カ国のリストを含むドロップダウン（Combobox / Select）を開く
- 100 個のチェックボックスを一括選択する
- Chrome DevTools で CPU を **4x スロットル**してプロファイリング
- 対象: MUI、Mantine、Ant Design、React Spectrum、Ionic 他 10 ライブラリ

**ドロップダウン開閉の結果（4x CPU スロットル時）:**

| ライブラリ | 開閉時間 | 最長ブロック時間 | 100ms 予算超過 |
|-----------|---------|---------------|--------------|
| Mantine | 84 ms | — | なし |
| Ant Design | 134 ms | — | なし |
| MUI | 200ms 超 | — | 超過 |
| React Spectrum | 227 ms | 162 ms | 超過 |
| Ionic | 最も遅い（React Spectrum の 5 倍以上） | — | 超過 |

**チェックボックス 100 個選択の結果:**

| ライブラリ | 選択時間 |
|-----------|---------|
| React Spectrum | 298 ms（最長 53 ms ブロック） |
| Ant Design | MUI の約 6 倍遅い |

**React Spectrum が遅い根本原因の特定:**

Chrome Profiler でスタックを追うと、React Spectrum が内部で使用する **React Aria** の `useVirtualizerItem` フックが犯人だった。

```
// 問題の再現（疑似コード）: 各アイテムごとにこれが走る
function useVirtualizerItem(item) {
  useLayoutEffect(() => {
    // 1. checkVisibility() を呼ぶ → Layout を強制
    const isVisible = isElementVisible(node)  // → checkVisibility()
    
    // 2. height をリセット → もう一度 Layout を強制
    node.style.height = ''
    
    // 3. サイズを計測 → 再度 Layout を強制
    const size = getSize(node)  // → getBoundingClientRect() etc.
  })
}
```

各オプションの `LayoutEffect` が **1 つずつ順番に** 実行され、その度に `checkVisibility()` → Layout 強制が発生。249 要素分これが繰り返されるため、UI がフリーズする。

Den Odell は再現リポジトリ（`denodell/react-spectrum-picker-open-repro`）を作成して Adobe チームに Issue を報告し、既にレビュー中の修正 PR がある（`adobe/react-spectrum#10787`）。

**重要な観察:**
- パフォーマンスはフレームワーク（React）の問題ではなく、**ライブラリ実装の問題**
- Ant Design と MUI は同じ React を使っているが、パフォーマンスが大きく異なる

### ③ なぜ効果的か

- 実際のユーザー操作シナリオで測定しており、「体感の遅さ」と一致する
- CPU スロットルにより、低スペックデバイスでの挙動を再現
- 100ms という「ユーザーが即時と感じる閾値」（RAIL モデル）を基準に評価
- Layout Thrashing（レイアウトの強制再計算）という具体的な問題を特定できた

## 3. React.lazy と Suspense の隠れた 300ms 遅延

**参照:**
- https://rahuulmiishra.medium.com/one-of-the-toughest-react-interview-questions-react-lazy-and-the-hidden-300-ms-wait-5e3843740534
- https://tabwidgets.com/blog/react-lazy-suspense-delay
- GitHub Issue: https://github.com/react/react/issues/36569

### ① 目的・問題意識

`React.lazy` でコード分割したコンポーネントを事前にプリロードしても、**初回レンダリング時に必ず Suspense フォールバックが表示されてしまう**という挙動がある。これは開発者にとって「なぜプリロードしても意味がないのか？」という疑問につながる、直感に反する動作。

### ② 技術詳細

**根本的な仕組み:**

```tsx
// lazy() が返すオブジェクトは内部的にこういう状態を持つ
const LazyComponent = React.lazy(() => import('./HeavyComponent'))
// 状態: { status: 'pending', value: Promise }
//       { status: 'fulfilled', value: Module }
//       { status: 'rejected', value: Error }
```

```tsx
// 問題の再現
function App() {
  // プリロードしても...
  useEffect(() => {
    LazyComponent._init(LazyComponent._payload) // 内部APIで強制ロード
  }, [])

  return (
    <Suspense fallback={<Spinner />}>
      <LazyComponent /> {/* 初回レンダリングで必ずフォールバックが表示 */}
    </Suspense>
  )
}
```

**なぜ遅延が発生するか:**

React には `FALLBACK_THROTTLE_MS = 300` という定数があり、**Suspense バウンダリが一度フォールバックを表示した後、次にコンテンツを表示するまで最低 300ms 待つ**仕組みになっている。

```
Timeline:
t=0ms   : LazyComponent がレンダリング開始
t=0ms   : Suspense が投げられる（import() はプロミスを返す = 非同期）
t=0ms   : フォールバック (<Spinner />) が表示される
t=1ms   : import() が完了（コードは既にキャッシュ済みだとしても）
t=~304ms: コンテンツが表示される ← 300msの遅延
```

**計測結果（Medium 記事より）:**

| シナリオ | 表示までの時間 |
|---------|-------------|
| コードをプリロード済み | ~304 ms |
| コードをオンデマンドロード | ~305 ms |

プリロードしてもしなくても、ほぼ同じ時間がかかる。

**React Issue #36569 の報告:**

```
// 再現ステップ
const loader = () => import('./Panel')
const LazyPanel = React.lazy(loader)

// 事前にロード
await loader()

// レンダリング時にまだ 300ms 待つ
// → Suspense fallback がない場合は空白が 300ms 表示される
```

**ワークアラウンド（非推奨だが実用的）:**

```tsx
// React の内部 API を利用（バージョンアップで壊れる可能性あり）
// React 19.x での例
function preloadLazy(lazyComponent) {
  const payload = lazyComponent._payload
  const init = lazyComponent._init
  if (payload._status === -1) {
    // ロードを開始して状態を fulfilled にする
    init(payload)
  }
}

// より安全なアプローチ: startTransition を使う
function Parent() {
  const [show, setShow] = useState(false)

  return (
    <>
      <button onClick={() => startTransition(() => setShow(true))}>
        Show
      </button>
      {show && (
        <Suspense fallback={<Spinner />}>
          <LazyComponent />
        </Suspense>
      )}
    </>
  )
}
// startTransition を使うと、既存の UI を表示したまま待機できる
```

**ドキュメントの問題:**

`react.dev` の Suspense ドキュメントにはこの 300ms 遅延について記載がなく、GitHub Issue #8490 でドキュメント追加の要望が出ているが、まだ反映されていない。

### ③ なぜ効果的か（この知識が重要な理由）

- パフォーマンス最適化として「プリロードすれば速くなる」という思い込みを防げる
- `startTransition` を使った正しい遷移実装の理解につながる
- `FALLBACK_THROTTLE_MS` の存在を知ることで、謎の遅延デバッグに役立つ
