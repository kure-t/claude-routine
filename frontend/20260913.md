## 1. 新しい HTML「Capability Elements」— `<geolocation>` と `<usermedia>`

**記事タイトル**: Introducing the `<geolocation>` HTML element / Introducing the `<usermedia>` HTML element
**URL**: [https://developer.chrome.com/blog/geolocation-html-element](https://developer.chrome.com/blog/geolocation-html-element) / [https://developer.chrome.com/blog/usermedia-html-element](https://developer.chrome.com/blog/usermedia-html-element)
**関連**: [MDN `<geolocation>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/geolocation)

### ① 目的・問題意識

これまで位置情報やカメラ／マイクへのアクセスは `navigator.geolocation.getCurrentPosition()` や `navigator.mediaDevices.getUserMedia()` のような JavaScript API を script から呼び出す形でしか実現できなかった。この方式には次のような課題があった。

- 許可プロンプトが「ページの読み込み直後にいきなり出る」など、ユーザーの意図とタイミングが一致しないことが多く、ブラウザの自動クワイエットモード（無言でブロックする挙動）に引っかかりやすい
- 一度拒否されると、ユーザーは複雑なブラウザ設定を開いて手動で権限を戻す必要があった
- 許可を得るための「ボタンを押す」という UI をこれまで毎回開発者が自前で実装しなければならなかった

Chrome は 2026 年に「Capability Elements」という新しいカテゴリの HTML 要素群を導入し、位置情報・カメラ・マイクなどセンシティブな権限を要求する UI をブラウザ自身が提供する宣言的な要素として標準化し始めた。`<geolocation>`（Chrome 144〜）と `<usermedia>`（Chrome 151〜）はその第一弾・第二弾である。

### ② 具体的な技術詳細とコード例

**`<geolocation>` 要素の基本**

- `autolocate` 属性を `true` にすると、以前に許可済みであれば要素がレンダリングされた時点で即座に位置情報を取得する。`false`（デフォルト）の場合はユーザーが要素を操作するまで取得されない。
- 要素は単なる「許可ボタン」ではなく、位置情報そのものを取得して配信する「データメディエーター」として機能する。
- サポートされていないブラウザでは、要素内部に置いた fallback 用の子要素（ボタンなど）がそのまま描画される。対応ブラウザでは自身がレンダリングされ、子要素は隠される。

```html
<!-- 対応ブラウザ: ブラウザネイティブの位置情報コントロールが描画される -->
<!-- 非対応ブラウザ: 内部の <button> がそのまま表示され、フォールバックとして機能する -->
<geolocation autolocate="false">
  <button id="fallback-locate">現在地を取得</button>
</geolocation>
```

```javascript
// 対応判定 + イベント購読
if ('HTMLGeolocationElement' in window) {
  const el = document.querySelector('geolocation');
  el.addEventListener('location', (event) => {
    if (event.error) {
      console.error('位置情報取得エラー:', event.error);
      return;
    }
    const { position } = event;
    console.log(position.coords.latitude, position.coords.longitude);
  });
} else {
  // フォールバック: 従来の Geolocation API を手動で呼び出す
  document.querySelector('#fallback-locate').addEventListener('click', () => {
    navigator.geolocation.getCurrentPosition(
      (position) => console.log(position.coords.latitude, position.coords.longitude),
      (error) => console.error(error)
    );
  });
}
```

**`<usermedia>` 要素**

- カメラ／マイクへのアクセス許可フロー全体（意図のキャプチャ → ブラウザプロンプトの管理 → `MediaStream` オブジェクトの配信）を丸ごと引き受ける。
- プロンプトは要素への「物理的なタップ」の後にしか表示されないため、ユーザーの明確な意図の証拠（trusted signal of intent）としてブラウザに扱われ、script が勝手に呼び出した場合に働く自動クワイエットブロックを回避できる。
- 過去にアクセスを拒否していた場合でも、要素をタップすると専用の「リカバリーフロー」が起動し、ブラウザ設定画面を開かずにその場でカメラ／マイクを再許可できる。
- Chrome 153 では、この Capability Elements 系列がさらに拡張され、映像だけを要求する `<camera>` 要素と、音声だけを要求する `<microphone>` 要素が追加されている。

```html
<usermedia>
  <button>カメラとマイクを有効にする</button>
</usermedia>
```

```javascript
document.querySelector('usermedia').addEventListener('mediastream', (event) => {
  const stream = event.stream; // MediaStream をそのまま受け取れる
  videoEl.srcObject = stream;
});
```

### ③ なぜそれが効果的か

- **信頼できる意図のシグナル**: プロンプトがユーザーの物理的な操作に直結しているため、ブラウザ側が「これは本物のユーザー操作だ」と確信を持って扱える。script 起因の許可リクエストに対する自動ブロックを回避しやすい。
- **開発コストの削減**: 許可の取得・拒否後の再許可導線・ストリームの受け渡しをブラウザが肩代わりするため、開発者は同等の UI を毎回自作する必要がなくなる。
- **段階的強化 (progressive enhancement)**: 要素内部に fallback 用の子要素を置くだけで、非対応ブラウザでは自動的に従来の JS API ベースの実装にフォールバックできる。
- **プライバシーの一貫性**: ブラウザが権限フローを一元的に握ることで、サイトごとにバラバラだった許可 UI のパターンが統一され、ユーザーがフィッシング的な偽の許可 UI と本物を区別しやすくなる。

## 2. HTML-in-Canvas — Canvas の中に本物の DOM を描画する

**記事タイトル**: Exploring the HTML-in-Canvas Proposal / HTML-in-Canvas: The Biggest Canvas API Addition Since OffscreenCanvas
**URL**: [https://wicg.github.io/html-in-canvas/](https://wicg.github.io/html-in-canvas/) （[GitHub: WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）

### ① 目的・問題意識

Web 開発者はこの 20 年間、次の二択を迫られてきた。

- **DOM**: リッチでセマンティックかつアクセシブルな UI が作れるが、大量の要素やピクセル単位の細かい描画には向かない
- **Canvas**: 高速な 2D/3D 描画ができるが、アクセシビリティ・ページ内検索・翻訳機能・ダークモード対応・オートフィル・拡張機能・DevTools でのインスペクトなど、DOM が標準で持っている恩恵をすべて自前で再実装する必要がある

チャートライブラリ、図形エディタ、デザインツールなどは特に軸ラベル・凡例・ツールチップのようなテキスト主体で複雑なレイアウトを Canvas 上で自前実装しており、フォント計測や折り返し処理をゼロから再発明していた。HTML-in-Canvas はこのジレンマを解消し、Canvas の中に「本物の」HTML 要素を描画できるようにする WICG 提案である。Chromium 146+ でフラグの裏に実装されている。

### ② 具体的な技術詳細とコード例

- `layoutsubtree` 属性を `<canvas>` 要素に付与すると、その子孫要素がレイアウトとヒットテストに参加するようになる。子要素はブラウザによってレイアウトされるが、明示的に描画されるまで画面には表示（ペイント）されない。
- `drawElementImage()` メソッドが中核 API。`<canvas>` の直接の子要素に対して呼び出すと、その要素の現在のレンダリング結果を canvas 上に描画し、DOM 上の位置を描画位置に同期させるための CSS transform を返す。

```html
<canvas id="source" layoutsubtree>
  <div id="content">
    <p>これは本物の DOM 要素です</p>
    <button>クリック可能なボタン</button>
  </div>
</canvas>
```

```javascript
const canvas = document.getElementById('source');
const content = document.getElementById('content');
const ctx = canvas.getContext('2d');

canvas.onpaint = () => {
  ctx.reset();
  // content (本物の DOM) を canvas に描画し、
  // 対応する transform を取得する
  const transform = ctx.drawElementImage(content, 0, 0);
  content.style.transform = transform; // DOM 上の位置を描画位置に同期
};

canvas.requestPaint();
```

- 有効化方法: Chromium 系ブラウザで `chrome://flags/#canvas-draw-element` を有効にする（動かない場合は Chrome Canary を推奨）。
- ユースケース: チャートライブラリの軸・凡例・ツールチップ、図形/デザインツールのラベル、データ可視化ダッシュボードなど。これまで「絶対配置の DOM オーバーレイを Canvas の描画位置に手動で追従させる」というズレやすい実装をしていた箇所を、ブラウザ標準の仕組みに置き換えられる。

### ③ なぜそれが効果的か

- **DOM と Canvas の両立**: アクセシビリティツリー、ページ内検索、翻訳、ダークモード、オートフィル、拡張機能、DevTools でのインスペクトなど、DOM が持つ恩恵を保ったまま Canvas/WebGL/WebGPU テクスチャに描画できる。
- **既存実装の置き換え**: これまで独自に再実装されていたテキストレイアウト・フォント計測・折り返し処理をブラウザに委譲でき、実装コストとバグ面積を削減できる。
- **同期のズレがなくなる**: `drawElementImage()` が返す transform を DOM 要素にそのまま適用するだけで、描画位置と実際の DOM 位置の同期が保証される。

## 3. `<model>` 要素 — 3D モデルを `<video>` と同じ感覚で埋め込む

**記事タイトル**: The `<model>` element (Explainer)
**URL**: [https://github.com/immersive-web/model-element/blob/main/explainer.md](https://github.com/immersive-web/model-element/blob/main/explainer.md)

### ① 目的・問題意識

HTML は `<img>` / `<picture>` / `<video>` など多様なメディアタイプを宣言的に扱えるが、3D コンテンツを直接扱う宣言的な手段を持っていない。そのため 3D モデルの埋め込みは `<canvas>` を script で操作する形に頼らざるを得ず、Three.js や Babylon.js のようなサードパーティライブラリへの依存が常態化していた。この提案が解決しようとする課題は主に 3 つ。

1. **セキュリティ／プライバシー**: 現状の AR 体験は、ユーザー視点から正しく描画するためにカメラ映像やシーン理解、精密な位置情報など過剰な権限をページに与える必要がある。単に 3D モデルを見せるだけの用途としては不釣り合いなプライバシーリスクになっている。
2. **Canvas の限界**: `<canvas>` は本質的に 2D であり、遠近補正が重要になる没入的コンテキストでの 3D 描画には向かない。
3. **ライブラリ依存**: 他のメディア形式と同じように宣言的に埋め込みたいだけなのに、3D モデルだけは毎回サードパーティライブラリが必須になっている。

### ② 具体的な技術詳細とコード例

**基本形（`<video>` の `<source>` パターンを踏襲）**

```html
<model style="width: 400px; height: 300px">
  <source src="assets/example.usdz" type="model/vnd.usdz+zip">
  <source src="assets/example.glb" type="model/gltf-binary">
</model>
```

**ユーザーによる自由回転を許可する `stagemode`**

```html
<model style="width: 400px; height: 300px" stagemode="orbit">
  <source src="assets/example.usdz" type="model/vnd.usdz+zip">
  <source src="assets/example.glb" type="model/gltf-binary">
</model>
```

**アニメーションの自動再生**

```html
<model style="width: 400px; height: 300px" autoplay>
  <source src="assets/example.usdz" type="model/vnd.usd+zip">
  <source src="assets/example.glb" type="model/gltf-binary">
</model>
```

**フォールバックコンテンツ（非対応環境・非対応形式向け）**

```html
<model>
  <source src="fake.typ1" type="imaginary/type-1">
  <source src="fake.typ2" type="imaginary/type-2">
  <img src="animated-version.gif" alt="Ha Ha reaction bubble">
</model>
```

**`HTMLModelElement` API（抜粋）**

| メンバー | 種別 | 内容 |
|---|---|---|
| `currentSrc` | プロパティ (読取専用) | 読み込み済みリソースの URL |
| `autoplay` | プロパティ | アニメーション自動再生の可否 |
| `stageMode` | プロパティ | `"orbit"` などユーザー操作モード |
| `environmentMap` | プロパティ | IBL／正距円筒画像による照明設定 |
| `loop` | プロパティ | アニメーションのループ設定 |
| `entityTransform` | プロパティ (JS API) | ビューへのマッピングを表す `DOMMatrixReadOnly` |
| `boundingBoxCenter` / `boundingBoxExtents` | プロパティ (読取専用) | バウンディングボックスの中心／サイズ |
| `duration` / `currentTime` / `playbackRate` | プロパティ | アニメーションの長さ・再生位置・再生速度 |
| `play()` / `pause()` | メソッド | 再生制御（`play()` は Promise を返す） |
| `ready` / `environmentMapReady` | Promise | ソース読み込み完了／照明環境読み込み完了を検知 |

`pointerdown` イベントで `preventDefault()` を呼ぶことで、組み込みのオービット操作を無効化し独自のコントロールを実装できる。

### ③ なぜそれが効果的か

- **`<embed>`/`<object>` を再利用しない理由**: 3D コンテンツは他のメディアタイプと同等のセマンティックな明確さに値するため、専用要素として設計されている。
- **ブラウザネイティブ描画によるセキュリティ**: レンダリングを JavaScript ライブラリではなくブラウザ自身に委譲することで、信頼できないページスクリプトにセンシティブな環境情報を渡さずに済む。
- **`<source>` による形式の柔軟性**: `<audio>`/`<video>` と同じパターンを踏襲し、ブラウザがサポートするファイル形式を自由に選べる。
- **物理ベースレンダリング (PBR) 前提の設計**: ピクセル単位の完全な一致を求めない代わりに、ハードウェアの進化がそのまま描画品質向上につながり、ソースを変更せずに描画が改善し、ページスクリプトからは触れられない環境コンテキスト（影・反射）をブラウザが安全に活用できる。

## 4. Antiquated HTML Snippets and Artefacts — 廃れた HTML の遺物たち

**記事タイトル**: Antiquated HTML Snippets and Artefacts
**URL**: [https://vale.rocks/posts/html-relics](https://vale.rocks/posts/html-relics)

### ① 目的・問題意識

この記事は「廃止された HTML 仕様の要素」ではなく、ブラウザ間競争・サードパーティ連携・ベンダー拡張・プラットフォーム固有ハックの結果として、多くのサイトのソースコードに今も残り続けている遺物的なスニペット群を掘り起こしている。これらは削除しても実害はないのに、コピー&ペーストの連鎖でボイラープレートに居座り続けている、というのが問題意識である。

### ② 具体的な技術詳細とコード例

記事が扱う代表的な遺物（カタログ）:

- **Conditional Comments（条件付きコメント／“condcoms”）**: IE 固有の分岐記法。ブラウザ戦争時代に特定バージョンの IE だけをターゲットにするために使われた。

```html
<!--[if lt IE 9]>
  <script src="html5shiv.js"></script>
<![endif]-->
```

- **`X-UA-Compatible`**: ブラウザが短期間に大きく変わっていた時代に、特定バージョンのレンダリングエンジンとの互換性を宣言するための meta タグ。

```html
<meta http-equiv="X-UA-Compatible" content="IE=edge">
```

- **PICS content labelling**: 古いコンテンツレーティング／ラベリングの仕組み。
- **Microsoft Smart Tags**: ページ内の特定語句を自動的にリンク化する、今は廃止された IE の機能への対応コード。
- **Skype Toolbar のオプトアウト**: 電話番号らしき文字列を Skype が自動リンク化するのを止めるための meta タグ。
- **`msapplication` ピン留めサイト用タグ**: Windows のタスクバーにピン留めした際のアイコン・色などを指定する IE/Edge 専用 meta タグ群。
- **Apple iOS Web App 用 meta タグ**: `apple-mobile-web-app-capable` などホーム画面追加時の挙動を制御するタグ。
- **AMP（Accelerated Mobile Pages）関連マークアップ**。
- **RSD (Really Simple Discoverability) とピンバック**: WordPress などブログツールが自動生成していた発見用リンク・トラックバック機構。
- **Facebook の旧 “Share Partners” タグ**（Open Graph 以前のもの）。
- **Twitter Card 用 meta タグ**: Twitter Cards 機能自体が終了した今では実質的に死んでいるが、多くのサイトに残存している。

### ③ なぜそれが効果的か（＝なぜ削除してよいのか）

- 対象としていたブラウザ（旧 IE 等）や外部サービス（Skype ツールバー、Twitter Cards 等）自体がすでに終了・廃止されているため、これらのタグは実質的に何の効果も発揮していない。
- 残しておくことで得られる利益はゼロだが、HTML の可読性を下げ、ページの `<head>` を肥大化させ、新しく参加した開発者に「これは今も必要なのか？」という無駄な調査コストを強いる。
- 削除することでマークアップがシンプルになり、実際に機能している現行の meta タグ・link タグとの区別がつきやすくなる。

## 5. モダン CSS でカスタムスクロールバーを作る

**記事タイトル**: Custom Scrollbars In CSS
**URL**: [https://ishadeed.com/article/custom-scrollbars-css/](https://ishadeed.com/article/custom-scrollbars-css/)（標準仕様: [MDN: CSS scrollbars styling](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scrollbars_styling)）

### ① 目的・問題意識

これまでカスタムスクロールバーを実装するには、Chrome/Safari/Edge 系ブラウザ専用の非標準擬似要素 `::-webkit-scrollbar-*` に頼るしかなく、Firefox など非対応ブラウザとの互換性維持や、標準化されていない API ゆえの将来性の不安があった。CSS Scrollbars Styling Module の登場（`scrollbar-color` / `scrollbar-width` プロパティの標準化、Chrome 121+ でサポート）により、この状況が変わりつつある。しかし完全な移行にはまだ早く、細かい調整（角丸・hover 状態など）は依然として WebKit 系プレフィックス付き擬似要素でしか実現できないため、両者を組み合わせる「ハイブリッドアプローチ」が実用上の解となる。

### ② 具体的な技術詳細とコード例

**標準構文（`scrollbar-color` / `scrollbar-width`）**

```css
.poem {
  overflow: scroll;
  scrollbar-color: red orange; /* 第1値: thumb（つまみ）の色, 第2値: track（背景）の色 */
  scrollbar-width: thin;       /* auto | thin | none */
}
```

**WebKit 系の擬似要素構文（きめ細かい調整が可能）**

```css
/* 幅 */
::-webkit-scrollbar {
  width: 20px;
}
/* トラック */
::-webkit-scrollbar-track {
  box-shadow: inset 0 0 5px grey;
  border-radius: 10px;
}
/* つまみ（ハンドル） */
::-webkit-scrollbar-thumb {
  background: red;
  border-radius: 10px;
}
```

**`@supports` を使ったハイブリッド実装（標準構文を優先しつつ WebKit 環境にフォールバック）**

```css
/* 標準仕様をサポートするモダンブラウザ向け */
@supports (scrollbar-color: auto) {
  .container {
    scrollbar-color: #337ab7 #f5f5f5;
    scrollbar-width: thin;
  }
}

/* WebKit 系ブラウザ向けフォールバック（角丸・hover などの細部を作り込める） */
.container::-webkit-scrollbar {
  width: 10px;
  height: 10px;
}

.container::-webkit-scrollbar-track {
  background-color: #f5f5f5;
  border-radius: 10px;
}

.container::-webkit-scrollbar-thumb {
  background-color: #337ab7;
  border-radius: 10px;
  border: 1px solid #f5f5f5;
}

.container::-webkit-scrollbar-thumb:hover {
  background-color: #23527c;
}
```

### ③ なぜそれが効果的か

- **標準構文はシンプルで宣言的**: `scrollbar-color` と `scrollbar-width` の 2 行だけで、ベンダー非依存のスクロールバー配色ができる。
- **`@supports` によるプログレッシブエンハンスメント**: 標準構文に対応しているブラウザではそちらを優先させつつ、対応していないブラウザ（あるいは角丸やホバー演出など標準構文では表現できない細部）は WebKit 擬似要素で補うことで、両者の「いいとこ取り」ができる。
- **保守性の向上**: 将来的に標準構文の対応ブラウザが増えるほど WebKit 固有コードへの依存度を下げていけるため、段階的な移行パスとして機能する。

## 6. ブラウザのメインスレッドは高価である — `scheduler.yield()` で応答性を守る

**記事タイトル**: The Browser's Main Thread Is Expensive
**URL**: [https://kciter.so/posts/the-expensive-main-thread/en/](https://kciter.so/posts/the-expensive-main-thread/en/)

### ① 目的・問題意識

50ms を超える JavaScript タスクは「Long Task」と呼ばれ、ブラウザのメインスレッドをブロックしてクリック・キー入力の処理やフレーム描画を止めてしまう。記事はメインスレッド上で DOM 操作を伴うメッセージ処理を連続で行うデモを通じて、FPS が急落し、入力への反応が目に見えて遅延する様子を示している。一方、処理の合間に「譲る（yield）」タイミングを挟むと、入力応答性が劇的に改善することも同じデモで示されている。この記事は、なぜメインスレッドがそれほど「高価」なのか、そしてどうすれば長い処理を分割してブラウザの応答性を保てるかを解説している。

### ② 具体的な技術詳細とコード例

**問題: ブロッキングな長時間処理**

50ms を超えるタスクがあると、その間ブラウザは入力処理もレンダリングも行えない。

**解決策 1: `scheduler.yield()` の基本パターン**

```javascript
async function task() {
  while (stillMoreWorkToDo()) {
    doChunkOfWork();
    if (navigator.scheduling.isInputPending()) {
      // 保留中の入力があるときだけメインスレッドを明け渡す
      await scheduler.yield();
    }
  }
}
```

**解決策 2: 単純なチャンク分割**

```javascript
function doWork(value) {
  console.log(`work chunk ${value}`);
}

const workList = [0, 1, 2, 3, 4];
for (const work of workList) {
  doWork(work);
  await scheduler.yield(); // 1チャンクごとにメインスレッドを解放
}
```

**解決策 3: イベントハンドラ内での yield**

```javascript
checkbox.addEventListener('change', async () => {
  await scheduler.yield();
  doSlowContentFiltering(); // 重い処理を次のタスクとして実行
});
```

- `scheduler.yield()` は Scheduler インターフェースのメソッドで、タスクの途中でメインスレッドを一旦明け渡し、続きの処理を「優先度付きの継続タスク」としてスケジュールし直す。これにより長時間処理を分割してもブラウザの応答性を維持できる。
- `navigator.scheduling.isInputPending()` は、イベントキューに未処理の入力イベント（ユーザーが操作しようとしている兆候）があるかどうかを確認できる API。「本当に必要なときだけ yield する」判断に使う。

### ③ なぜそれが効果的か

- **INP（Interaction to Next Paint）の改善**: メインスレッドのブロック時間を減らすことで、ユーザー操作から次の描画までの遅延を直接的に短縮できる。
- **優先度付き継続**: `setTimeout(fn, 0)` のような従来の分割手法と異なり、`scheduler.yield()` の継続タスクはブラウザのタスクスケジューラーに優先度を認識された状態で再スケジュールされるため、単純な遅延実行より効率的に処理を再開できる。
- **`isInputPending()` との組み合わせ**: 常に yield するのではなく「入力が来ていそうなときだけ yield する」ことで、無駄なタスク分割によるオーバーヘッドを避けつつ応答性を確保できる。

## 7. CSS: the bomb inside your inbox — CSS だけでできる Webmail キーロガー

**記事タイトル**: CSS: the bomb inside your inbox（Black Hat USA 2026 講演）
**URL**: [https://portswigger.net/research/css-the-bomb-inside-your-inbox](https://portswigger.net/research/css-the-bomb-inside-your-inbox)（資料一式: [GitHub: PortSwigger/css-the-bomb-inside-your-inbox](https://github.com/portswigger/css-the-bomb-inside-your-inbox)）
**著者**: Gareth Heyes（PortSwigger）

### ① 目的・問題意識

多くの Webmail クライアント（Gmail, Outlook, Yahoo Mail, AOL Mail, Fastmail, ProtonMail 等）は、受信 HTML メールの JavaScript は徹底的にサニタイズ・無効化する一方で、見た目を保つために CSS はある程度そのまま描画させている。この研究は「CSS だけで、JavaScript や悪性の添付ファイルなしに、どこまで攻撃的なことができるか」を検証したもので、見過ごされてきた攻撃対象領域（overlooked attack surface）を暴いている。実際に、CSS のみで動作するキーロガーを構築し、Microsoft のログイン画面を偽装してパスワードをリアルタイムに盗み取るデモまで作られている。

### ② 具体的な技術詳細とコード例

記事で示されている主要なテクニックのカテゴリ:

- **CSS mutation（CSS ミューテーション）**: サニタイザーの正規表現的な処理をすり抜けるよう CSS を変形させ、フィルタを回避する。
- **属性セレクタのネスト**: `input[value^="a"] input[value^="ab"] { ... }` のように属性セレクタを入れ子にすることで、ペイロードサイズを抑えながらトークンを総当たり（ブルートフォース）的に推測する。
- **`:has()` / `:checked` / `:before` / `:after` などの疑似クラス・疑似要素の悪用**: `<select>` のドロップダウンメニューをパスワード入力欄に見せかけたり、ユーザー操作（チェック状態など）に応じてスタイルを変化させたりする。
- **`background-image` / `@font-face` / `@property` によるリソース要求を使ったデータ持ち出し（exfiltration）**: 入力された値や状態に応じて異なる背景画像 URL・フォント URL をリクエストさせることで、キー入力 1 文字ずつを攻撃者のサーバーへ送信する。
- **フォントの高さオラクル + CSS アニメーション**: CSP が外部リクエストをブロックしている状況でも、文字の高さやアニメーションのタイミング差から数値トークンを推測する手法。
- **クリップボード経由の CSS インジェクション**。
- **`-webkit-text-security` を使った“それっぽい”パスワードフィールドの偽装**: `<select>` 要素の癖を利用し、視覚的にパスワード入力欄に見えるが実態はセレクトメニューである要素を作り、キー入力のたびに一意の CSS ルールを発火させて 1 文字ずつサーバーへ問い合わせを送るキーロガーを構築。
- **HTML のみ（CSS すら使わない）でのキー入力捕捉手法**: 目に見えないほど小さい Unicode 文字で文字を隠し、`<marquee>` 要素でセレクトドロップダウンの見た目を誤魔化す手口も含まれる。

公開されている PoC（10 件超）には、FastMail への CSS hotwiring 攻撃、paste 操作経由のトークン持ち出し、CSP 制限下でのテキストノード抽出、Outlook の画面改ざん、Outlook ラベルの偽装、Firefox 向け／サニタイズ後でも動く／Chrome でリアルタイムに動く各種 Outlook キーロガー、メール経由でのプロンプトインジェクション（OpenAI Atlas 向け）などが含まれる。検証・攻略支援ツールとして CSS トークン持ち出しツール（GitLab で検証済み）、Shazzer（CSS バイパス手法の発見支援）、Hackvertor（CSS ミューテーションの構築支援）も公開されている。

### ③ なぜそれが効果的か

1. **JavaScript を使わない**: Webmail クライアントは JavaScript を徹底的に無効化するが、CSS の描画自体はメールの見た目を保つために許可せざるを得ない。この非対称性そのものが攻撃対象領域になっている。
2. **CSS がユーザー操作に反応できる**: `:hover` / `:focus` / `:checked` / `:has()` のようなセレクタでユーザーの状態変化に反応し、アニメーションを起動したり `background-image` / `@font-face` / `@property` でリソースをリクエストさせたりできるため、正規のブラウザリクエストという「合法的な」経路でデータを持ち出せる。
3. **サニタイザーの盲点を突く CSS ミューテーション**: HTML/CSS サニタイザーは既知の危険なパターンを除去するが、構文的に等価だが表記の異なる CSS へと変形（ミューテーション）させることで検出を回避できる。
4. **ベンダーごとに対応状況が割れている**: Fastmail は 2 件の CSS ミューテーションバグと Proton Mail のプロキシバイパスを修正済みだが、研究公開時点（8/6）で Outlook のラベル偽装や Gmail の `image-set()` バイパスは依然として有効だった。これは「CSS は安全」という前提が業界全体でまだ十分に共有されていないことを示している。
