## 1. The Goldilocks customizable select height

**記事タイトル**: The Goldilocks customizable select height
**著者**: Jake Archibald
**URL**: [https://jakearchibald.com/2026/goldilocks-select-height/](https://jakearchibald.com/2026/goldilocks-select-height/)

### ① 目的・問題意識

CSS の `appearance: base-select`（カスタマイズ可能な `<select>`）を使うと、`::picker(select)` 疑似要素でドロップダウンの見た目を自由にスタイリングできるようになった。しかし、ピッカーの「高さ」をどう決めるかは非自明な問題だった。

- 選択肢が少ない場合、`min-block-size` を固定値（例: `12em`）にすると、無駄に大きな空白ができてしまう
- 選択肢が多い場合、高さを内容に合わせて無制限に広げると、ビューポートからはみ出す
- つまり「小さすぎず、大きすぎない、ちょうどいい（Goldilocks）」高さを CSS だけで実現する必要がある
- 目標は、選択肢が少ない時は内容に合わせて縮み、選択肢が多い時は適切な最大値でクリップされ、かつビューポート内に収まること

### ② 具体的な技術詳細とコード例

#### 本命: `calc-size()` を使う方法（Chrome 対応）

`calc-size()` は第一引数に intrinsic size（`fit-content` など）を渡し、第二引数でその値（`size` キーワード）を使って計算できる関数。

```css
.custom-select::picker(select) {
  --min-size: 12em;
  min-block-size: var(--min-size);

  /* calc-size() を使う方法 */
  @supports (min-block-size: calc-size(fit-content, min(size, 1px))) {
    min-block-size: calc-size(fit-content, min(size, var(--min-size)));
  }

  /* calc-size() 非対応時のフォールバック（ハック） */
  @supports not (min-block-size: calc-size(fit-content, min(size, 1px))) {
    &:not(
      :has(:where(option:nth-of-type(4))),
      :has(:where(optgroup:nth-of-type(2)))
    ) {
      min-block-size: 0;
      max-block-size: fit-content;
    }
  }
}
```

- `min-block-size: calc-size(fit-content, min(size, var(--min-size)))` は「内容に応じた高さ（`fit-content`）」と「上限値 `--min-size`（12em）」の小さい方を最小高さとして採用する、という意味になる。これにより、選択肢が少なくコンテンツの高さが 12em 未満なら、その内容の高さがそのまま `min-block-size` として使われ、余白ができない。
- `::picker(select)` にはさらに `min-inline-size`（ボタンと同じ幅以上を保証）、`max-block-size`（ビューポートからはみ出さないようにする上限）も併用する。

#### フォールバック: `calc-size()` 非対応ブラウザ向けハック

Firefox / Safari はまだ `calc-size()` 未対応のため、`:has()` を使ったセレクタで「選択肢が3個以下、かつ optgroup が1個以下」の場合にのみ `min-block-size` を 0 にし、`max-block-size: fit-content` にすることで、内容に応じて自然に縮む挙動を疑似的に再現する。

- `:has(:where(option:nth-of-type(4)))` = 4番目の `option` が存在する（＝選択肢が4個以上ある）かどうかを判定
- `:has(:where(optgroup:nth-of-type(2)))` = 2番目の `optgroup` が存在するかどうかを判定
- これらのどちらにも該当しない（＝選択肢が少ない）場合だけ、最小高さの制約を外す

### ③ なぜそれが効果的か

- `calc-size()` はレイアウトエンジンに「実際のコンテンツサイズ」を計算させた上でCSS内で算術演算できる、CSSにおいて数少ない「intrinsic size を扱える calc」であるため、JavaScript でコンテンツの高さを測定してインラインスタイルを設定するような処理を完全に代替できる。
- フォールバックは条件のロジックこそ違う（「対象の要素が“該当しない”時だけ制約を外す」という否定形の設計）が、視覚的には calc-size 版とほぼ同じ「ちょうどいい高さ」の挙動を、`:has()` の疑似クラスの組み合わせだけで実現しており、宣言的スタイルシートの範囲内で漸進的強化（progressive enhancement）を成立させている。
- `@supports` によるフィーチャーディテクションで、ブラウザの対応状況に応じて最適な手法へ自動的に切り替わる。

## 2. An animated radial gradient mask over text in CSS

**記事タイトル**: An animated radial gradient mask over text in CSS
**著者**: Cassidy Williams (cassidoo.co)
**URL**: [https://cassidoo.co/post/radial-mask-text-css/](https://cassidoo.co/post/radial-mask-text-css/)

### ① 目的・問題意識

テキストの上に「同心円状に広がるストライプ」のようなアニメーションするマスクを重ねる視覚効果を、画像処理やJSアニメーションライブラリを使わず、CSSの `mask` プロパティだけで実現する。CSS Houdini の Properties and Values API（`@property`）がベースラインとして広く使えるようになったことで、これまでアニメーションできなかった `mask` 用のグラデーション値をアニメーション可能にできる、という点が技術的な核心。

### ② 具体的な技術詳細とコード例

#### マスクの中心コード（`repeating-radial-gradient`）

```css
.masked-text {
  mask: repeating-radial-gradient(
    circle at 198.2px 69.6px,
    black,
    var(--stripes),
    black,
    0,
    transparent,
    calc(var(--stripes) * 2),
    transparent 0
  );
}
```

- `repeating-radial-gradient(circle at X Y, ...)` で、指定した座標を中心に同心円状の縞模様（ストライプ）を繰り返すグラデーションを生成する。
- `--stripes` はカスタムプロパティで、初期値は `2px`。2px ごとに「白い帯」か「透明な帯」が交互に描画される。
- `mask` プロパティにこのグラデーションを渡すと、グラデーションの `black`（不透明・要素が見える部分）と `transparent`（透明・要素が隠れる部分）に応じて、下にあるテキストがアルファマスキングされる。

#### アニメーション可能にするための `@property` 登録

CSS Houdini の Properties and Values API を使って `--stripes` を「アニメーション可能な数値（長さ）」としてブラウザに型登録する。

```css
@property --stripes {
  syntax: "<length>";
  inherits: false;
  initial-value: 2px;
}

.masked-text {
  animation: stripe-in-out 3s ease-in-out infinite;
}

@keyframes stripe-in-out {
  0%, 100% {
    --stripes: 2px;
  }
  50% {
    --stripes: 40px;
  }
}
```

（デモ内ではこのアニメーション定義部分がデフォルトでコメントアウトされており、コメントを外すとグラデーションのストライプ幅がアニメーションで拡大・縮小し、マスクが呼吸するように動く。）

### ③ なぜそれが効果的か

- 通常、CSSのグラデーション関数（`radial-gradient` など）の引数はカスタムプロパティ経由でも「文字列」として扱われ、ブラウザは値の型を知らないためアニメーション（中間値の補間）ができない。`@property` で `syntax: "<length>"` を明示的に指定することで、ブラウザがカスタムプロパティを「アニメーション可能な長さ型」として認識し、`--stripes` の値がなめらかに補間されるようになる。これが Houdini Properties and Values API の核心的な利点。
- `mask` はアルファマスキング（不透明部分＝表示、透明部分＝非表示）で動作するため、画像だけでなくテキストやどんなDOM要素にも同じ手法を適用できる、汎用性の高いテクニックである。
- 実装はJSを一切使わず、CSSの宣言的な仕組み（グラデーション生成 + カスタムプロパティのアニメーション）だけで完結しており、パフォーマンス面でもブラウザのコンポジタに最適化を任せられる。
- 記事では Firefox と Safari でレンダリングの挙動差があり、試行錯誤が必要だったと述べられており、ブラウザ間の `mask` 実装差異が実務上の注意点として言及されている。

## 3. WebGL without a GPU

**記事タイトル**: WebGL without a GPU
**掲載元**: Microlink Blog
**URL**: [https://microlink.io/blog/webgl-without-a-gpu](https://microlink.io/blog/webgl-without-a-gpu)

### ① 目的・問題意識

Microlink はサーバーサイドで大量のWebページ（three.js などを使った3D/WebGLコンテンツを含む）をスクリーンショット・レンダリングするサービスを提供しているが、多くのクラウドインフラのノードには物理GPUが搭載されていない。GPUなしのLinuxノード上で、Chromium 経由の WebGL レンダリングをいかに高速かつ正確に行うかが課題だった。

- WebGL は本来 GPU を前提とした API であるため、GPUがない環境では何らかの形でCPU上にエミュレートする必要がある
- Chrome のデフォルトのソフトウェアレンダラ（SwiftShader）は動作するが、1ページあたり約24秒（〜31秒）かかり、実運用には遅すぎた

### ② 具体的な技術詳細とコード例

#### 技術構成: ANGLE 経由で Mesa llvmpipe を使う

- ANGLE（Almost Native Graphics Layer Engine）は WebGL 呼び出しを、プラットフォームが持つ実際のグラフィックスバックエンド（Metal、Vulkan、OpenGL、あるいはソフトウェアレンダラ）に変換するレイヤー。GPUがない場合、ANGLE はソフトウェアレンダラに変換先を切り替える。
- Chrome のデフォルト（SwiftShader）の代わりに、`--use-angle=gl` フラグを指定して ANGLE のバックエンドを Mesa の `llvmpipe`（OpenGLのソフトウェア実装）に向ける。

#### Mesa のビルド（llvmpipe のみを有効化）

```
meson setup build \
  -Dbuildtype=release \
  -Dgallium-drivers=llvmpipe \
  -Dvulkan-drivers= \
  -Dllvm=enabled \
  -Dshared-llvm=enabled
```

- `-Dgallium-drivers=llvmpipe` で Gallium ドライバをllvmpipeのみに限定し、`-Dvulkan-drivers=`（空）で Vulkan ドライバをビルド対象から外すことで、余計な依存とビルド時間・イメージサイズを削減する。
- Dockerfile はマルチステージビルドになっており、Mesa をコンパイルするステージと、そのビルド成果物だけをクリーンなベースイメージに `COPY` する最終ステージに分離。これによりイメージサイズが 4.5GB から 2.65GB に削減された。

#### 実行時設定

- Chrome 起動前に `Xvfb`（仮想フレームバッファ）を起動し、ヘッドレス環境でもディスプレイサーバーが存在するようにする。
- 環境変数 `LIBGL_ALWAYS_SOFTWARE=1` を設定して、Mesa がハードウェアGPUドライバを探さず、常に `llvmpipe` を使うように固定する。

#### ベンチマーク結果

| レンダラ | 1ページあたりの処理時間 | 備考 |
|---|---|---|
| SwiftShader（Chromeデフォルト） | 約24〜31秒 | 汎用C++ヘルパーでシェーダ命令をインタプリタ的に解釈し、スレッドプールで並列化するが、各フラグメントは汎用的なCPUコードを通る |
| Mesa llvmpipe（`--use-angle=gl`） | 約6秒 | シェーダソースをLLVMで一度だけJITコンパイルしてネイティブ機械語にし、SIMDベクトル化命令を生成。各CPUコアで複数ピクセルを1サイクルで処理できる |

さらに別データとして、Chromium の ANGLE バックエンドを SwiftShader から Mesa llvmpipe に切り替えることで、1インスタンスあたりのCPU使用率が約999%から約513%に低下（約49%削減）し、WebGL1/WebGL2 の互換性は維持されたという計測結果も紹介されている。

### ③ なぜそれが効果的か

- SwiftShader は「汎用的に動く」ことを優先した実装であり、シェーダ命令をポータブルなC++コードとして都度解釈（インタプリタ的実行）するため、1フラグメントごとに汎用CPUコードのオーバーヘッドがかかる。
- 対して llvmpipe はシェーダソースをLLVM経由でネイティブ機械語に事前コンパイル（JIT）し、さらにSIMD命令によるベクトル化で複数ピクセルを同時処理するため、原理的にCPUの並列演算資源をより効率的に使い切れる。これが約4倍の高速化（24秒→6秒）の技術的な理由。
- Dockerイメージをマルチステージビルド化してビルド成果物のみをコピーする手法は、WebGL固有の技術ではないが、CI/CD環境や大量ノードへのデプロイを前提とするサービスでは、イメージサイズの削減がデプロイ速度・コストに直結するため、実運用上の効果が大きい。

## 4. Where to Find the Colors Your Screen Can't Show You

**記事タイトル**: Where to Find the Colors Your Screen Can't Show You
**著者**: Ryan Moulton
**URL**: [https://moultano.wordpress.com/2026/06/19/where-to-find-the-colors-your-screen-cant-show-you/](https://moultano.wordpress.com/2026/06/19/where-to-find-the-colors-your-screen-cant-show-you/)

（本記事はCSS/JSの実装コードを扱う技術チュートリアルではなく、色空間・ディスプレイの物理的な限界に関するサイエンスライティング記事。フロントエンドで扱う色（`sRGB`, `display-p3` などのCSS色空間）の背景にある理論を解説する内容として、技術詳細を抽出する。）

### ① 目的・問題意識

Web/ディスプレイで標準的に使われる `sRGB` という色空間は、人間の目が知覚できる色のごく一部しか再現できない。なぜ蝶の羽、クジャクの羽、熱帯の入江、晴れた日の落葉樹の森のような自然の色が、画面に映した写真よりもずっと鮮やかに見えるのか、その理由を色彩科学（CIE色度図・スペクトル軌跡）の観点から説明する。

### ② 具体的な技術詳細

#### 色域（ガマット）の考え方

- ディスプレイは赤・緑・青（RGB）の3つの原色を混ぜ合わせることで色を作り出すが、3つの点（原色）を混ぜて作れる色は、その3点を頂点とする三角形の内側の色に限られる。
- CIE 1931 色度図（人間が知覚できる全ての色を表す馬蹄形の領域）の中で、`sRGB` がカバーするのは全体の約35%、Apple製品で2016年以降標準となっている `Display-P3` でも約45%程度に留まる。
- 色度図の外周（スペクトル軌跡＝単一波長の光が作る曲線）は場所によってほぼ直線に近い区間があり、そうした区間では2つの波長を混ぜても曲線の外側（より鮮やかな側）には出られない（2点の平均は常にその2点を結ぶ直線上にあるため）。しかし外周が曲線状に大きくカーブしている領域（特にシアン〜緑周辺）では、複数の波長が混ざることで、単色光では出せないような、色度図の内側だが人間の三色型視覚だけがギリギリ知覚できるような鮮烈な色（例: 緑の葉を透過した光がさらに緑を強調するケースなど）が自然界には存在しうる。

#### 具体例として挙げられているもの

- `sRGB` の外側に色を持つ鳥は約500種、`Display-P3` の外側でも約100種存在する。例としてアマゾン西部に生息するハチドリの一種（オウゴンオトメハチドリ、golden-tailed sapphire）は、体のほぼ全体がスペクトル全域にわたる色を持つとされる。
- 木漏れ日のように、1枚の葉を一度透過した光がもう1枚の緑の葉に当たって反射する場合、その緑色はすでに `sRGB`/`Display-P3` のガマットの外側に出てしまう（「緑より緑」な色になる）という具体例が紹介されている。

### ③ なぜそれが効果的か（記事の意義）

- フロントエンド開発者にとって `color-gamut` メディアクエリや `display-p3` / `rec2020` といったCSSの広色域カラー機能は「なぜ必要なのか」が実感しづらい抽象的な話になりがちだが、本記事は「自然界にはディスプレイの色域外の色が普通に存在する」という具体例（鳥や葉）を提示することで、広色域対応の必要性を直感的に理解させる。
- 色度図における「直線区間では鮮やかさが増えない・曲線区間でこそ混色によって鮮やかさが増しうる」という説明は、なぜ特定の色相（シアンや黄緑）だけがディスプレイで特に不足しがちなのかという、CSS Color 4 の広色域仕様の設計背景を理解する助けになる。

## 5. New in Chrome 150

**記事タイトル**: New in Chrome 150
**掲載元**: Chrome for Developers Blog
**URL**: [https://developer.chrome.com/blog/new-in-chrome-150](https://developer.chrome.com/blog/new-in-chrome-150)

### ① 目的・問題意識

Chrome 150 で追加された、レスポンシブタイポグラフィ、装飾的なグラデーションボーダー、複雑なウィジェットのキーボード操作、OSテーマ統合など、フロントエンド開発者向けの複数の新機能・APIをまとめて紹介する。

### ② 具体的な技術詳細とコード例

#### 5-1. `text-fit` — コンテナ幅にテキストを自動フィットさせる

- 目的: 見出しや動的コンテンツの文字サイズを、手動での `font-size` 計算や複雑なJavaScriptを使わずに、コンテナの横幅いっぱいにフィットさせる。
- 技術詳細: `text-fit` は、テキストノードのフォントサイズをコンテナの幅にぴったり合わせてスケーリングするCSSプロパティ。これまで `clamp(1.8rem, 2.5vw, 2.8rem)` のような `vw` ベースの近似計算（ビューポート幅に対する相対値を最小・最大値の範囲でクランプする手法）で代替されてきたが、`text-fit` はコンテナ自体の実測幅に基づいて厳密にフィットさせられる点で異なる。
- 効果: レスポンシブなタイポグラフィをCSSネイティブに、JSのレイアウト計測やResizeObserverを使わずに実現できる。

#### 5-2. `background-clip: border-area` — CSSネイティブなグラデーションボーダー

目的: これまで `border-image` を使った複雑なワークアラウンドが必要だったグラデーションボーダーを、`background` プロパティだけで実現する。

```css
@supports (background-clip: border-area) {
  figure {
    background-image: linear-gradient(in hsl, #dc9323, #7f416a);
    background-origin: border-box;
    border: 30px solid transparent;
    background-clip: border-area;
    padding: 6px;
  }
}
```

グラデーションテキスト＋グラデーションボーダーを組み合わせる例:

```css
.gradient-text-border {
  border: 10px solid #0000;
  color: #0000;
  background-image: linear-gradient(#FF4E50, #40C0CB);
  background-clip: border-area text;
  background-origin: border-box;
}
```

- 技術詳細: `background-clip: border-area` は、要素の背景を「ボーダーのストローク部分が描画される領域」にクリップする。`border-width` と `border-style` は考慮されるが、`border-color` の透明度は無視される。`border: 30px solid transparent` として実際のボーダー色を透明にしつつ、その領域にだけ背景（グラデーション）を見せることで、グラデーションボーダーを表現する。
- `background-clip: border-area text` のように複数のクリップ領域を指定すると、ボーダー部分とテキスト部分の両方に同じグラデーション背景をクリップできる。
- 効果: `border-image` の複雑なスライス指定なしに、通常の `background` / `border` プロパティの組み合わせだけでグラデーションボーダーが作れるため、実装がシンプルになる。ただしChrome 150時点ではChromeのみの対応のため `@supports` によるプログレッシブエンハンスメントが推奨される。

#### 5-3. `polygon()` の角丸パラメータ

目的: `clip-path: polygon()` で作る多角形の角を丸めるために、これまではベジェ曲線を手計算する必要があったが、それを不要にする。

```css
clip-path: polygon(round 10px, 0 0, 100% 0, 100% 100%, 0 100%);
```

- 技術詳細: `polygon()` 関数に `round <length>` というオプションのパラメータを追加できるようになり、多角形の各頂点に指定した長さ分の丸みを自動的に適用できる。
- 効果: クリッピングやマスキング、シェイプベースのデザインで多角形の角を丸めたい場合に、複雑な座標計算やベジェ曲線の手動計算をせずに済む。

#### 5-4. `focusgroup` 属性 — 複合ウィジェットの宣言的キーボードナビゲーション

目的: ツールバーやタブリストのような複合UIウィジェットにおいて、矢印キーでのフォーカス移動、確実なTabストップの提供、直前にフォーカスしていた項目を記憶する「last-focused memory」を、これまでのような手書きの roving tabindex スクリプト（JSでtabindexを動的に切り替える実装）を使わずに実現する。

```html
<div focusgroup="toolbar wrap" aria-label="Formatting">
  <button>Bold</button>
  <button>Italic</button>
  <button>Underline</button>
</div>
```

- 属性の構文: `focusgroup="<behavior> [inline|block] [wrap] [nomemory]"` — 最初のトークンがウィジェットパターンを宣言する挙動トークン（例: `toolbar`）で、それに続いて `inline`/`block`（ナビゲーション方向の指定）、`wrap`（端まで行ったら反対側の端に戻る）、`nomemory`（フォーカスの記憶を無効化）などの修飾トークンをオプションで付加できる。
- 挙動: `Tab` キーで focusgroup 同士の間を移動し、focusgroup 内部では矢印キーで項目間を移動する。ブラウザが参加要素を自動的に1つのTabストップにまとめてくれるため、開発者は非アクティブな項目に `tabindex="-1"` を手動で設定する必要がない。ユーザーがそのfocusgroupから一度離れて戻ってきた場合、離れる直前にフォーカスしていた項目にフォーカスが復元される。

#### 5-5. `AccentColor` / `AccentColorText` システムカラー

目的: OSでユーザーが設定しているアクセントカラーをCSSから参照し、インストール済みのWebアプリ（PWA）などで、ネイティブアプリのようにOSテーマと統合したスタイリングを実現する。

- 技術詳細: `AccentColor`（背景色）と `AccentColorText`（その上に乗るテキストの色）という2つのCSSシステムカラーキーワードが使えるようになり、ユーザーのデバイスで指定されたシステムのアクセントカラーにアクセスできる。

#### 5-6. PWAのオリジン間シームレス移行

目的: インストール済みのPWAを、同一サイト内の新しいオリジンへユーザーの信頼・権限設定を保持したまま移行できる仕組みを提供する。

#### 5-7. スクロール完了を検知できる Promise

目的: プログラム的なスムーススクロールが完了したタイミングを、確実なシグナルとして取得できるようにする。

- 技術詳細: `Element` と `Window` の各種スクロールメソッドが、スクロール完了時に解決される `Promise` オブジェクトを返すようになった。これにより、スクロールアニメーションの完了を `setTimeout` によるおおよその時間待機や `scrollend` イベントリスナーに頼らず、`await` で直接待ち受けられる。

#### 5-8. その他

- Chrome 150 では433件の脆弱性が修正され、Googleは20件を「重大（Critical）」と評価している。
- DevToolsやChromeのUI自体にも「WebUI Refresh 2026」と呼ばれる視覚的刷新（アイコン再デザイン、ボタンアニメーション更新、コンテキストメニューの簡素化など）が導入されている。

### ③ なぜそれが効果的か

- `text-fit` と `background-clip: border-area` はいずれも「これまでJSやハックが必要だった視覚効果を、宣言的なCSSだけで完結させる」という共通の設計思想に基づいており、実装コストと実行時パフォーマンス（レイアウト計算やDOM測定の削減）の両面でメリットがある。
- `focusgroup` はアクセシビリティ実装の定番パターン（roving tabindexによるARIAコンポジットウィジェット）をブラウザネイティブに引き上げるもので、開発者が手書きしていたキーボードイベントハンドラのバグ（フォーカス管理の抜け漏れなど）を構造的になくせる点が大きい。
- スクロール完了のPromise化は、これまで「スクロールがいつ終わるか正確にはわからない」という非同期処理上の弱点を解消し、スクロール後に何か処理を行うアニメーションやUIロジックを、タイマーに頼らず正確に組めるようにする。
