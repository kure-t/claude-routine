## 1. Beyond the viewport: Introducing Site Seeing（Ahmad Shadeed）— 巻頭記事

- 記事: https://ishadeed.com/article/beyond-the-viewport/ （2026-11-05 公開）
- ツール: https://lab.ishadeed.com/tools/site-seeing/ （Chrome と Safari のみ対応）

### ① 目的・問題意識
レスポンシブデザインのテストは「ブラウザウィンドウの幅を変える」か「デスクトップとモバイルのプリセット幅で見る」になりがちです。しかし実際のユーザーは、次のような**変則的なビューポート**でサイトを見ています。

- DevTools を横や下にドッキングしてビューポートが狭くなった状態
- 縦タブ（vertical tabs）でブラウザ UI が横幅を占有している状態
- 縦タブと DevTools の併用で、さらに狭く縦長になった状態
- スクリーンキーボードが開いて高さが大きく減った状態
- SNS アプリなどのアプリ内ブラウザ（in-app browser）の中途半端なサイズ
- OS のスプリットビュー（画面分割）
- 印刷（print styles）

Shadeed は、こうした状況への配慮は「ビューポートサイズだけを気にすること」より遥かに重要だと主張しています。

### ② 技術詳細
- ブラウザ上で動く無料ツールです。URL を入れて、モード（文脈）を選ぶと、その状況でのページ表示をプレビューします。
- 確認できたモードは次のとおりです。
  - Full browser（通常表示）
  - Vertical tabs（縦タブ）
  - DevTools open（DevTools を開いた状態）
  - Vertical tabs + DevTools（両方の組み合わせ）
  - キーボード表示
  - アプリ内ブラウザ
  - スプリットビュー
  - Print（印刷）
- 対象ユーザーはデザイナー、PM、開発者です。
- RTL（右から左に書く言語）表示は今後対応予定です（Shadeed の LinkedIn での返信より）。
- 内部実装（iframe かどうかなど）は、検索結果からは確認できませんでした。

関連して、こうした変則ビューポートに強いレイアウトを作る CSS の例を挙げます（**再構成例**。記事中のコードではありません）。

```css
/* 高さが減る文脈（キーボード表示・アプリ内ブラウザ）に強い全画面レイアウト */
.app {
  min-height: 100dvh; /* 動的ビューポート単位。ブラウザ UI やキーボードの出入りに追従 */
}

/* 横幅ではなく「コンポーネントが置かれた幅」で切り替える。
   DevTools や縦タブでビューポートが狭くなっても壊れにくい */
.card-list { container-type: inline-size; }
@container (min-width: 40rem) {
  .card { display: grid; grid-template-columns: 12rem 1fr; }
}

/* 低い高さ（横向きスマホ、キーボード表示中）では固定ヘッダーをやめる */
@media (max-height: 30rem) {
  .site-header { position: static; }
}

/* 印刷文脈 */
@media print {
  nav, .ads { display: none; }
  a[href]::after { content: " (" attr(href) ")"; }
}
```

```html
<!-- キーボード表示時にレイアウトビューポートもリサイズさせる指定（Chrome） -->
<meta name="viewport" content="width=device-width, initial-scale=1, interactive-widget=resizes-content">
```

### ③ なぜ効果的か
- 幅だけを変えるテストでは見落とす崩れを、実際の利用文脈ごとにワンクリックで再現できます。例えば、高さが足りずに固定ヘッダーが画面の大半を占める、ブレークポイント境界でナビが崩れる、といったケースです。
- デザイナーや PM も開発環境なしでブラウザから確認できます。そのため、レビューの段階で「変則的な文脈」をチェック項目に組み込めます。

## 2. Modern Web Guidance 1.0 がステーブルに（Chrome / Edge / Firefox / MDN）

- 公式: https://developer.chrome.com/blog/modern-web-guidance-v1 、まとめ記事 https://developer.chrome.com/blog/modern-web-guidance-recap （2026-11-10）
- リポジトリ: https://github.com/GoogleChrome/modern-web-guidance

### ① 目的・問題意識
AI コーディングエージェントは、学習データの影響で古い書き方を出力しがちです。例えば、2019 年頃の JavaScript、JS で書いたモーダルやツールチップ、ブラウザ互換性を無視した API の使用などです。Modern Web Guidance は、**最新の Web プラットフォームの知識・ベストプラクティス・ブラウザ互換性データ（Baseline）をエージェントに「スキル」として注入**して、これを解決します。

### ② 技術詳細
- **中身**: v1.0 には、203 個のユースケース別ガイドが含まれ、250 の Web プラットフォーム機能をカバーします。分野は CSS/レイアウト、JavaScript/API、HTML/DOM です。各ガイドには Baseline 互換性データとフォールバック方法が付いています。
- **体制**: Chrome が作り、現在は Chrome・Microsoft Edge・Mozilla Firefox・MDN の各チームが共同で管理しています。1.0 で Firefox と Edge が正式に参加しました。
- **CLI コマンド**（原文で確認できたもの）:

```bash
# プロジェクトのディレクトリでインストール（エージェント用スキルとして配置）
npx modern-web-guidance@latest install

# 既存ユーザーの更新
npx modern-web-guidance@latest update

# トピックからガイドを検索（オフラインの埋め込みモデル + BM25 で照合。ネットワーク通信なし）
npx modern-web-guidance@latest search "<topic>"

# ID を指定してガイドを取得
npx modern-web-guidance@latest retrieve <guide-id>

# コードベース内のレガシーパターンを検出（1.0 の新機能）
npx modern-web-guidance@latest legacy-scan --json
```

- **Vercel の Agent Skills 経由で入れる方法**: `npx skills add GoogleChrome/modern-web-guidance`。Claude Code などのエージェント向けにはプラグイン形式でも配布されています。
- **legacy-scan の仕組み**:
  1. まずファイルを文字列で絞り込みます（関係しそうな部分文字列を含むファイルだけを候補にする）。
  2. 候補ファイルとルールに対してだけ、AST/CSS/HTML パーサーを起動します（高速化のため）。
  3. 現時点で検出できるのは、決定的なレガシー判定ルールを持つ約 20% のガイド分だけです。そのため「検出ゼロ」でもコードがモダンだとは限りません。
- **モダナイズのワークフロー**: エージェントは scan → verify → report → modernize の 4 段階で動きます。
- **効果（報告値）**: Chrome によると、ガイダンスなしのエージェントはテストスイートのチェック通過率が約 50% で、使用時は約 90% です。別媒体は 61% → 94% と報じており、数値は媒体によって異なります。
- ライセンスは Apache-2.0 と報じられています（サードパーティ情報）。

### ③ なぜ効果的か
- エージェントが「今、主要ブラウザで安全に使える機能か」を Baseline データで判断できるようになります。その結果、モダンな代替手段を選び、必要に応じてフォールバックを付けられます。モダンな代替手段とは、例えば JS 製ツールチップの代わりに Popover API や Anchor Positioning を使うことです。
- 検索はオフラインで完結するので、高速でプライバシー面も安全です。
- ブラウザベンダー 3 社と MDN の共同管理なので、特定ブラウザに偏らない推奨になります。

## 3. Computing with CSS Layout（noscript.ing / Agustin Capeletto と推定）

- 記事: https://noscript.ing/compute （2026-11-05 更新）
- 号の紹介文:「CSS の『計算結果』を数値として読み戻し、実用に使う（アニメーションするグラフの描画を含む）インタラクティブな記事」
- 著者名は検索結果の上で Agustin Capeletto（layoutit.com、CSS Voxel Editor の作者）と近接して表示されていましたが、確証はありません。

### ① 目的・問題意識
CSS の `calc()` などの数学関数は四則演算や三角関数を扱えますが、「並べ替え」「中央値」のような**データ全体に依存する計算**はできません。この記事は、**ブラウザのレイアウトエンジンそのものを計算機として使い**、その結果を数値として読み戻す手法を紹介しています。

### ② 技術詳細（検索スニペットから確認できた要素）
- **値を幅として表現し、レイアウトに計算させる**: 各値を要素の幅やグリッドのトラックとして配置し、レイアウトの結果（列の幅など）を「計算結果」とみなします。
- **クエリコンテナで結果を読み戻す**: `container-type` を指定した要素は、自身の幅を `100cqw` として参照できます。原文には `round(100cqw / 1px)` で長さを単位なしの数値に変換する記述があります（原文）。
- **並べ替えと中央値**: 値を `order` で並べ替え、小さい順にブラウザにレイアウトさせます。ペアごとの比較式は不要です。そのうえで、5 列のうち中央の列の下にクエリコンテナを置き、その列の幅を読むことで中央値を得ます。
- **残りの計算は `calc()` で行う**: レイアウトで得た値に対して、`calc()` で残りの演算を組み合わせます。
- **応用**: 読み戻した数値を使い、アニメーションするグラフを CSS だけで描画します。
- **結論**:「十分な要素数と時間があれば、CSS は何でも計算できる」。
- **ブラウザ対応**: コンテナクエリ単位は Chrome 105 / Safari 16 / Firefox 110 以降で利用できます（Widely available）。

原文のコードブロックは検索結果で崩れていて復元できませんでした。以下は、上記の要素を組み合わせた**説明用の再構成例**です。

```html
<div class="calc">
  <!-- 各値をカスタムプロパティで渡す -->
  <div class="bar" style="--v: 40"></div>
  <div class="bar" style="--v: 10"></div>
  <div class="bar" style="--v: 30"></div>
  <div class="bar" style="--v: 50"></div>
  <div class="bar" style="--v: 20"></div>
  <div class="readout"><span></span></div>
</div>
```

```css
/* (1) レイアウトの結果を数値として読む基本形 */
.readout {
  container-type: inline-size; /* 自分の幅を cq 単位で参照可能にする */
}
.readout span {
  /* 自身の幅(px)を単位なしの整数に変換する（原文にある round(100cqw / 1px) の考え方） */
  --w: round(100cqw / 1px);
}

/* 単位なしの数値は CSS カウンター経由で画面に表示できる */
@property --n { syntax: "<integer>"; inherits: false; initial-value: 0; }
.readout span {
  --n: round(100cqw / 1px);
  counter-reset: n var(--n);
}
.readout span::after { content: counter(n); }

/* (2) 並べ替え: 値そのものを order に使い、レイアウトエンジンに昇順配置させる */
.calc { display: flex; }
.bar {
  order: var(--v);                   /* 比較ロジックなしで小さい順に並ぶ */
  width: calc(var(--v) * 1px);
  height: 1rem;
}
/* 並んだ結果の「3 番目（中央）」の位置に読み取り用コンテナを置けば中央値が読める */
```

### ③ なぜ効果的か
- 並べ替えや最大・最小の選択を、ブラウザのレイアウトアルゴリズムに丸ごと任せられます。そのため、CSS にない手続き的な処理を JS なしで実現できます。
- コンテナクエリ単位で結果を読み戻し、`calc()` と組み合わせれば、計算結果を数値表示やグラフ描画などの見た目に直結させられます。
- JavaScript が無効な環境（記事のサイト名は noscript）でもデータの可視化が動きます。

## 4. System Colors Need to Work Together（Aaron Gustafson）

- 記事: https://www.aaron-gustafson.com/notebook/system-colors-need-to-work-together/
- 調査用リポジトリ: https://github.com/aarongustafson/system-color-study

### ① 目的・問題意識
CSS のシステムカラー（`Canvas`、`CanvasText`、`ButtonFace`、`ButtonText`、`Field`、`FieldText`、`Highlight`、`HighlightText` など）は、OS やユーザー設定に追従する色です。これらは「前景と背景のペアで使えば読める」という前提で使われています。しかし実際には、**ブラウザ・OS・カラースキームによってペアのコントラストが破綻する**ことがあります。

### ② 技術詳細
- **調査方法**: クライアントサイドだけで動く、繰り返し実行可能なスタンドアロンの調査ツールを作りました。ブラウザ・OS・要求するカラースキーム（light/dark）・ユーザー設定（強制カラーなど）ごとに、システムカラーの解決値を記録し、コントラストを測定します。
- コントラストは、デフォルトでは各モードの不透明な `Canvas` を背景として計算します。これはコントラストの計算方法だけに関わる設定で、解決された生の色の値は変わりません。
- 値を単独で見るのではなく、**組み合わせとしての振る舞い**を比較します。
- 検証したペア:
  - `ButtonText` on `ButtonFace`
  - `FieldText` on `Field`
  - `HighlightText` on `Highlight`
- **最悪の結果**: Android の Chrome のダークモードで、`HighlightText` が中間調のグレーになり、`HighlightText` on `Highlight` のコントラスト比が **1.98:1** でした。WCAG のコントラスト基準 5 つすべてを満たしません。
- **主張**: 補完関係にあるシステムカラーは、デフォルトで一緒に機能すべきです。ブラウザ固有のデフォルト値の回避策を、作者に強いるべきではありません。調査で「必ず安全」と保証できるわけではありませんが、どのペアが比較的安全かは分かります。

システムカラーを使う一般的なコード（**再構成例**）:

```css
:root { color-scheme: light dark; }   /* システムカラーをダーク/ライトに追従させる */

body   { background: Canvas;     color: CanvasText; }
button { background: ButtonFace; color: ButtonText; border: 1px solid ButtonBorder; }
input  { background: Field;      color: FieldText; }

/* 選択色はペアで指定する（強制カラーモードでは ::selection が Highlight/HighlightText を使う） */
::selection { background: Highlight; color: HighlightText; }

/* 調査結果を受けた防御策の例: ペアが破綻する環境向けに、自分で保証できる色を使う */
@media (prefers-color-scheme: dark) {
  ::selection { background: #3a6ee8; color: #fff; }
}
@media (forced-colors: active) {
  ::selection { background: Highlight; color: HighlightText; } /* 強制カラーではユーザー設定を尊重 */
}
```

### ③ なぜ効果的か
- 「システムカラーを使えばアクセシブル」という思い込みを、ブラウザ横断の実測データで検証しています。具体的にどの環境のどのペアが危険かを特定できます。
- ブラウザベンダーにとっては修正すべきバグの根拠になります。作者にとっては、ペアの安全度に応じてフォールバックを用意する判断材料になります。

## 5. Blunt Banhammer Blocks Basic Bots Ballistically（Terence Eden）— ボットを締め出す工夫

- 記事: https://shkspr.mobi/blog/2026/11/blunt-banhammer-blocks-basic-bots-ballistically/
- 関連: Dan Q による反論・改良「Re: Blunt Banhammer…」 https://danq.me/2026/11/09/re-blunt-banhammer-blocks-basic-bots-ballistically/ と実運用版 https://danq.me/2026/11/10/geohashing-sites-better-banhammer/

### ① 目的・問題意識
`robots.txt` を無視するスクレイパー（AI クローラーなど）の大量アクセスで、個人サイトが過負荷になっていました。行儀の悪いボットだけを、人間や行儀の良いクローラーに影響を与えずに自動で締め出すことが目的です。

### ② 技術詳細（ハニーポット方式）
1. `robots.txt` で `/honeypot/` ディレクトリを Disallow にします。行儀の良いクローラーはここに来ません。
2. 全ページに、人間には見えない `/honeypot/` へのリンクを置きます。人間はクリックしません。
3. `/honeypot/` にアクセスしてきたクライアントは「robots.txt を無視するボット」とみなします。その IP を `.htaccess` に書き込み、以後ブロックします。

- 結果: 帯域使用量がほぼ 90% 減りました。ただしトレードオフもあると記事は述べています（共有 IP の巻き添え、`.htaccess` の肥大化など）。

原文のコードは取得できませんでした。手順に沿った**再構成例**:

```txt
# robots.txt
User-agent: *
Disallow: /honeypot/
```

```html
<!-- 全ページに埋め込む不可視リンク（支援技術にも読ませない） -->
<a href="/honeypot/" hidden aria-hidden="true" tabindex="-1" rel="nofollow">.</a>
```

```php
<?php
// /honeypot/index.php — アクセスした IP を .htaccess の拒否リストに追記する
$ip = $_SERVER['REMOTE_ADDR'];
if (filter_var($ip, FILTER_VALIDATE_IP)) {
    file_put_contents(__DIR__ . '/../.htaccess', "Require not ip {$ip}\n", FILE_APPEND | LOCK_EX);
}
http_response_code(403);
```

```apache
# .htaccess（Apache 2.4）
<RequireAll>
  Require all granted
  # ↓ ハニーポットが追記していく
  Require not ip 203.0.113.5
</RequireAll>
```

### Dan Q の指摘と改良
- **DoS に悪用できる問題**: 第三者が別のサイトや掲示板にハニーポットのリンクを仕込むと、それを踏んだ一般の訪問者の IP までブロックされてしまいます。
- **改良案**: 署名付きトークンを使います。ハニーポットの URL に、自サイトが発行した署名付きトークンを含めます。正当なトークン付きのアクセスだけをバン対象にすることで、外部に仕込まれたリンク経由の誤バンを防ぎます。
- **実運用版**: `.htaccess` を直接書き換える代わりに、ログを Fail2Ban で監視し、nftables でブロックします。こちらの方が、バンの期限設定や解除の管理がしやすくなります。

### ③ なぜ効果的か
- 判定基準が「robots.txt を無視して、見えないリンクまで辿った」という**行動**なので、User-Agent を偽装するボットにも効きます。
- 人間と、規約を守るクローラー（検索エンジンなど）は理論上ハニーポットに到達しません。そのため誤検知が少なく、実装も数行で済みます。

### 同じ号のボット関連トピック
- **Hugo Attal**: サーバーログを調べると、「人間」の訪問者の約 90% が実はボットでした。クローラーを歓迎しているサイトでも、ボットはアクセス解析の数字を歪めるという指摘です（元記事は検索で特定できませんでした）。
- **Utku Sen**: テストサイトをタブー（AI が拒否しやすい）フレーズで埋めたところ、AI エージェントがそのサイトの処理を拒否しました。コンテンツ側から AI エージェントを遠ざけるという発想です（元記事は検索で特定できませんでした）。

## 6. Run AI Coding Models on Your Own Machine

- 号の紹介文:「ローカルモデルは、日常的なコーディングには十分な性能になった」
- 元記事の URL と著者は検索で特定できませんでした。

### ① 目的・問題意識
クラウドの AI コーディングツールには、コスト、プライバシー（社外にコードを送る）、オフライン時に使えない、といった問題があります。ローカルで動くオープンウェイトモデルで、どこまで代替できるかを扱う記事です。

### ② 技術詳細（周辺情報からの整理）
- Ollama などでローカルにモデルを動かし、Continue や Aider などのエディタ/CLI と接続するのが一般的な構成です。
- 目安として、RAM 32GB 前後があれば快適と言われています。
- 得意な作業: 補完、小さな編集、コードの説明、テストの作成。
- 苦手な作業: 複数ファイルにまたがる大規模リファクタ、エージェント的な長時間タスク。

```bash
# 一般的な例（再構成）
ollama pull qwen2.5-coder:14b
ollama run qwen2.5-coder:14b
# エディタ拡張（Continue 等）の接続先を http://localhost:11434 に設定する
```

### ③ なぜ効果的か
コードが外部に出ず、利用量による課金もかかりません。日常的な定型作業の多くをローカルで済ませ、難しいタスクだけをフロンティアモデルに回す、という使い分けができます。
