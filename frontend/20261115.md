## 1. Next.js 16.4 — Cache Components がすべてのアプリで推奨デフォルトに

**リンク:** https://nextjs.org/blog/next-16-4

### ① 目的・問題意識

Next.js 16.3 で導入された Cache Components は、コンポーネント単位でのキャッシュ戦略を明示的に制御できる機能だったが、デフォルトでは無効だった。16.4 では **Cache Components を全アプリの推奨デフォルト** とし、`create-next-app` で生成される新規プロジェクトは最初から有効化される。次の 17.0 では全アプリのデフォルトになる予定。

### ② 技術詳細・コード

**Cache Components の基本構文:**

```tsx
// app/products/page.tsx
import { unstable_cache } from 'next/cache';

// Cache Component: コンポーネントレベルでキャッシュ境界を定義
export default async function ProductsPage() {
  return (
    <main>
      <StaticHeader />        {/* キャッシュされる静的部分 */}
      <DynamicContent />      {/* リクエスト時に動的に取得 */}
    </main>
  );
}
```

**`navigation()` と `prefetch()` によるプリフェッチ制御:**

```tsx
import { navigation, prefetch } from 'next/cache';

// 高コストなデータをプリフェッチから除外し、ナビゲーション時にのみ取得
export default async function HeavyPage() {
  const data = await navigation(async () => {
    return fetch('/api/expensive-data').then(r => r.json());
  });

  // プリフェッチ対象に明示的に含めるデータ
  const preview = await prefetch(async () => {
    return fetch('/api/preview').then(r => r.json());
  });

  return <div>{/* ... */}</div>;
}
```

**`ensureStatic` — ルートの静的性を強制:**

```tsx
// app/marketing/page.tsx
export const dynamic = 'ensureStatic';
// ビルド時に動的コンテンツが混入した場合、ビルドを失敗させる

export default async function MarketingPage() {
  const content = await getCachedContent(); // 静的なデータのみ許可
  return <div>{content}</div>;
}
```

**Turbopack のオンデマンドコンパイル:** 16.4 では Turbopack がリクエストが発生したときのみサーバー更新をコンパイル・適用するよう改善され、Turbopack のディスクキャッシュが 20〜25% 削減された。

**AI エージェント向けアップグレード支援:**

```bash
npx next@canary upgrade --agent=latest
# バージョン固有の移行ガイド・コードモッド・検証手順を AI エージェント向けに生成
```

**React 19.3 の同梱:** Next.js 16.4 は React 19.3 を同梱し、以下の新機能が stable になった（後述）。

**Rust 製 React Compiler (実験的):**
- メモリ使用量 30% 削減
- コンパイル速度 15% 向上

### ③ なぜ効果的か

Cache Components は「どこをキャッシュするか」をコンポーネントレベルで宣言できるため、ページ全体の静的/動的の二択ではなく、粒度の細かいキャッシュ制御が可能になる。`ensureStatic` によりビルド時に意図しない動的コンテンツの混入を検出でき、`navigation()`/`prefetch()` でプリフェッチコストをコントロールできる。

## 2. React 19.3 — View Transitions と Fragment Refs が Stable に

**リンク:** https://react.dev/blog/2026/09/09/react-19-3

### ① 目的・問題意識

アニメーションを伴う画面遷移のコードは煩雑になりがちで、ブラウザネイティブの View Transition API を直接扱うのは複雑だった。また、DOM ラッパー要素を追加せずに複数の子要素をまとめて参照する方法がなかった。

### ② 技術詳細・コード

**`<ViewTransition>` コンポーネント:**

```tsx
import { ViewTransition } from 'react';

function App() {
  return (
    <ViewTransition>
      {/* このコンポーネントツリーの変化がブラウザのView Transition APIでアニメーションされる */}
      <PageContent key={currentPage} />
    </ViewTransition>
  );
}

// Suspense との統合: 画像・フォントの読み込み待ちでも自然なトランジション
function ImageGallery() {
  return (
    <ViewTransition>
      <Suspense fallback={<Skeleton />}>
        <LazyImage src={imageUrl} />
      </Suspense>
    </ViewTransition>
  );
}
```

**Fragment Refs:**

```tsx
import { Fragment, useRef } from 'react';

function HighlightGroup() {
  const fragmentRef = useRef(null);

  const handleHighlight = () => {
    // fragmentRef.current は FragmentInstance
    // 直接の子 DOM ノード群に対して DOM-like API が使える
    fragmentRef.current?.getBoundingClientRect(); // 全子要素を包む矩形
    fragmentRef.current?.scrollIntoView();
  };

  return (
    <>
      <Fragment ref={fragmentRef}>
        {/* ラッパー要素なしで複数の子を一つの ref で参照 */}
        <p>段落 1</p>
        <p>段落 2</p>
        <span>インライン要素</span>
      </Fragment>
      <button onClick={handleHighlight}>Highlight</button>
    </>
  );
}
```

**`browser()` — クライアントサイド専用コンテンツ:**

```tsx
import { browser } from 'react';

// SSR をオプトアウト: このコンポーネントはブラウザでのみレンダリング
const ClientOnlyMap = browser(() => {
  // window, document, localStorage など、ブラウザAPI を安全に使用できる
  return <MapComponent />;
});
```

### ③ なぜ効果的か

`<ViewTransition>` はブラウザネイティブの CSS View Transition API をラップし、React の宣言的レンダリングモデルと統合することで、複雑な命令型コードを書かずに滑らかな遷移アニメーションを実現する。Fragment Refs は DOM ラッパー要素（余分な `<div>`）を追加せずに複数要素をまとめて操作でき、アクセシビリティとレイアウトへの影響を排除できる。

## 3. A Visual Notation for React's Parent and Owner Trees

**リンク:** https://julesblom.com/writing/react-visual-notation

### ① 目的・問題意識

React のコンポーネント構造を説明する際、テキストコードだけでは「親ツリー（parent tree）」と「オーナーツリー（owner tree）」の違いを直感的に伝えられない。この2つの概念を同時に可視化できる統一された図示記法がなかった。

### ② 技術詳細・コード

**2つのツリーの定義:**

| ツリー | 意味 | React DevTools の表示 |
|--------|------|----------------------|
| **親ツリー (Parent Tree)** | JSX がネストされた結果の構造（要素がどこに存在するか） | デフォルト表示 |
| **オーナーツリー (Owner Tree)** | どのコンポーネントが要素を `render()` したか（誰が作ったか） | オーナービュー |

**図示記法:**

- **インデントツリー**: 親ツリーを表す（DevTools の一般的なビュー）
- **アーク図**: オーナーツリーをオーバーレイで表示（弧で「作成」関係を示す）
- **React.memo**: 塗りつぶし四角形で表示
- **Suspense境界**: 破線の囲みで表示
- **Context**: プロバイダーからコンシューマーへの矢印
- **RSC (React Server Component)**: サーバー側コンポーネントを区別するマーク

**具体的なシナリオ:**

```tsx
// 親ツリーと所有者ツリーが異なる例
function Layout({ children }) {
  return <div className="layout">{children}</div>;
}

function App() {
  return (
    <Layout>
      {/* <Layout> が親だが、<Button> を render() したのは <App> (owner) */}
      <Button />
    </Layout>
  );
}
```

この場合:
- **親ツリー**: `App > Layout > Button`
- **オーナーツリー**: `App` が `Button` を所有（`Layout` はスルー）

**npm パッケージ:** `react-parent-owner-trees` として公開済み。React 19 アプリの開発時に追加すると、ライブでツリーを描画できる。

**React Trees Playground:** コードを貼り付けると、即座に親・オーナーツリーを図示するツール。

### ③ なぜ効果的か

React Compiler はキャッシュをオーナーツリー単位で管理するため、オーナーの概念を理解することでパフォーマンス最適化の判断が正確になる。Context は親ツリーに沿って伝播し、props はオーナーツリーに沿って流れるため、この2つを同時に可視化することで複雑なデータフローのデバッグが容易になる。

## 4. TanStack Charts 1.0

**リンク:** https://tanstack.com/blog/tanstack-charts-1-0

### ① 目的・問題意識

既存のチャートライブラリは大きく2系統に分かれていた。(a) 高レベルで使いやすいが柔軟性が低いもの (b) D3 のように柔軟だが学習コストが高いもの。TanStack Charts は「小さく始めて大きく育てられる」グラフィックス文法ベースのライブラリを目指した。

### ② 技術詳細・コード

**基本的な折れ線グラフ:**

```tsx
import { Chart, Line, XAxis, YAxis } from '@tanstack/react-charts';

const data = [
  { date: '2026-01', value: 420 },
  { date: '2026-02', value: 380 },
  { date: '2026-03', value: 510 },
];

function MyChart() {
  return (
    <Chart>
      <XAxis dataKey="date" />
      <YAxis dataKey="value" />
      <Line dataKey="value" data={data} />
    </Chart>
  );
}
```

**複合チャート（マーク合成）:**

```tsx
import { Chart, Line, Bar, XAxis, YAxis, Tooltip } from '@tanstack/react-charts';

function ComposedChart() {
  return (
    <Chart>
      <XAxis dataKey="month" />
      <YAxis />
      {/* ライン と バーを合成 */}
      <Bar dataKey="revenue" data={revenueData} />
      <Line dataKey="target" data={targetData} />
      <Tooltip />
    </Chart>
  );
}
```

**Canvas レンダラーへの切り替え（大量データ向け）:**

```tsx
// デフォルトは SVG、Canvas は明示的インポートでオプトイン
import { CanvasRenderer } from '@tanstack/react-charts/canvas';

function HighPerformanceChart() {
  return (
    <Chart renderer={CanvasRenderer}>
      <Line dataKey="price" data={millionRows} />
    </Chart>
  );
}
```

**主な特徴:**
- **フレームワーク非依存**: React / Vue / Angular / Solid 対応
- **TypeScript ファースト**: strict モードで無効な定義はビルド時にエラー
- **バンドルサイズ**: 約 43〜50 kB (gzip、SVG レンダラー込み)。Canvas・モーションは未使用ならバンドルに含まれない
- **Angular**: Angular Core + Platform-browser 19 以降が必要
- **安定 API**: 1.0 でドキュメント化されたパブリック API は互換性保証

### ③ なぜ効果的か

グラフィックス文法（Grammar of Graphics）ベースの設計により、ラインやバー・ポイントなどの「マーク」を組み合わせることで複合チャートを宣言的に構築できる。SVG/Canvas の切り替えも API を変えずに実現でき、小〜大規模のユースケースに対応できる。

## 5. React Compiler と Context セレクター — context を安価にする

**リンク:** https://reactdigest.net/newsletters/2385-making-context-cheap-with-react-compiler

### ① 目的・問題意識

React の Context はプロバイダーの値が変わると**すべてのコンシューマーが再レンダリング**される。これを避けるために `use-context-selector` などのライブラリが使われてきたが、React Compiler がこの問題を緩和できるか検証した記事。

### ② 技術詳細・コード

**問題のあるパターン（Compiler なし）:**

```tsx
// Context 値が変わるたびに ButtonGroup も再レンダリングされる
const ThemeContext = createContext({ color: 'blue', size: 'md' });

function ButtonGroup() {
  const { color } = useContext(ThemeContext); // size は不要だが変わると再レンダリング
  return <Button color={color} />;
}
```

**React Compiler が解決するパターン:**

```tsx
// Compiler が自動で JSX 要素をメモ化
// ThemeContext.size が変化しても、color が変わらなければ Button は再レンダリングされない
function ButtonGroup() {
  const { color } = useContext(ThemeContext);
  // Compiler が `<Button color={color} />` の元となる JSX を記憶し
  // color が同じなら同一の element オブジェクトを返す → React がスキップ
  return <Button color={color} />;
}
```

**Compiler で解決しないパターン（コンテキスト全体が変わる場合）:**

```tsx
// プロバイダーで毎回新しいオブジェクトを作ると Compiler も助けられない
function ThemeProvider({ children }) {
  const [color, setColor] = useState('blue');
  const [size, setSize] = useState('md');

  // NG: size が変わると color が変わってなくても新しいオブジェクト参照
  const value = { color, size };

  return <ThemeContext.Provider value={value}>{children}</ThemeContext.Provider>;
}
```

**推奨パターン（Context 分割 + Compiler）:**

```tsx
// Context を分割してコンパイラと組み合わせる
const ColorContext = createContext('blue');
const SizeContext = createContext('md');

function ButtonGroup() {
  const color = useContext(ColorContext); // size 変化で再レンダリングされない
  return <Button color={color} />;
}
```

**選択肢のまとめ:**

| アプローチ | 適した場面 |
|-----------|-----------|
| Context 分割 + Compiler | 多くのアプリで十分 |
| `use-context-selector` | 多数のコンシューマー + 細かいスライス |
| Zustand / Jotai | セレクター要件が複雑化した場合 |

### ③ なぜ効果的か

React Compiler は JSX 要素オブジェクトをメモ化するため、context の値参照が変わっても **コンポーネントが受け取る props が同じなら子コンポーネントをスキップ**できる。ただし、コンテキスト値自体（プロバイダーの `value` prop）が新しい参照になると Compiler は介入できないため、Context の設計（分割・useMemo によるオブジェクト固定）は依然として重要。

## 6. Coinbase が React Native を離れ Swift/Kotlin へ移行

**リンク:** https://itnext.io/

### ① 目的・問題意識

Coinbase は 2019年から React Native を採用し、2021年に iOS/Android アプリをネイティブから React Native へ移行を完了させた。しかし約5年後の 2026年10月、ネイティブ（Swift / Kotlin）への再移行を発表した。

### ② 内容詳細

- **移行方針**: コンシューマー向けトレーディングアプリを Swift（iOS）と Kotlin（Android）で完全に再構築
- **移行期間中の対応**: React Native アプリを引き続き維持しながら、Swift/Kotlin 版を並行開発するためのエンジニア費用を確保
- **背景となった課題**: 5年間の React Native 採用で得た知見として、パフォーマンス・ネイティブ機能アクセス・プラットフォーム固有の最適化に限界があったと推測される

### ③ なぜ注目か

Coinbase は React Native 採用の先行事例として広く知られており、その撤退はエコシステムへの影響が大きい。一方で、このケースはアプリの規模・複雑さ・ネイティブ機能要件によっては React Native が最適解でなくなるケースを示す事例となっている。

## 7. Redux Toolkit 2.13

**リンク:** https://github.com/reduxjs/redux-toolkit/releases

### ① 目的・問題意識

Redux Toolkit は Redux の公式推奨スターターキットとして継続的にメンテナンスされている。2.13 は 2.14 に向けた安定化リリース。

### ② 技術詳細

Redux Toolkit 2.13 は安定版リリース。直近の変更点として:

- **2.12 での変更 (参考)**: TypeScript のネイティブ `NoInfer` ユーティリティ型への移行（破壊的変更）

```typescript
// 2.12 以降: TypeScript 組み込みの NoInfer を使用
import { createSlice, PayloadAction } from '@reduxjs/toolkit';

interface CounterState {
  value: number;
}

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 } as CounterState,
  reducers: {
    increment: (state) => { state.value += 1; },
    addAmount: (state, action: PayloadAction<number>) => {
      state.value += action.payload;
    },
  },
});

export const { increment, addAmount } = counterSlice.actions;
```

- **2.14 のロードマップ公開**: Redux Toolkit 3.0 に向けた計画を発表
  - 2.x 系での追加作業内容
  - 3.0 の破壊的変更の予告
  - RTK Query の `RootState` 型を `ApiRootState` に非推奨化

### ③ なぜ効果的か

RTK は Redux の冗長なボイラープレートを大幅に削減し、`createSlice` による直感的なステート管理を提供する。3.0 に向けたロードマップの公開は、移行計画を事前に立てやすくするプロジェクト側の配慮。

## 8. React プロジェクトのフォルダ構造 — 2026年版ガイド

**リンク:** (複数の記事を総合)

### ① 目的・問題意識

React はフォルダ構造を規定しないため、プロジェクトが大きくなるほど設計の判断が重要になる。2026年の推奨事項はどう変化したか。

### ② 推奨構造・技術詳細

**基本的なフィーチャーベース構造:**

```
src/
├── features/              # 機能ドメイン単位でモジュール化
│   ├── auth/
│   │   ├── components/    # auth 関連コンポーネント
│   │   ├── hooks/         # auth 関連カスタムフック
│   │   ├── stores/        # auth の状態管理 (Zustand slice など)
│   │   ├── api/           # auth 関連 API 呼び出し
│   │   └── index.ts       # パブリック API (barrel export)
│   └── products/
│       ├── components/
│       ├── hooks/
│       └── index.ts
├── shared/                # 横断的な共有モジュール
│   ├── components/        # 汎用 UI コンポーネント
│   ├── hooks/             # 共通フック
│   └── utils/
├── pages/ (または app/)   # ルートコンポーネント
└── lib/                   # 外部ライブラリのラッパー
```

**2026年時点での主な推奨事項:**

1. **サーバー状態とクライアント状態を分離**
   ```tsx
   // サーバー状態: TanStack Query
   const { data: products } = useQuery({ queryKey: ['products'], queryFn: fetchProducts });

   // クライアント状態: Zustand (2026年の最人気ライブラリ)
   const count = useCartStore((state) => state.count);
   ```

2. **テストの配置**: 小規模プロジェクトはコロケーション（同ディレクトリ）、大規模チームは `__tests__` ディレクトリを分離

3. **バレルエクスポートを適切に使用**
   ```typescript
   // features/auth/index.ts
   export { LoginForm } from './components/LoginForm';
   export { useAuthStore } from './stores/authStore';
   export type { AuthUser } from './types';
   ```

### ③ なぜ効果的か

フィーチャーベースの構造は「凝集性の高いモジュール」を実現し、変更が一機能に局所化されるためチームでの並行開発がしやすい。バレルエクスポートにより、機能内部の詳細をカプセル化しつつ明確なパブリック API を維持できる。
