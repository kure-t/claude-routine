## 1. Pete Hunt、Vercel に入社し Next.js をリード

**記事:** [Vercel hires React's Pete Hunt and GraphQL's Nick Schrock](https://digg.com/tech/7xkbdhn4)  
**関連ポスト:**
- [Guillermo Rauch on X](https://x.com/rauchg/status/2077870043833229692)
- [Pete Hunt on X](https://x.com/floydophone/status/2077871722003636712)

### ① 目的・問題意識

Vercel が React エコシステムの重鎮 2 人を採用したことで、Next.js の今後の方向性に大きな注目が集まった。

- **Pete Hunt**（@floydophone）: Meta 社で React の初期開発に関わったエンジニア。Instagram Web を React で構築するという社内での「早期のベット」をリードし、React の社内外への普及を推進した人物。
- **Nick Schrock**（@schrockn）: GraphQL の共同発明者。API レイヤーの設計に多大な功績を持つ。

これまで Next.js は Vercel エンジニアリングチームが主導してきたが、より React コミュニティに根ざした視点からのリーダーシップが求められるタイミングだった。

### ② 具体的な役割・技術詳細

**Pete Hunt の役割:**
> "very excited to be leading web frameworks (incl @nextjs) at @vercel! let me know in the comments what your favorite and least favorite things about nextjs are"
> — Pete Hunt

Pete Hunt は Vercel で「Frameworks」部門を率い、Next.js のリードを担う。Vercel CEO の Guillermo Rauch は以下のようにコメントしている：

> "Pete was one of the pioneers of @reactjs at Meta. He made an early bet to power Instagram Web with ⚛️ React, evangelizing it internally and externally. He will be running Frameworks and leading @nextjs. I couldn't imagine a better person to lead React's most popular framework to even greater heights."

**Nick Schrock の役割:**
Nick Schrock は「Agentic Developer Experience（エージェント型開発者体験）」を担当する。AI コーディングエージェントが Next.js を活用するためのツールや体験の設計が主なフォーカスとなる。

### ③ なぜ効果的か

- Pete Hunt は React のルーツを熟知しており、React コミュニティとの信頼関係が厚い。Next.js に対するコミュニティからの批判（複雑すぎる、Vercel 利益優先など）に対して、オープンな対話を進める姿勢が期待されている。
- Nick Schrock の参加は、AI エージェントが開発ワークフローに組み込まれる時代に向けた Vercel の本気度を示す。
- このダブル採用は「Next.js が React コミュニティの声を真摯に受け止める」という強いシグナルとなっている。

## 2. shadcn/typeset — HTML タイポグラフィを 1 つの CSS ファイルで統一

**記事:** [July 2026 - Introducing shadcn/typeset - shadcn/ui](https://ui.shadcn.com/docs/changelog/2026-07-typeset)  
**ドキュメント:** [Typeset - shadcn/ui](https://ui.shadcn.com/docs/typeset)  
**比較記事:** [shadcn/typeset vs Tailwind Typography: Styling Markdown](https://dev.to/morellodev/shadcntypeset-vs-tailwind-typography-styling-markdown-c82)

### ① 目的・問題意識

マークダウンをレンダリングすると、スタイルのない生の HTML が返ってくる。見出し・段落・リスト・テーブル・コードブロック、それぞれを個別にスタイリングしなければならない。

> 「ブログでやる。ドキュメントでまたやる。チャットでまた繰り返す。毎回、同じ問題と戦っている：サイズとスペーシング。」

shadcn が作成した `typeset.css` はこの問題を解決する：**1 つの CSS ファイルで `typeset` コンテナ内のすべての要素をスタイリングする**。

### ② 具体的なコード・技術詳細

**基本使用法:**

```html
<!-- typeset クラスを追加するだけで HTML 全体がスタイリングされる -->
<article class="typeset">
  <h1>タイトル</h1>
  <p>本文テキスト。見出し、段落、リスト、テーブル、コードが統一スタイルで表示される。</p>
  <ul>
    <li>リストアイテム</li>
  </ul>
  <pre><code>const x = 1;</code></pre>
</article>
```

**3 つのコントロール（CSS カスタムプロパティ）:**

| プロパティ | 意味 | 例 |
|---|---|---|
| `--typeset-size` | ベースフォントサイズ | `15px`, `16px` |
| `--typeset-leading` | 行の高さ（line-height） | `1.6`, `1.75` |
| `--typeset-flow` | 要素間の垂直スペース | `1em`, `1.5em` |

**コンテキストごとのチューニング例:**

```css
/* チャット用：タイトなリズム */
.typeset-chat {
  --typeset-leading: 1.6;
  --typeset-flow: 1em;
}

/* ドキュメント用：余裕のあるリズム */
.typeset-docs {
  --typeset-size: 15px;
  --typeset-leading: 1.75;
  --typeset-flow: 1.5em;
}
```

```jsx
// React での使用例
<div className="typeset typeset-chat">{chatMessage}</div>
<article className="typeset typeset-docs">{documentContent}</article>
```

**設計の特徴:**
- `typeset` はコンテナのサイズに追従する（コンテナクエリベース）
- `:last-child`, `:has()`, `:empty` などの前向きセレクタを意図的に排除 → **ストリーミングコンテンツ（AI チャット等）でレイアウトが崩れない**
- プロジェクトにコピーして直接編集できる「自分のファイル」という哲学（shadcn/ui の "own it" の精神）

**Tailwind Typography（`@tailwindcss/typography`）との違い:**

| | shadcn/typeset | Tailwind Typography |
|---|---|---|
| 哲学 | 自分のファイルとして所有・編集 | 依存関係として設定で制御 |
| ストリーミング対応 | ○（前向きセレクタなし） | △ |
| テーマ連携 | shadcn テーマを自動使用 | 独立したカラーシステム |
| カスタマイズ | CSS を直接編集 | config でオプション指定 |

### ③ なぜ効果的か

- **ゼロ依存・ゼロ設定の起点**: CSS ファイル 1 枚をコピーするだけで、全コンテキストのタイポグラフィが統一される。
- **ストリーミング UI への最適化**: AI チャットのように逐次的に DOM が構築されるケースで、スタイルが途中で崩れない設計。
- **shadcn テーマと自動統合**: カラースキーム（ダーク/ライト）、フォント設定が typeset に自動反映される。
- **自由な編集**: `.prose` のように「設定で制御する依存関係」ではなく、「コードとして所有するスタートポイント」として提供されており、不要なルールを削除可能。

## 3. shadcn/ui: React Aria が第一級コンポーネントベースに

**記事:** [July 2026 - React Aria - shadcn/ui](https://ui.shadcn.com/docs/changelog/2026-07-react-aria)

### ① 目的・問題意識

shadcn/ui はこれまで Radix UI と Base UI の 2 つのヘッドレスライブラリをコンポーネントベースとしてサポートしていた。しかし、Adobe の React Aria はアクセシビリティに特化した強力なヘッドレスライブラリとして、コミュニティから長年の採用要望があった。

React Aria は特に：
- アクセシビリティ（ARIA 属性、キーボード操作）が非常に堅牢
- テーブル、DatePicker、ComboBox など複雑なコンポーネントの実装が充実
- Adobe のプロダクションアプリで実績のある設計

### ② 具体的なコード・技術詳細

**プロジェクト初期化（React Aria ベース）:**

```bash
# shadcn/create で React Aria を選択
npx shadcn create --base aria

# または既存プロジェクトに追加
npx shadcn init --base aria
```

**コンポーネントのインストール:**

```bash
npx shadcn add button       # React Aria ベースのボタン
npx shadcn add datepicker   # React Aria の DatePicker
npx shadcn add combobox     # React Aria の ComboBox
```

**React Aria コンポーネントの使用例:**

```tsx
import { Button } from "@/components/ui/button";
import { DatePicker } from "@/components/ui/datepicker";

export function Example() {
  return (
    <div>
      <Button>アクセシブルなボタン</Button>
      <DatePicker label="日付を選択" />
    </div>
  );
}
```

**対応スタイル:**
React Aria は shadcn の 8 つのスタイル（Vega, Nova, Maia, Lyra, Mira, Luma, Rhea, Sera）すべてに対応。

**既存プロジェクトへの影響:**
- Base UI・Radix UI を使用している既存のコンポーネントは変更なし
- React Aria 固有の依存関係は `aria` レジストリにスコープされる
- 3 つのベース（Base UI, Radix, React Aria）が CLI で並立してサポートされる

### ③ なぜ効果的か

- **アクセシビリティへの強化**: WCAG 準拠が必要なエンタープライズアプリや行政・教育系アプリに、shadcn/ui のデザインシステムをそのまま使える。
- **複雑なコンポーネントの充実**: DatePicker、Calendar、ComboBox など、Radix や Base UI では難しいコンポーネントが React Aria には豊富に揃っている。
- **選択の自由**: プロジェクトの要件に応じてヘッドレスライブラリを選べる。「デザインシステムは shadcn/ui で統一しつつ、特定ページだけ React Aria」も可能。

## 4. shadcn/ui: Base UI がデフォルト化（Radix から切り替え）

**記事:** [July 2026 - Base UI as the Default - shadcn/ui](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)

### ① 目的・問題意識

shadcn/ui はもともと Radix UI をデフォルトのヘッドレスライブラリとして採用していた。しかし、Radix UI の開発元が MUI に買収された後、同じチームが新たに開発した Base UI が登場し、コミュニティはすでに Base UI へのシフトを始めていた。

shadcn チームは実際のデータから判断した：
> 「shadcn/create で作成されたプロジェクトのうち、Base UI と Radix UI の選択比率はすでに 2:1 で Base UI が多かった。コミュニティはもう判断を下していた。」

### ② 具体的なコード・技術詳細

**新しいプロジェクト作成（デフォルトが Base UI）:**

```bash
# デフォルトで Base UI が選択される
npx shadcn init

# Radix を明示的に指定したい場合
npx shadcn init -b radix
```

**既存プロジェクトへの影響:**

```bash
# 既存の Radix ベースのプロジェクトは変更不要
# CI/CD スクリプトで非対話的に init していた場合は -b radix を追加
npx shadcn init -b radix  # 従来と同じ動作
```

**Base UI と Radix UI の比較:**

| | Base UI | Radix UI |
|---|---|---|
| 開発元 | MUI（旧 Radix チーム） | MUI（Radix から移行） |
| 設計思想 | スタイルなしの行動ロジック | スタイルなしの行動ロジック |
| アップデート頻度 | 活発 | 維持管理のみ |
| TypeScript | フルサポート | サポート |
| 非推奨化 | なし（shadcn は引き続き両方サポート） | - |

### ③ なぜ効果的か

- **コミュニティの現実に追従**: コミュニティの選択を公式化することで、新規ユーザーが悩む必要がなくなる。
- **Base UI の積極開発**: Base UI は Radix UI より活発に開発されており、最新の React パターン対応が速い。
- **後方互換性の維持**: Radix は非推奨にならず、既存プロジェクトへの影響ゼロで移行ができる。

## 5. React チームが Working Groups 体制に再編

**参考:** [Meet the Team – React](https://react.dev/community/team) / [React Working Group · GitHub](https://github.com/reactwg)

### ① 目的・問題意識

2026年2月に React は Meta の所有から離れ、Linux Foundation の傘下に設立された「React Foundation」に移管された（[The React Foundation: A New Home for React](https://react.dev/blog/2026/02/24/the-react-foundation)）。この組織変更に伴い、React のチーム体制とガバナンスが刷新された。

従来のフラットなコアチームから、各専門領域を担当する Working Groups 体制に移行することで、大規模なオープンソースプロジェクトにふさわしい透明性とスケーラビリティを確保する。

### ② 具体的なコード・技術詳細

**Working Groups の構成:**

| Working Group | 担当領域 |
|---|---|
| **Server** | React Server Components、サーバー関連機能 |
| **DOM** | ブラウザ DOM との統合、DOM 固有 API |
| **Fiber** | React の内部スケジューラ・コアレンダラ |
| **Docs & Community** | ドキュメント、コミュニティ運営 |
| **Compiler** | React Compiler（旧 React Forget） |
| **DevX** | 開発者体験、ツール、CLI |
| **React Native** | React Native のコア部分 |

**ガバナンス構造:**
- 各 Working Group が **Leadership Council** に 1 名の代表を送る
- Leadership Council がプロジェクト全体の方向性を調整
- react.dev/community/team ページが刷新され、各メンバーの Working Group への所属がバッジで表示されるようになった

**技術的ガバナンスの独立性:**
> 「React の技術的ガバナンスは常に React Foundation の理事会から独立している。React の技術的方向性は引き続き、React に貢献しメンテナンスする人々によって決定される。」

### ③ なぜ効果的か

- **透明性**: 誰がどの領域を担当しているかが明確になり、コミュニティからの Issue や PR が適切な担当者に届きやすくなる。
- **スケーラビリティ**: Meta 外からのコントリビューターが Working Group に参加しやすくなり、React のオープンソース化が進む。
- **Foundation 独立性**: 特定企業（Meta, Vercel など）の利益に左右されない技術ガバナンスが明示された。

## 6. Kent C. Dodds: フレームワーク戦争は終わった

**動画:** [The Framework wars are over. Why no one dethroned React - YouTube](https://www.youtube.com/watch?v=mxRjJPoWBE4)  
**関連:** [React Never Got Dethroned | Kent C. Dodds - LinkedIn](https://www.linkedin.com/posts/kentcdodds_every-few-years-someone-declares-the-framework-activity-7481036036798689280-IyIj)

### ① 目的・問題意識

数年おきに「React を倒すフレームワーク」が話題になる。Vue、Angular、Svelte、Solid、Qwik、Astro... しかし React は依然として支配的地位を保ち続けている。なぜ React は倒れなかったのか？

Kent C. Dodds がこの問いに Jobs Theory（仕事理論）、ネットワーク効果、フレームワーク選択の意味という観点から答えた。

### ② 具体的な内容・技術詳細

**React Conf 2026 での発言:**
> 「新しいプロジェクトを始めるなら、間違いはありません。すべてのフレームワークは素晴らしい。React はいまや私たちのためにずっと多くのことをしています。フレームワークは本当に収束しており、非常に似てきています。」

**React が倒れなかった理由（動画の内容）:**

1. **Jobs Theory（仕事理論）の適用**
   - React はただの「ビューライブラリ」ではなく、「複雑な UI を組織で構築する」という "Job to be done" に最適化されている
   - 競合フレームワークは技術的に優れていても、この「仕事」を同等にこなせる生態系を持っていない

2. **ネットワーク効果**
   - コンポーネントライブラリ、スタイリングシステム、フォームライブラリ、状態管理...React エコシステムは圧倒的に豊富
   - 採用できる開発者プールの大きさ、Stack Overflow の回答数、OSS の選択肢

3. **フレームワークの収束**
   - Solid、Qwik、Vue、Svelte はすべて React の概念（コンポーネント、リアクティビティ、サーバーレンダリング）を採用している
   - 「React と戦う」のではなく「React から学ぶ」方向に各フレームワークが進化した

4. **React 自体の進化**
   - React Server Components、React Compiler、Suspense など、競合の強みを React 自身が取り込んできた

**「フレームワーク戦争は終わった」の意味:**
- これはどれか 1 つのフレームワークが「勝利した」という宣言ではなく、**成熟した技術選択の時代に入った**ことを意味する
- ユースケースに応じて複数のフレームワークが共存しており、それぞれに適した場所がある

### ③ なぜ効果的か

- **エンジニアの意思決定の参考**: 「React を使い続けるべきか」という問いに対して、感情論ではなく構造的な分析を提供する。
- **フレームワーク選択の脱宗教化**: 技術選択をポジション争いではなく、プロジェクトの要件・チームの能力・エコシステムの成熟度で判断する視点を与える。
- **2026 年時点のリアル**: React 19、React Compiler、RSC が揃った現在、React の技術的な弱点は大幅に減少しており、「React vs X」の議論は以前より意味をなさなくなっている。

## 7. ReactBench — コーディングエージェントの React 評価ベンチマーク

**GitHub:** [millionco/reactbench](https://github.com/millionco/reactbench)  
**公式サイト:** [ReactBench](https://www.reactbench.com/blog)  
**Leaderboard:** [BenchLM.ai - ReactBench](https://benchlm.ai/benchmarks/reactBench)

### ① 目的・問題意識

> 「今日のベンチマークですべてのテストをパスできるモデルが、実際のプロダクション React コードでは失敗するコードを書く」

現行の AI コーディングエージェントのベンチマーク（SWE-bench 等）は、コードが「動作するか」は評価するが、**React 特有の品質問題**（不要な再レンダリング、壊れた Effect、アクセシビリティの欠如）は見逃す。

ReactBench は Million.js チーム（React Scan、React Doctor、Million.js の開発元）が作成したベンチマークで、**プロダクション水準の React コードをエージェントが書けるか**を評価する。

### ② 具体的なコード・技術詳細

**評価の仕組み:**

```
タスク入力（instruction prompt）
    ↓
エージェントが React コードを実装
    ↓
[1] 非公開の行動テスト（behavioral tests）でパスチェック
[2] React Doctor スキャン → 新たな問題が増えていないかチェック
    ↓
スコアリング: パス = 1, 失敗 = 0 のバイナリ評価
```

**2 種類のタスク:**

| タスク種別 | 内容 |
|---|---|
| **Write React** | 50 以上の OSS リポジトリから実際にマージされた PR を元に、機能実装・バグ修正を行う |
| **Fix React** | 既存の React の問題を特定・リファクタリングし、新たな問題を増やさない |

**評価基準（React Doctor スキャンが検出する問題）:**
- 不要な再レンダリング（unnecessary renders）
- 壊れた Effects（broken effects）
- アクセシビリティの問題（accessibility issues）
- コード品質の問題（maintainability issues）

**テスト環境:**
- Harbor フレームワーク（エージェントとベリファイアを別々のサンドボックスコンテナで実行）
- Playwright + Chromium によるエンドツーエンド検証（実際のブラウザで動作確認）
- エージェントは非公開テスト・参照ソリューション・外部ネットワークにアクセス不可（クリーンルーム条件）

**ベンチマーク規模:**
- 51 タスク、60 のエフォートバリアント
- 50 以上の OSS React リポジトリを対象

**2026 年時点のリーダーボード（主要モデル比較）:**

| モデル | スコア | コスト効率 |
|---|---|---|
| GPT 5.6 | トップ | 6× コスト効率（Fable 5 比） |
| Fable 5 | 上位 | コスト高 |
| その他 | - | - |

**使用技術背景（Million.js チームの実績）:**
- React Doctor: 13,800 スター（GitHub, PayPal, Rippling, Airbnb で採用）
- React Scan: 21,600 スター
- Million.js: 17,700 スター

### ③ なぜ効果的か

- **プロダクションレベルの評価**: 動作するだけでなく、「React らしい質の高いコード」を書けるかを評価する。SWE-bench などの汎用ベンチマークが見落とすReact特有の問題を捉える。
- **実際の OSS コードベース**: 合成タスクではなく、実際にマージされた PR を基にしているため、現実の開発に近い評価ができる。
- **エージェント選択の根拠に**: React プロジェクトで AI コーディングエージェントを採用する際に、どのモデルが最も適しているか判断する実用的な指標となる。
- **Chromium での実際の動作検証**: テストパスだけでなく、実ブラウザでのレンダリングと動作を確認するため、UI の問題も検出できる。
