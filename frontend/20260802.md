## 1. Edge が CSS mixins（`@mixin` / `@apply`）に対応開始

**関連URL**: [https://learn.microsoft.com/en-us/microsoft-edge/web-platform/release-notes/150](https://learn.microsoft.com/en-us/microsoft-edge/web-platform/release-notes/150)（Microsoft Edge 150 Web platform release notes, 2026年7月）

### ① 目的・問題意識

これまで CSS で「同じスタイルの塊を複数のセレクタで使い回す」には、Sass などのプリプロセッサの `@mixin` / `@include` に頼るしかなかった。ビルドステップなしでは共通化ができず、以下のような問題があった。

- プリプロセッサ導入によるビルド環境の複雑化
- ネイティブ CSS だけでは「引数付きの再利用可能なスタイル定義」ができない
- カスタムプロパティ（CSS変数）だけでは値の再利用はできても、プロパティの組み合わせ（複数の宣言セット）は再利用できない

CSS Working Group で標準化が進む **CSS Functions and Mixins Module** は、これをネイティブ CSS だけで解決しようとする仕様であり、Chrome/Edge（Chromium系）が実験的対応を進め、2026年に入り Chrome Canary から段階的に安定版へ展開されている。Microsoft Edge もこの流れに追随し、Chromium ベースの実装を通じて `@mixin` / `@apply` のサポートに着手した。

### ② 具体的なコード・技術詳細

Sass ライクな記法だが、ネイティブ CSS のアットルールとして定義する。

**基本形（引数なし）**

```css
@mixin --center {
  display: flex;
  align-items: center;
  justify-content: center;
}

.card {
  @apply --center;
}
```

**スクリーンリーダー専用テキストのユーティリティ例**

```css
@mixin --sr-text {
  position: absolute;
  left: -10000px;
  top: auto;
  width: 1px;
  height: 1px;
  overflow: hidden;
}

header a:first-child {
  @apply --sr-text;
}
```

**引数（パラメータ）付き mixin — 型指定 `type()` を使ったグラデーション定義**

```css
@mixin --gradient-linear(
  --color-1 type(<color>),
  --color-2 type(<color>),
  --angle type(<angle>)
) {
  background: linear-gradient(var(--angle), var(--color-1), var(--color-2));
}

.hero {
  @apply --gradient-linear(#667eea, #764ba2, 135deg);
}
```

**ボタンスタイルの再利用例**

```css
@mixin --button-style {
  background: linear-gradient(135deg, #667eea 0%, #764ba2 100%);
  border: none;
  border-radius: 8px;
  color: white;
  padding: 12px 24px;
  font-weight: 600;
  transition: transform 0.2s ease;
}

.btn-primary {
  @apply --button-style;
}
```

**条件分岐の組み込み（`@media` を mixin 内に含める）**

mixin 定義の内部に `@media (prefers-contrast: more)` のような条件付きブロックを含めることができ、呼び出し側の文脈に応じてスタイルを出し分けられる。

```css
@mixin --accessible-border {
  border: 1px solid #ccc;

  @media (prefers-contrast: more) {
    border: 2px solid black;
  }
}
```

- `--` から始まる名前（カスタムプロパティと同じ命名規則）で mixin を宣言する
- `@apply` は宣言ブロック内（セレクタの中）でのみ使用可能
- 2026年7月時点で安定版ブラウザに完全実装したものはまだ無く、Chrome Canary 等のフラグ付き実験的対応が中心。Microsoft Edge 150 (2026年7月) のリリースノートでは、AccentColor 系のシステムカラー、`polygon()` の角丸対応、`page-margin-safety` プロパティなど周辺の CSS 機能とあわせて、mixins 関連仕様への追随が進められている段階として紹介されている

### ③ なぜそれが効果的か

- **ビルドレス化**: Sass などのプリプロセッサなしで「スタイルの塊の再利用」がブラウザネイティブで可能になる。ビルドパイプラインへの依存を減らせる
- **動的な値の受け渡し**: `type()` によるパラメータの型付けにより、単なる文字列置換ではなく、色・角度など意味を持った値としてバリデーションされた引数を渡せる
- **条件ロジックの内包**: `@media` などをミックスイン内部に持たせられるため、呼び出し側のコードをシンプルに保ったまま、状況に応じたスタイル出し分けを一箇所に集約できる
- **保守性**: カスタムプロパティが「値」の再利用にとどまるのに対し、mixins は「宣言の集合（振る舞い）」を再利用できるため、デザインシステムのトークン管理と役割分担がしやすくなる

## 2. Safari MCP server — Web 開発者向けの公式 MCP サーバー

**記事タイトル**: Introducing the Safari MCP server for web developers
**URL**: [https://webkit.org/blog/18136/introducing-the-safari-mcp-server-for-web-developers/](https://webkit.org/blog/18136/introducing-the-safari-mcp-server-for-web-developers/)（WebKit Blog, 2026年7月1日）
**関連報道**: [9to5Mac](https://9to5mac.com/2026/07/01/safaris-new-mcp-server-lets-coding-agents-inspect-and-debug-websites/), [MacRumors](https://www.macrumors.com/2026/07/01/apple-releases-safari-technology-preview-247/), [Daring Fireball](https://daringfireball.net/linked/2026/07/02/safari-mcp)

### ① 目的・問題意識

AI コーディングエージェント（Claude や Codex など）がフロントエンドを実装・デバッグする際、これまでは「ブラウザの中で実際に何が起きているか」を直接見ることができなかった。DOM の状態、コンソールログ、ネットワークリクエスト、レンダリング結果のスクリーンショットなどはすべて開発者が手動で DevTools を開いて確認し、エージェントに伝える必要があった。この「エージェントとブラウザの間の断絶」が、AI 支援開発における実装〜検証ループのボトルネックになっていた。

Safari MCP server はこの課題に対し、**Safari 自体が MCP（Model Context Protocol）サーバーとして振る舞い、AI エージェントに実ブラウザセッションへの直接アクセスを提供する**というアプローチを取る。これにより、Safari は主要ブラウザの中で初めてネイティブに MCP を実装したブラウザとなった。

### ② 具体的な技術詳細

- **提供形態**: Safari 27 beta および Safari Technology Preview 247 に同梱。macOS 上でローカルに動作し、セッションデータは Apple のサーバーではなく、すべて手元のデバイスに留まる
- **対応クライアント**: Claude、OpenAI Codex を名指しで互換クライアントとして例示。MCP プロトコルを話せるエージェントであれば任意のものが利用可能
- **提供ツール数**: 17種類のツールを提供し、開発者が DevTools で手動で行っていた作業をエージェントが代行できるようにする
- **ツールのカテゴリ構成**:
  - **ナビゲーション系**: `navigate_to_url`（URLへの遷移）、`create_tab` / `close_tab` / `switch_tab` / `list_tabs`（タブ操作）
  - **ページ検査系**: `get_page_content`（ページ内容取得）、`page_info`、`screenshot`（現在のページを PNG としてキャプチャ）
  - **DOM操作系**: `page_interactions`（click・type・scroll・hover・keyPress などの操作をシーケンスとして実行）
  - **ランタイムアクセス系**: `evaluate_javascript`（アクティブページ上での JS 実行）、`browser_console_messages`（現在または指定タブのバッファ済みコンソールログを返す）、`browser_dialogs`
  - **ネットワーク可視化系**: `list_network_requests`（URL・メソッド・ステータス・タイミングなどのリクエスト概要を一覧表示）、`get_network_request`（個別リクエストの詳細取得）
- **DOM スナップショットの取得方式**: 壊れやすい CSS セレクタではなく、ページ再レンダリングをまたいでも安定する UID を持つ**アクセシビリティツリー**経由で DOM 要素を参照する設計になっている。これによりエージェントが要素を見失いにくい
- **ネットワーク情報の粒度**: リクエスト/レスポンスボディ、ヘッダー、ペイロード、タイミングまで含めたフルキャプチャが可能
- **CSS 検査**: 算出スタイル（computed style）の検査もサポート
- **想定される用途**: JavaScript エラーの捕捉、算出スタイルの検査、ネットワーク呼び出しの確認、チェックアウトフローやフォーム送信のようなインタラクティブな状態が正しく動作しているかの検証など、開発者が手動で DevTools を触る場面の代表4カテゴリをカバー
- **有効化に必要な準備（一般的な MCP ブラウザ拡張と同様）**: Safari 側で Web 開発者向け機能を有効化し、リモートオートメーションを許可する設定が必要

### ③ なぜそれが効果的か

- **フィードバックループの短縮**: エージェントが「コードを書く→自分でスクリーンショットを撮る→DOMを読む→ネットワークログを確認する→JSを実行して検証する」までを人間を介さず一気通貫で行えるため、実装→検証のサイクルが大幅に短縮される
- **ローカル完結によるプライバシー**: セッションデータがすべてデバイス内に留まるため、機密性の高い開発中のアプリケーションでも安心して使える
- **標準プロトコルによる汎用性**: 特定のエージェント専用の統合を Apple 側が個別に作り込む必要がなく、MCP という共通プロトコルに対応するだけで Claude・Codex を含む任意のクライアントが利用できる。これはエコシステム全体にとってのスケーラビリティに直結する
- **安定した要素参照**: アクセシビリティツリーベースの UID 参照は、CSS セレクタに比べて DOM 構造の変化（クラス名変更やDOM再構築）に強く、エージェントによる自動操作の信頼性を高める

## 3. CSS Anchor Positioning 入門（Josh W. Comeau）

**記事タイトル**: Getting Started with Anchor Positioning
**URL**: [https://www.joshwcomeau.com/css/anchor-positioning/](https://www.joshwcomeau.com/css/anchor-positioning/)

### ① 目的・問題意識

ツールチップ、ドロップダウンメニュー、ポップオーバー、コンテキストメニューなど「ある要素（トリガー）を基準に、別の要素（フローティング要素）を相対配置する」UI パターンは、これまで JavaScript（`getBoundingClientRect()` の計算や Popper.js のようなライブラリ）や `position: fixed` + 手動座標計算に頼らざるを得なかった。ビューポート端での自動反転（フリップ）や、スクロール時の追従なども自前で実装する必要があり、実装コストと保守コストが高かった。

**Anchor Positioning API** は、この「一方の要素ともう一方の要素を紐付けて位置決めする」という課題を、JavaScript・ポータル・`getBoundingClientRect()` を一切使わず、**CSS だけ**で解決する新しいブラウザ API である。記事はこの API のうち「全体の20%の知識で実務上の80%のユースケースを解決できる」部分に絞って解説している。2026年初頭時点で主要ブラウザ（Chrome, Edge, Safari, Firefox）すべてに実装済みで、実務投入可能な段階にある。

### ② 具体的な技術詳細とコード

**基本構造: アンカー要素とターゲット要素の紐付け**

1. アンカーとなる要素に `anchor-name` を付与する
2. 位置決めしたい要素（ターゲット）を `position: absolute` にし、`position-anchor` でアンカーを指定する

```css
/* トリガーとなるボタン（アンカー） */
.trigger-button {
  anchor-name: --my-trigger;
}

/* ボタンに紐付けて表示するツールチップ（ターゲット） */
.tooltip {
  position: absolute;
  position-anchor: --my-trigger;
  position-area: top;
}
```

- `anchor-name` の値は、カスタムプロパティと同じく `--` から始まる任意の文字列
- `position-anchor` はターゲット要素の「デフォルトのアンカー」を設定するプロパティで、これを指定しておくと以降の位置決め系プロパティ（`position-area` や `anchor()` 関数）がそのアンカーを自動的に参照するようになる

**`position-area` による簡易配置**

`position-area: top` を指定すると、ターゲット要素はアンカーの「上側」に配置される。3x3 のグリッド（上/中/下 × 左/中/右）のような概念でアンカー周囲の9領域を指定でき、`position-area: top` のように単一方向を指定した場合は、ターゲットがアンカーの真上、かつ横方向は3カラム分（アンカーの左端〜右端の幅）にまたがって配置される。

**`anchor()` 関数による座標指定（より低レベルな制御）**

`anchor()` 関数を使うと、アンカー要素の特定の辺を基準にした座標計算を CSS の `top` / `left` などのプロパティに直接埋め込める。

```css
.tooltip {
  position: absolute;
  position-anchor: --my-trigger;
  top: anchor(bottom);
  left: anchor(left);
}
```

- これは `position-anchor` + `anchor(bottom)` / `anchor(left)` のように、アンカー要素の下端・左端を基準にターゲットの `top` / `left` を決定する記法で、`position-area` よりも細かい制御が可能

**主な実務ユースケース（記事で紹介されている適用例）**

- ビューポート端に近づくと自動的に反転するツールチップ
- トリガーボタンの直下に表示するドロップダウンメニュー
- スクロール中もアンカーに追従し続けるポップオーバー
- クリック座標を起点に表示するコンテキストメニュー
- フォーム入力欄に追従するフローティングラベル

### ③ なぜそれが効果的か

- **JavaScript 計算の排除**: これまで `getBoundingClientRect()` でアンカー要素の座標を都度計算し、スクロール・リサイズのたびに再計算していた処理が不要になる。ブラウザのレイアウトエンジンが直接位置を管理するため、リフローのたびにJSが介入する必要がなくなりパフォーマンス上も有利
- **ライブラリ依存の解消**: Popper.js やその後継である Floating UI のようなポジショニング専用ライブラリを、シンプルなユースケースであれば CSS だけで代替できる。バンドルサイズの削減にも寄与する
- **宣言的な記述**: 「どこに」「何を基準に」配置するかを CSS の宣言だけで表現できるため、コンポーネントのロジックとスタイルの関心分離が明確になり、可読性・保守性が向上する
- **ブラウザネイティブな自動反転**: `position-try` など関連機能と組み合わせることで、ビューポート境界に応じた自動フリップもブラウザ側の標準機能として扱えるようになり、エッジケースの実装漏れを減らせる

## 4. フロントエンド開発、この20年の変遷

### ① 目的・問題意識

Issue #749 では、フロントエンド開発がこの20年間でどのように変化してきたかを振り返る読み物記事も取り上げられている。2000年代の素朴な HTML/CSS/JS の時代から、jQuery による DOM 操作の効率化、SPA（シングルページアプリケーション）の台頭と React・Angular・Vue.js によるコンポーネント指向への転換、モバイルファーストへのシフト、そして2020年代以降の AI 支援開発・ノーコード/ローコードの浸透に至るまでの流れを俯瞰し、「なぜ今のフロントエンドはこの形になっているのか」という歴史的文脈を開発者に提供することを目的とした記事である。

この種の記事は特定の実装テクニックを提示するものではなく、業界の潮流を振り返るエッセイ・retrospective 形式のコンテンツであるため、他の3本のような具体的なコードサンプルは存在しない。

### ② 内容の要点

- **2000年代前半**: 静的な HTML と最小限の CSS が中心。JavaScript は補助的な役割にとどまっていた
- **2000年代後半〜2010年代前半**: jQuery の普及によりクロスブラウザの DOM 操作・イベント処理が簡素化され、Ajax による非同期通信が一般化
- **2010年代**: React・Angular・Vue.js の登場によりコンポーネント指向・宣言的 UI が主流化。SPA の爆発的普及と、それに伴うバンドルサイズ肥大化（モバイル体験の悪化）という副作用も顕在化
- **2010年代後半〜2020年代前半**: メタフレームワーク（Next.js など）によるハイブリッドレンダリング（SSR/SSG/CSR の使い分け）が標準に。TypeScript の実務必須化が進む
- **2020年代後半（現在）**: AI がワークフロー全体に組み込まれ、開発者は単一のレンダリング戦略を選ぶのではなく、同一ページ内で複数の戦略を組み合わせるのが当たり前になっている

### ③ なぜこの振り返りが意味を持つか

- 現在主流となっている技術選定（メタフレームワーク、TypeScript、AIアシスト開発）が、過去の失敗や課題（SPAの肥大化、ビルド複雑性、クロスブラウザ対応コスト）への反動として生まれてきた経緯を理解することで、新しい技術トレンドに対しても「なぜこれが必要とされているのか」を文脈込みで評価できるようになる
- 20年という長期スパンでの俯瞰は、目先の流行に振り回されず、フロントエンド技術選定における普遍的な原則（パフォーマンス、保守性、アクセシビリティの重要性は時代を通じて変わらない）を再確認する機会になる

## まとめ

Issue #749 は、**ブラウザネイティブでの CSS の表現力拡張（mixins, anchor positioning）** と **AI エージェントとブラウザの統合（Safari MCP server）** という、2026年半ば時点でのフロントエンド領域における2つの大きな潮流を象徴する内容だった。

- CSS mixins は「プリプロセッサなしでの再利用可能なスタイル定義」を実現し、ビルドレスな開発体験をさらに後押しする
- Safari MCP server は、AI コーディングエージェントに実ブラウザの状態への直接アクセスを与えることで、実装と検証のループを劇的に短縮する
- Anchor Positioning は、JavaScript 依存の高かった UI パターン（ツールチップ・ドロップダウン等）を宣言的な CSS だけで実現可能にする
- 20年の歴史的俯瞰は、これら個々の技術トレンドを「業界全体の進化の文脈」の中に位置づける材料を提供する
