## 1. React Router v8 — "退屈だが、良い"リリース

**リンク:** https://remix.run/blog/react-router-v8  
**カテゴリ:** メイン記事

### ① 目的・問題意識

React Router は v7 で「Future Flags」という仕組みを使い、破壊的変更を段階的にオプトインできる形で提供してきた。v8 は、それら Future Flags を全て「デフォルト有効」にした集大成リリース。「boring（退屈）」と呼ばれるのは、v7 の Future Flags を全て採用していた開発者なら、API 変更が最小限であることを意味する。同時に ESM 専用化・最新ランタイム要件への移行により、モダンな開発環境への切り替えを促す。

### ② 具体的な技術詳細

#### 新しい最低要件

| 依存 | 最低バージョン |
|------|----------------|
| Node.js | 22.22.0+ (Node 20 のサポート終了に合わせた選定) |
| React | 19.2.7+ |
| Vite | 7.0+ |

#### 主な破壊的変更

**1. `react-router-dom` パッケージの廃止**

v7 では `react-router-dom` は単なる re-export だった。v8 では完全に削除。

```js
// Before (v7)
import { Link, useNavigate } from 'react-router-dom'

// After (v8)
import { Link, useNavigate } from 'react-router'
// DOM固有API
import { RouterProvider } from 'react-router/dom'
```

**2. ESM 専用配布 (ES2022 ターゲット)**

CommonJS ビルドが廃止。バンドラー側の ESM 対応が必須。

**3. Future Flags の廃止とデフォルト化**

v7 で `future` オプションに設定していたフラグが全て取り除かれ、デフォルト動作となった。

```js
// Before (v7) — future フラグで有効化
export default {
  future: {
    v8_middleware: true,
    v8_viteEnvironmentApi: true,
    v8_splitRouteModules: true,
  },
} satisfies Config

// After (v8) — フラグ不要
export default {} satisfies Config
```

**4. `meta` API の `data` パラメータ削除**

非推奨だった `data` が `loaderData` に完全置換。

```js
// Before (v7)
export function meta({ data }) { ... }

// After (v8)
export function meta({ loaderData }) { ... }
```

**5. Cloudflare Dev Proxy の削除**

Cloudflare の公式 Vite プラグインを使う形に移行。

#### 新たにデフォルト化された機能

**ミドルウェア (`v8_middleware`)**  
ルートレベルのミドルウェアパイプラインが標準有効。リクエスト処理を各ルートで横断的に制御できる。

**Split Route Modules (`splitRouteModules`)**  
クライアント専用エクスポート (`clientLoader`, `clientAction`, `clientMiddleware`, `HydrateFallback`) をコンポーネントとは別チャンクに自動分割。初期バンドルサイズを削減し、コード分割を自動最適化する。

**Vite Environment API**  
Vite 6+ の分離された Environment パイプラインを全面採用。SSR ビルドの設定が変わる場合がある。

```js
// vite.config.ts — Vite Environment API の SSR 設定
export default defineConfig({
  environments: {
    ssr: {
      build: {
        rollupOptions: {
          // SSR 固有のオプションはここへ移動
        }
      }
    }
  }
})
```

**`fetcher.reset()` API の安定化**  
フェッチャーの状態をプログラム的にリセットできる。

**`RouterProvider` の `onError` プロップ安定化**  
ルーターレベルのエラーハンドリングが公式 API に昇格。

#### v7 からの移行手順

1. `react-router-dom` を `react-router` に置換
2. DOM 固有 API は `react-router/dom` からインポートに変更
3. `future` フラグの設定を削除
4. `data` → `loaderData` に置換
5. Node 22.22+、React 19.2.7+、Vite 7+ にアップグレード

### ③ なぜ効果的か

「年1回のメジャーリリース」という計画的な開発体制により、破壊的変更を予測可能なタイミングで提供。Future Flags パターンによって事前のオプトインが可能なため、実際のアップグレードコストが極めて低い。ESM 専用化・最新ランタイム要件への移行は、バンドルサイズ削減・ツリーシェイキング改善・将来の機能（RSC 安定化など）の基盤を整備する。

## 2. React Compiler の Rust 移植 — ビルドが 40% 高速化

**リンク:** https://github.com/react/react/pull/36173  
**カテゴリ:** 技術解説

### ① 目的・問題意識

React Compiler は元々 TypeScript で書かれており、Next.js との統合では WebAssembly ブリッジを経由していた。AST をシリアライズ → WASM に渡す → コンパイル → デシリアライズというラウンドトリップがビルド速度のボトルネックだった。Rust への移植はこの WASM ラウンドトリップを排除し、Turbopack と同一バイナリとして動作させることを目的とする。

### ② 具体的な技術詳細

**PR #36173** — 2026年6月9日マージ  
担当: Joseph Savona (josephsavona)

#### アーキテクチャ

TypeScript 版と同じ HIR (High-level Intermediate Representation) ベースのアーキテクチャを完全移植。

```
AST (Babel/OXC/SWC)
    ↓
HIR (Control Flow Graph + SSA形式)
    ↓
15以上のリアクティブパス処理
    ↓
最適化済みコード出力
```

- **CFG (Control Flow Graph)**: 制御フローをグラフ構造で表現
- **SSA (Single Static Assignment)**: 各変数は一度だけ代入される形式に正規化

#### 統合方式

| 統合 | パッケージ名 |
|------|------------|
| Babel プラグイン | `react_compiler_babel` (既存互換) |
| OXC 統合 | `react_compiler_oxc` |
| SWC 統合 | `react_compiler_swc` |

#### パフォーマンスベンチマーク

| 統合方式 | 速度向上 |
|----------|---------|
| Babel プラグイン (TS版比) | **3x 高速** |
| 変換ロジック単体 | **~10x 高速** (シリアライズオーバーヘッドを除く) |
| Turbopack ネイティブ統合 (Next.js 16.4) | **40%以上** ビルド高速化 |

#### テスト品質

- **1725個のフィクスチャ全て合格**
- TypeScript 版との出力コード比較テスト
- パスごとのコンパイラ中間表現検証
- エラーハンドリング一貫性チェック

#### 開発方法論

「人間がアーキテクチャ設計・テスト戦略を担当し、AI が TypeScript → Rust の機械的な変換を担当」という手法で開発。

#### Next.js 16.4 での設定

```js
// next.config.js
module.exports = {
  experimental: {
    reactCompiler: true,
  },
}
```

#### なぜ WASM より Rust ネイティブが速いか

```
[従来] TypeScript Compiler + WASM ブリッジ
  TS コード → SWC プラグイン → WASM境界 → シリアライズ
  → コンパイル → デシリアライズ → 出力

[新規] Rust Compiler + Turbopack ネイティブ
  Rust コード → 同一バイナリ内でコンパイル → 出力
  (WASM境界 = 0、シリアライズ = 0)
```

### ③ なぜ効果的か

Rust は Turbopack と同一の言語・エコシステムであり、バイナリ内での直接呼び出しが可能。シリアライズ境界を完全に排除することで、理論的に可能な最大パフォーマンスを実現。開発者はコードを変更せずに恩恵を受けられる（コンパイラは自動的に適切なツールチェーンを選択）。Sanity Studio は使用後に全体レンダリング時間・レイテンシが 20〜30% 削減されたと報告。

## 3. React Native 0.86 — 破壊的変更なし、エッジトゥエッジ完全対応

**リンク:** https://reactnative.dev/blog/2026/06/11/react-native-0.86  
**カテゴリ:** リリース

### ① 目的・問題意識

Android 15 ではエッジトゥエッジ (edge-to-edge) 表示がシステムレベルで強制されるようになったが、React Native の既存 API が正しく対応できておらず、座標計算・キーボード回避・ステータスバーなど複数の箇所でサイレントな不具合が発生していた。0.86 はこれらを修正しつつ、破壊的変更なしでのアップグレードを実現する。

### ② 具体的な技術詳細

#### エッジトゥエッジ対応の修正点

| API | 修正内容 |
|-----|---------|
| `KeyboardAvoidingView` | Android 15+ でのキーボード回避領域を正確に計算 |
| `Dimensions` (window) | エッジトゥエッジ有効時の旧デバイスで正しい値を返す |
| `measureInWindow` | エッジトゥエッジ有効時に正確な座標を返す |
| `StatusBar` | Modal が開いている間もスタイル・visibility の更新が可能 |
| Navigation bar | `enforceNavigationBarContrast` テーマ設定を正しく反映 |

#### DevTools 改善

**ライト/ダークモードエミュレーション**

`Emulation.setEmulatedMedia` API を通じて、デバイス設定を変更せずに DevTools から直接ライト/ダークモードを切り替えてテスト可能になった。

```js
// DevTools の Emulation.setEmulatedMedia を使用
// → prefers-color-scheme: dark / light を切り替え可能
// デバイス設定変更不要でダークモード対応をテストできる
```

#### その他の改善点

- **TextInput `autoComplete`**: Android の autofill ヒントを拡張サポート（`androidx.autofill` を 1.3.0 に更新）
- **Pressable**: `android_ripple` で `PlatformColor` サポート追加
- **View Transitions API**: `unstable_getViewTransitionInstance` を UIManagerBinding に追加
- **`mixBlendMode`**: `plus-lighter` をサポート
- **iOS**: WebSocket ヘッダーインジェクション用の `SRWebSocketProvider` API 追加
- **LogBox**: Android バックボタンで閉じられるように

#### バグ修正

- Samsung キーボードでのマイナス符号入力不具合を修正
- BoringLayout の負の幅クラッシュを修正
- Image API 24 での画像コンテンツ消失を修正
- `Image.getSize` が実際のソース寸法を返すように修正（ダウンサンプル後の値ではなく）

#### リポジトリ移行

React Native のリポジトリが `facebook/react-native` から `react/react-native` に移行（React Foundation 設立に伴う移動）。Metro、Yoga、React Native Website も同様に移行済み。

#### 依存関係更新

- Metro: `^0.84.2`
- Hermes コンパイラ・ランタイム更新
- セキュリティパッチ: `fast-xml-parser` (4.5.0→4.5.4)

### ③ なぜ効果的か

Android 15 でのエッジトゥエッジ強制は多くのアプリに影響するが、0.86 はアプリコードを変更せずに対処できる（0.85 からのゼロ破壊的変更アップグレード）。DevTools のモードエミュレーションにより、デバイスを持ち替えずにダーク/ライトモードのテストが完結でき、開発効率が大幅に向上する。

## 4. WordPress の React 19 アップグレード問題 — 一時的な巻き戻し

**リンク:** https://make.wordpress.org/core/2026/05/27/react-19-upgrade-in-wordpress/  
**関連リンク:** https://make.wordpress.org/core/2026/06/05/react-19-upgrade-temporarily-reverted-in-gutenberg/  
**カテゴリ:** 事例・教訓

### ① 目的・問題意識

WordPress/Gutenberg が React 18 から React 19 にアップグレードしようとしたところ、多数のサードパーティプラグインが予期せずクラッシュする問題が発覚した。React 19 の JSX ランタイムの変更が原因で、旧バージョンの JSX ランタイムをバンドルしていたプラグインとの互換性が失われた。

### ② 具体的な技術詳細

#### 問題の経緯

1. Gutenberg 23.3.0 で React 19 へアップグレード
2. 多数のプラグインがクラッシュ
3. Gutenberg 23.3.2 で React 18 に差し戻し

#### 根本原因: JSX ランタイムの非互換

多くのプラグインは自前でビルドした `react/jsx-runtime` ヘルパーをバンドルしていた。

```js
// React 18 JSX ランタイムが生成する要素オブジェクト
{
  $$typeof: Symbol(react.element),  // React 18形式
  type: 'div',
  key: null,
  ref: null,
  props: {},
}

// React 19 JSX ランタイムが生成する要素オブジェクト
{
  $$typeof: Symbol(react.transitional.element),  // React 19形式（新しい形式）
  type: 'div',
  key: null,
  props: {},
  // ref は props に統合
}
```

React 19 は **React 18 ランタイムが生成した要素オブジェクトを能動的に拒否**する。プラグインが React 18 の `jsx-runtime` をバンドルしたまま React 19 環境に読み込まれると即座にクラッシュ。

#### 新しい戦略

- **実験的フィーチャーフラグ**: React 18 と React 19 を切り替えられるフラグを提供
- **互換レイヤー**: 既存プラグイン向けの互換性アダプター
- **目標バージョン**: WordPress 7.1 での React 19 移行を維持（より段階的なアプローチで）

### ③ なぜ効果的か（教訓）

この事例は **JSX ランタイムのバンドル問題** という広く存在する落とし穴を示している。プラグインやライブラリが `react` や `react/jsx-runtime` を `peerDependency` ではなく `dependency` としてバンドルすると、ホスト環境のバージョンと衝突する。特に CMS エコシステムのような「プラグイン型」アーキテクチャでは、React のメジャーバージョンアップはホストアプリだけでなく全プラグインのビルド設定の確認が必要。React 19 は元素オブジェクトの形式変更（`ref` を `props` に統合など）を行ったため、ランタイムレベルで厳格な検証が入っている。
