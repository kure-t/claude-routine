## 1. Redux Toolkit 2.14 リリース

### ① 目的・問題意識

Redux Toolkit 2.x ラインは、将来の破壊的変更を含む 3.0 リリースに向けた地ならしとして継続的に改善されている。2.14 では、パフォーマンス・型定義・API の改善が盛り込まれた。

### ② 具体的な技術詳細

**パフォーマンス改善 — リスナーミドルウェア**

以前はリスナー数に比例してコストが増加していたが、2.14 ではその問題が解消された。

**型宣言の改善**

RTK が独自の `Draft` と `Patch` 型を同梱するようになり、発行される型宣言が Immer に依存しなくなった。以前は型宣言内で `import type { Draft } from 'immer'` が生成されていたが、2.14 以降は `@reduxjs/toolkit` を参照するようになる。

**エンティティアダプターの新 API**

```ts
// removeMany に where オプションが追加
adapter.removeMany({ where: (entity) => entity.status === 'deleted' });

// selectByIds が追加
const selectedEntities = adapter.selectByIds(state, [1, 2, 3]);
```

**RTK Query: キャッシュエントリセレクター**

RTK Query にキャッシュエントリセレクターが追加された。

**DevTools 最適化**

変更のないキーはオブジェクト参照を維持するようになり、DevTools に毎回サブスクリプションの全コピーが送られる問題が解消された。

**バグ修正**

- 無限クエリトリガーで `skipToken` が正しく尊重されるよう修正
- レスポンスボディのタイムアウトが `TIMEOUT_ERROR` として適切に報告されるよう修正

### ③ なぜ効果的か

リスナーミドルウェアのパフォーマンス問題は大規模アプリで深刻になるケースがあり、今回の修正で数十のリスナーを持つアプリでも効率的な動作が期待できる。型の独立性改善により、プロジェクトの依存グラフが整理され、型の不整合リスクが低減する。

## 2. Redux Toolkit 3.0 ロードマップ（Mark Erikson による）

### ① 目的・問題意識

Redux Toolkit は現在 CommonJS/ESM 混在のパッケージング構造を持つが、エコシステムの変化（ESM 標準化、TypeScript 6.0、Node.js LTS 更新）に合わせて、3.0 では大規模な破壊的変更を伴うメジャーリリースが計画されている。変更規模は「React 19-scale」と表現されている。

### ② 具体的な技術詳細

**タイムライン**

- 3.0 リリースは約 6〜8 ヶ月後を想定
- それまでは 2.x マイナーリリースで地ならしを進める
  - v2.14（今週リリース）: パフォーマンス・型改善・新 API
  - v2.15: （計画中）
  - v2.16: キャッシュ書き込みと `upsertQueryEntries` オプション、`undo()` のガード、宣言的楽観的更新、`removeQueryData`
  - v2.17: ハイドレーションと Suspense 対応

**3.0 での破壊的変更**

```json
{
  "dependencies": {
    "redux": "^6.0.0",
    "reselect": "^6.0.0",
    "immer": "^11.0.0"
  },
  "engines": {
    "node": "^20.19.0 || >=22.12.0"
  },
  "peerDependencies": {
    "typescript": ">=6.0.0"
  }
}
```

**パッケージング変更**

- ESM のみのパッケージングに移行（CommonJS 廃止）
- 一連のパッケージを順序通りリリース: `redux 6` → `redux-thunk 4`（shimとして）→ `react-redux 10` → `reselect 6` → `@reduxjs/toolkit 3`

**API 変更**

```ts
// 旧: createApi + modules
const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  endpoints: (builder) => ({ ... })
});

// 新 3.0: プレーン createApi + reactify ラッパー
import { createApi } from '@reduxjs/toolkit/query';
import { reactify } from '@reduxjs/toolkit/query/react';

const baseApi = createApi({ ... });
const api = reactify(baseApi); // React Hooks が追加される
```

```ts
// 旧: extraReducers でクロスリデューサー処理
const slice = createSlice({
  extraReducers: (builder) => {
    builder.addCase(otherSlice.actions.foo, (state) => { ... });
  }
});

// 新 3.0: respondTo で置換
const slice = createSlice({
  respondTo: {
    [otherSlice.actions.foo]: (state) => { ... }
  }
});
```

**RTK Query: キャッシュ構造変更**

```ts
// 3.0 では RTKQ キャッシュがエンドポイントごとにネスト
// 旧: state.api.queries['getUser(1)']
// 新: state.api.getUser.queries['1']
```

**非推奨 / 削除**

- `RootState`（RTK Query の）→ 3.0 で削除、`ApiRootState` に移行
- 不変性ライブラリ（Immer）が交換可能になる

**トラッキング Issue**

- [#5483 RTK 2.x and 3.0 roadmap](https://github.com/reduxjs/redux-toolkit/issues/5483)
- [#5495 Packaging, dependencies and the 3.0 release](https://github.com/reduxjs/redux-toolkit/issues/5495)
- [#5529 Switch to ESM-only packaging](https://github.com/reduxjs/redux-toolkit/issues/5529)

### ③ なぜ効果的か

ESM のみへの移行はバンドル最適化（Tree-shaking の完全サポート）を可能にし、現代的なビルドツール（Vite、Rollup、esbuild など）との親和性が向上する。`respondTo` の導入はスライス間の依存を明示的に宣言できるようにし、コードの可読性・保守性を高める。`reactify` ラッパーによるモジュール分離は、React 非依存の RTK Query コアを他フレームワークでも利用しやすくする。

## 3. Next.js App Router における Go ルートハンドラ（実験的機能）

### ① 目的・問題意識

Next.js の App Router はこれまで JavaScript/TypeScript のみのルートハンドラをサポートしていた。CPU 集約的な処理（画像変換、データ圧縮、暗号処理など）では Node.js の単一スレッドが制約となり得る。この実験的 PR では、`route.go` ファイルを用いて Go で書かれたルートハンドラを App Router に組み込む仕組みを追加した。

### ② 具体的な技術詳細

**PR 情報**

- [PR #100130](https://github.com/vercel/next.js/pull/100130): `[experiment] support App Router route.go handlers`（by timneutkens）
- [PR #100170](https://github.com/vercel/next.js/pull/100170): `[experiment] serve Go routes from a native public frontend`（by timneutkens）

**アーキテクチャ**

```
[HTTP リクエスト]
       ↓
  [Node.js / proxy.ts]  ←── JS/TS ルートハンドラ（通常通り）
       ↓（route.go へのリクエスト）
  [プライベート ループバック HTTP]
       ↓
  [Go ワーカープロセス]
       ↓
  [Turbopack によるコンパイル済み Go バイナリ]
```

**有効化方法（実験的フラグ）**

```js
// next.config.js
module.exports = {
  experimental: {
    goRoutes: true,  // または PR #100170 では goServer: true
  },
};
```

**route.go ファイルの例（概念）**

```go
// app/api/heavy-compute/route.go
package handler

import (
  "encoding/json"
  "net/http"
)

func Handler(w http.ResponseWriter, r *http.Request) {
  result := heavyComputation()
  json.NewEncoder(w).Encode(map[string]interface{}{
    "result": result,
  })
}
```

**動作の仕組み**

- Turbopack が `route.go` をネイティブバイナリにコンパイル
- Go ワーカーはリビルド後に置き換えられ、ルート削除やシャットダウン時に終了
- JS/TS ハンドラ、React ページ、Pages Router の動作はすべて Node.js 上で継続
- PR #100170 の `goServer` フラグを有効にすると、公開 HTTP リスナーと全 Go ハンドラが単一の実行可能ファイルに移動し、Node を通じたプロキシが不要になる（ただし proxy.ts、リライト、リダイレクト、カスタムヘッダーを迂回する点に注意）

**将来的な展望**

ニュースレターによると、Rust サポートも続く可能性がある。

### ③ なぜ効果的か

Go のゴルーチンと低レイテンシのランタイムは、CPU 集約的なバックエンド処理において Node.js よりも高いスループットを発揮できる。Turbopack がコンパイルを担うことで、開発者は `go build` を手動で実行する必要がなく、Next.js の開発フローに自然に統合される。ただし、現時点ではドラフト PR であり CI も通過していないため、本番利用には適さない実験的機能である。
