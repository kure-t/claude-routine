## 1. CSS カスタム関数とミックスイン（@function / @mixin）— Edge がミックスインの実装に着手

**関連URL（技術詳細の参照元）**:
- MDN: [CSS custom functions and mixins](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Custom_functions_and_mixins)
- MDN: [@function CSS at-rule](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@function)
- CSS-Tricks: [CSS Functions and Mixins Module Notes](https://css-tricks.com/css-functions-and-mixins-module-notes/)
- Serg Hospodarets: [CSS @apply rule (native CSS mixins)](https://hospodarets.com/css_apply_rule)

### ① 目的・問題意識

これまで「値を計算して再利用する」「宣言のかたまりを再利用する」といったロジックは Sass などのプリプロセッサに頼らざるを得なかった。CSS Functions and Mixins Module はこれをネイティブ CSS だけで実現しようとする仕様で、次の2つの機能に分かれる。

- **`@function`（カスタム関数）**: カスタムプロパティのように見えるが、固定値ではなく、パラメータや条件分岐（`if()` や `@media` 等）を伴うロジックに基づいて**値**を返す。すでに Chrome や Microsoft Edge 139+ で `@function` 自体はサポートが進んでいる。
- **`@mixin` / `@apply`（ミックスイン）**: Sass の `@mixin`/`@include` に相当する、**宣言（プロパティのかたまり）**を再利用する仕組み。`@function` が「値の世界」で動くのに対し、`@mixin` は「宣言の世界」で動く点が異なる。今回の号（#749）の主題は、Edge がこのミックスイン側の実装に着手したというニュース。ただし検索時点でミックスインはどのブラウザでも未実装（`@function` のみ先行実装済み）。

### ② 具体的なコード・技術詳細

**カスタム関数 `@function` の基本構文**:

```css
@function --function-name(<function-parameter>#?) [returns <css-type>]? {
  <declaration-rule-list>
}
```

**シンプルな例（値を反転する `--negate`）**:

```css
@function --negate(--value) {
  result: calc(-1 * var(--value));
}

.box {
  padding: --negate(var(--gap));
}
```

**型注釈つきの例**:

```css
@function --negate(--value <length>) returns <length> {
  result: calc(-1 * var(--value));
}
```

- 関数名は `--` で始まる `<dashed-ident>`（大文字小文字を区別）
- パラメータには `<length>` や `<color>` のような `<css-type>` を指定でき、受け付ける入力の型を明示できる
- `returns` 節で戻り値の型を制約できる
- `result` ディスクリプタが関数の戻り値。`var()` でパラメータを参照でき、条件分岐ルールの中に出現させることもできる

**ミックスイン `@mixin` / `@apply` の例（中央揃えの再利用）**:

```css
@mixin --center {
  display: flex;
  align-items: center;
  justify-content: center;
}

.card {
  @apply --center;
}
```

**もう一つの例（スクリーンリーダー専用テキストのミックスイン）**:

```css
@mixin --sr-text {
  position: absolute;
  left: -10000px;
  top: auto;
  width: 1px;
  height: 1px;
  overflow: hidden;
}
```

### ③ なぜ効果的か

- Sass の `@mixin`/`@include` や `@function` に慣れた開発者にとって、**ビルドツールなしで**同等の再利用性をブラウザネイティブに得られる。CSS-in-JS やプリプロセッサへの依存を減らせる。
- `@function` は「値」を、`@mixin`/`@apply` は「宣言のかたまり」を再利用するという役割分担が明確なため、既存の CSS カスタムプロパティ（`var()`）の限界（固定値しか持てない）を超えて、条件分岐やパラメータ化されたロジックを CSS だけで表現できる。
- Edge（Chromium ベース）がミックスインの実装に着手したことは、Interop の主要ブラウザ間でこの仕様が実用段階に近づいていることを示すシグナルであり、デザインシステムのトークン管理やユーティリティの共通化が今後 CSS ネイティブで完結できる可能性を示している。

## 2. Safari MCP サーバー — AI エージェントに実ブラウザを渡す

**関連URL（技術詳細の参照元）**:
- WebKit Blog: [Introducing the Safari MCP server for web developers](https://webkit.org/blog/18136/introducing-the-safari-mcp-server-for-web-developers/)
- 9to5Mac: [Safari's new MCP server lets coding agents inspect and debug websites](https://9to5mac.com/2026/07/01/safaris-new-mcp-server-lets-coding-agents-inspect-and-debug-websites/)
- ppc.land: [WebKit ships Safari MCP server with 17 tools for AI debugging agents](https://ppc.land/webkit-ships-safari-mcp-server-with-17-tools-for-ai-debugging-agents/)

### ① 目的・問題意識

AI コーディングエージェントが生成したフロントエンドコードは、実際に Safari / WebKit でどう描画され、どう動くかを確認できないまま「動くはず」で終わりがちだった。特に Safari はレイアウト、CSS、メディア機能、タッチ操作、パフォーマンス、アクセシビリティの面で他ブラウザと挙動が異なりやすく、開発者にとって恒常的な悩みの種になっていた。Safari MCP サーバーは、MCP（Model Context Protocol）対応のエージェントに**実際に動いている Safari ブラウザウィンドウ**への接続を提供し、DOM・ネットワークリクエスト・スクリーンショット・コンソール出力にエージェントがアクセスできるようにすることでこの課題を解決する。

### ② 具体的な技術詳細

- **提供元**: WebKit（Safari Technology Preview 247 / Safari 27 Beta に組み込み）
- **接続方式**: MCP 対応の任意のクライアント（AIエージェント）が Safari MCP サーバーに接続できる。Apple 側のクラウドを経由しない（ローカルのSafariに直結）。
- **ツール数**: 17種類。カテゴリ別に整理すると以下の通り。
  - **ナビゲーション系**: `navigate_to_url`, `create_tab`, `close_tab`, `switch_tab`, `list_tabs`
  - **ページ検査系**: `get_page_content`, `page_info`（URL・タイトルなど現在のページ情報を取得）, `screenshot` / `take_screenshot`（現在のページを PNG としてキャプチャ）
  - **DOM操作系**: `page_interactions`（click, type, scroll, hover, keyPress などの操作シーケンスを実行）
  - **ランタイムアクセス系**: `evaluate_javascript`, `browser_console_messages`, `browser_dialogs`
  - **ネットワーク可視化系**: `list_network_requests`, `get_network_request`
  - **レイアウトテスト系**: `set_viewport_size`, `set_emulated_media`, `wait_for_navigation`

### ③ なぜそれが効果的か

- エージェントが「コードを書いて終わり」ではなく、**実際の Safari の描画結果・コンソールログ・ネットワーク挙動を見ながら反復修正できる**ようになる。これは人間の開発者がブラウザの開発者ツールを使ってデバッグする作業をエージェントに解放するもので、Safari 特有の不具合（レイアウト崩れ、タッチイベントの差異など）を早期に検出・修正できる。
- スクリーンショットや `page_info` により、視覚的なリグレッションやアクセシビリティ上の問題もエージェントが「見て」判断できるようになる。
- ローカルの Safari に直結し Apple のクラウドを経由しないため、プライバシー・レイテンシの面でも扱いやすい設計になっている。

## 3. CSS Anchor Positioning 入門

**関連URL（技術詳細の参照元）**:
- ishadeed.com: [The Basics of Anchor Positioning](https://ishadeed.com/article/anchor-positioning/)
- MDN: [Using CSS anchor positioning](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning/Using)
- Chrome for Developers: [Introducing the CSS anchor positioning API](https://developer.chrome.com/blog/anchor-positioning-api)
- CSS-Tricks: [CSS Anchor Positioning Guide](https://css-tricks.com/css-anchor-positioning-guide/)
- css-tip.com: [Dynamic Tooltip Position with Anchor Positioning](https://css-tip.com/tooltip-anchor/)

### ① 目的・問題意識

ツールチップ、ポップオーバー、ドロップダウンメニュー、ダイアログなど「ある要素を別の要素（アンカー）を基準に配置したい」というレイアウト要求は非常に多いが、従来は JavaScript ライブラリ（Floating UI など）で要素の位置を計算し、`position: absolute` の `top`/`left` を動的に書き換える必要があった。CSS Anchor Positioning API は、この配置ロジックを**宣言的に CSS だけで**書けるようにする仕様。

### ② 具体的なコード・技術詳細

**アンカー要素の指定（`anchor-name`）**:

```css
.trigger {
  anchor-name: --my-anchor;
}
```

**位置付け対象の要素をアンカーに紐付ける（`position-anchor`）**:

```css
.tooltip {
  position: fixed; /* or absolute */
  position-anchor: --my-anchor;
}
```

**`anchor()` 関数で相対配置**（例: 自分の上端をアンカーの下端に合わせる = `top: anchor(bottom)` は「自分の top 辺をアンカーの bottom 辺に揃える」の意）:

```css
.tooltip {
  position: fixed;
  position-anchor: --trigger;
  top: anchor(bottom);
  left: anchor(center);
  transform: translateX(-50%);
}
```

**`position-area` によるショートハンド配置**（アンカーの上に配置する例）:

```css
.tooltip {
  position-anchor: --my-anchor;
  position-area: top;
}
```

**画面端でのはみ出し対策（`position-try-fallbacks`）**:

```css
.tooltip {
  position-anchor: --trigger;
  top: anchor(bottom);
  position-try-fallbacks: flip-block;
}
```

このように `position-try-fallbacks: flip-block` を指定すると、ツールチップが画面外にはみ出しそうな場合に自動的に反対側（上下反転など）へ配置を切り替えてくれる。

### ③ なぜそれが効果的か

- JavaScript による位置計算・スクロール/リサイズ時の再計算処理が不要になり、**パフォーマンスとコードのシンプルさの両方**が向上する。Floating UI のようなライブラリへの依存を減らせる。
- `anchor()` と `position-area` によって「アンカーの上/下/左/右」といった相対配置を宣言的に書けるため、CSS だけでレスポンシブなツールチップ・ポップオーバー・メニューを構築できる。
- `position-try-fallbacks` により、画面端でのはみ出しをブラウザ側が自動的に回避してくれるため、フォールバック位置を JS で細かく計算するロジックが不要になる。
- ネイティブ機能であるため、`popover` 属性や `<dialog>` 要素と組み合わせてアクセシブルな UI コンポーネントを構築しやすい。

## 4. この20年のフロントエンド開発の変遷（読み物）

**概要**: 号の紹介文によれば、この20年間でフロントエンド開発がどう変わってきたかを振り返る記事が掲載されている。

### ① 内容の要旨（検索結果から再構成した文脈）

- jQuery が2010年代前半に DOM 操作とクロスブラウザ対応を簡素化し、フロントエンド開発の主流だった時代から、2013年の React 登場によりコンポーネントベース・仮想 DOM というパラダイムへ移行した。
- 2010年代を通じて Web アプリケーションの複雑性が爆発的に増大し、単なる情報ページから「ブラウザ上で動くソフトウェア」へと進化した。
- 2026年現在は、クライアントに全てのロジックを詰め込む SPA 全盛期からの揺り戻し（いわゆる "The Great Correction"）が起きており、サーバーファーストレンダリングが再びデフォルトになりつつある。
- AI エージェントの普及により、開発者の役割が「コードを書く」ことから「AIエージェント群を指揮する」ことへとシフトしつつある、という論調も見られる。
