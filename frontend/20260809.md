## 1. TanStack Table V9 正式リリース

**リンク:** https://tanstack.com/blog/announcing-tanstack-table-v9

### ① 目的・問題意識

TanStack Table V8 はすべての行・列・セル・ヘッダーのオブジェクトインスタンスに同一のメソッドをコピーしていたため、大量データ（数百万行）を扱う場合にメモリ使用量が急増するという問題があった。また、ソート・フィルタ・ページネーションなどのすべての機能が常にバンドルに含まれており、不要な機能のコードも一律配信されていた。V9 ではこれらを根本から解決する。

### ② 技術詳細・コード

**プラグイン（ツリーシェイカブル）アーキテクチャ:**

V9 の中心的変更は `tableFeatures()` による明示的なプラグイン登録。使用する機能だけをインポートし、バンドルに含める。

```typescript
import {
  tableFeatures,
  useTable,
  createSortedRowModel,
  createFilteredRowModel,
  createPaginatedRowModel,
  sortingFeature,
  filteringFeature,
  paginationFeature,
} from '@tanstack/react-table'

// 使用する機能だけを宣言
const features = tableFeatures({
  sortingFeature,
  filteringFeature,
  paginationFeature,
})

function MyTable({ data, columns }) {
  const table = useTable({
    features,
    columns,
    data,
    getSortedRowModel: createSortedRowModel(),
    getFilteredRowModel: createFilteredRowModel(),
    getPaginatedRowModel: createPaginatedRowModel(),
  })

  return (
    <table>
      <thead>
        {table.getHeaderGroups().map(headerGroup => (
          <tr key={headerGroup.id}>
            {headerGroup.headers.map(header => (
              <th key={header.id} onClick={header.column.getToggleSortingHandler()}>
                {header.column.columnDef.header}
                {header.column.getIsSorted() === 'asc' ? ' ↑' : header.column.getIsSorted() === 'desc' ? ' ↓' : ''}
              </th>
            ))}
          </tr>
        ))}
      </thead>
      <tbody>
        {table.getRowModel().rows.map(row => (
          <tr key={row.id}>
            {row.getVisibleCells().map(cell => (
              <td key={cell.id}>{cell.getValue()}</td>
            ))}
          </tr>
        ))}
      </tbody>
    </table>
  )
}
```

**V8 からの段階移行用 `useLegacyTable`（暫定）:**

```typescript
import { useLegacyTable } from '@tanstack/react-table'

// V8 と同じ API で動作（バンドルサイズは増加するため、最終的には useTable へ移行推奨）
const table = useLegacyTable({
  columns,
  data,
  getSortedRowModel: getSortedRowModel(),
})
```

**状態管理（TanStack Store 連携）:**

```typescript
import { tableFeatures, useTable, sortingFeature } from '@tanstack/react-table'
import { useStore } from '@tanstack/react-store'

const features = tableFeatures({ sortingFeature })

function MyTable({ data, columns }) {
  const table = useTable({ features, columns, data })

  // 特定スライスのみ購読して再レンダリングを最小化
  const sorting = useStore(table.store, state => state.sorting)

  return <div>現在のソート: {JSON.stringify(sorting)}</div>
}
```

**主な破壊的変更:**
- `useReactTable` → `useTable`
- `column.getAggregationValue()` は複数引数からオブジェクト引数に変更
- `column.getAggregationFn()` → `column.getAggregationFns()`
- `row.getToggleSelectedHandler()` がデフォルトで Shift クリックによる範囲選択を有効化

### ③ なぜ効果的か

- **メモリ削減:** 行・列・セル・ヘッダーの API を共有プロトタイプに移行したことで、大規模テーブルで最大 **90% のメモリ削減**を達成。V8 では 100 万行でメモリ限界に達していたが、V9 では 1,000〜1,600 万行まで対応可能。
- **バンドルサイズ削減:** 機能を使った分だけ含まれる。ソートのみのテーブルなら V8 の 15〜20KB から 6〜7KB 程度に削減。
- **React Compiler 対応:** TanStack Store を基盤とした状態管理により React Compiler と完全互換。
- **フレームワーク対応拡張:** React / Vue / Angular / Solid / Svelte / Lit に加え、Preact / Octane / Ember / Alpine も新たにサポート。

## 2. Next.js 16.3 — Instant Navigations

**リンク:** https://nextjs.org/blog/next-16-3 / https://nextjs.org/blog/next-16-3-instant-navigations

### ① 目的・問題意識

サーバードリブンの Next.js App Router では、ページ遷移のたびにサーバーからの応答待ちが発生し、SPA のような即時ナビゲーションが実現できなかった。また、各リンクが個別に prefetch リクエストを発行するため CDN への要求が多く、大規模サイトでは帯域・TTFB ともに問題になっていた。

### ② 技術詳細・コード

**設定（next.config.ts）:**

```typescript
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,        // use cache コンポーネントのプリレンダリングと再利用
  partialPrefetching: true,     // ルートごとに再利用可能な読み込みシェルを1回だけ prefetch
}

export default nextConfig
```

**Link コンポーネントによる制御:**

```tsx
import Link from 'next/link'

// デフォルト: loading shell のみ prefetch（最小限）
<Link href="/dashboard">Dashboard</Link>

// 静的部分と 'use cache' された部分も含めて prefetch
<Link href="/dashboard" prefetch={true}>Dashboard</Link>

// このルートを instant navigation から除外
// ページ側で export const instant = false を宣言
```

**ルート単位の instant navigation オプトアウト:**

```typescript
// app/heavy-route/page.tsx
export const instant = false  // このルートは通常のナビゲーションを使用

export default function HeavyPage() {
  return <div>...</div>
}
```

**`use cache` との組み合わせ:**

```typescript
// app/dashboard/page.tsx
import { unstable_cacheLife as cacheLife } from 'next/cache'

export default async function Dashboard() {
  'use cache'
  cacheLife('hours')

  const data = await fetchDashboardData()
  return <DashboardView data={data} />
}
```

### ③ なぜ効果的か

- ルートごとに **再利用可能な loading shell** を 1 回だけ生成・キャッシュし、複数のリンクが同一ルートを参照していても prefetch リクエストは 1 回に抑制。
- Vercel のデータでは、移行後のアプリで **prefetch リクエスト 45% 減**、**CDN リクエスト 17% 減**、**静的コンテンツのバイト数 24% 減**、**TTFB 最大 60% 低下**を確認。
- `cacheComponents` と `partialPrefetching` は将来のメジャーバージョンでデフォルト化が予定されており、今から採用しても行き止まりにはならない。

## 3. Next.js 16.3 — Turbopack の強化

**リンク:** https://nextjs.org/blog/next-16-3-turbopack

### ① 目的・問題意識

長時間の開発セッションや大規模プロジェクトで Turbopack のメモリ使用量が膨大になる問題と、`next build` が毎回フルリビルドとなりCI/CD の速度が低下する問題を解決する。

### ② 技術詳細・コード

**開発メモリの自動エビクション（デフォルト有効）:**

アクティブに作業していないルートのモジュールをメモリからディスクに退避。Vercel 自社のダッシュボードアプリで測定した結果、50 ルートのコンパイル後のメモリが **21.5GB → 2GB（約 90% 削減）**。設定不要でデフォルト有効。

**ビルドの永続キャッシュ（next.config.ts）:**

```typescript
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    turbopackFileSystemCacheForBuild: true,  // next build に永続キャッシュを適用
  },
}

export default nextConfig
```

CI/CD では `.next` キャッシュディレクトリを保存・復元することで **最大 5.5 倍高速化**。

**Rust 製 React Compiler（実験的）:**

```typescript
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    reactCompiler: {
      backend: 'rust',   // Babel ではなく Rust ネイティブのコンパイラを使用
    },
  },
}

export default nextConfig
```

Babel トランスフォームに比べてコンパイル速度 **20〜50% 向上**。Rust の Turbopack パイプラインと同一ランタイム上で動作し、JavaScript 実行待ちのボトルネックを解消。

**`import.meta.glob` サポート:**

```typescript
// 複数ファイルをワイルドカードでまとめてインポート
const modules = import.meta.glob('./components/*.tsx')

for (const path in modules) {
  const module = await modules[path]()
  console.log(path, module)
}
```

### ③ なぜ効果的か

開発中のメモリエビクションは「今触っていないルートはディスクに退避」という直感的な戦略で、HMR 性能は維持しつつ大規模アプリでの長時間開発を実現する。Rust 製コンパイラはパイプラインを均一化し、Turbopack が Babel を待つ非効率を根本から排除する。

## 4. Chrome 公式の `use-webmcp-tool` — React Hook で AI エージェント対応

**リンク:** https://github.com/GoogleChromeLabs/use-webmcp-tool

### ① 目的・問題意識

Web ページが AI エージェントに操作される場合、エージェントは DOM スクレイピング・アクセシビリティツリー・スクリーンショットに頼らざるを得ず、精度・速度・信頼性に限界がある。**WebMCP**（W3C 提案中）は `document.modelContext` という API でページが直接 JavaScript 関数を「ツール」として登録し、エージェントが認証済み・型安全な形で呼び出せる仕組み。Chrome 146（2026年2月）で DevTrial として実装された。`use-webmcp-tool` はそのための公式 React フック。

### ② 技術詳細・コード

**ネイティブ命令型 API（`document.modelContext`）:**

```javascript
const controller = new AbortController()

document.modelContext.registerTool(
  {
    name: 'add-todo',
    description: "Add a new item to the user's active todo list",
    inputSchema: {
      type: 'object',
      properties: {
        text: { type: 'string', description: 'The text content of the todo item' },
      },
      required: ['text'],
    },
    async execute({ text }) {
      // ページの実際の状態を変更するロジック
      return { content: [{ type: 'text', text: `Added todo: "${text}"` }] }
    },
  },
  { signal: controller.signal }  // コンポーネントのアンマウント時に登録解除
)
```

**React Hook（`use-webmcp-tool` パッケージ）:**

```typescript
import { useWebmcpTool } from 'use-webmcp-tool'

// マウント時に登録、アンマウント時に自動解除
// API が存在しない環境では no-op にフォールバック
function TodoApp() {
  const [todos, setTodos] = useState<string[]>([])

  useWebmcpTool({
    name: 'addTodo',
    description: 'Add a new item to the todo list',
    inputSchema: {
      type: 'object',
      properties: {
        text: { type: 'string' },
      },
      required: ['text'],
    },
    execute: ({ text }) => {
      setTodos(prev => [...prev, text])
      return { content: [{ type: 'text', text: `Added: ${text}` }] }
    },
  })

  return (
    <ul>
      {todos.map((todo, i) => <li key={i}>{todo}</li>)}
    </ul>
  )
}
```

**react-webmcp（MCPCat 製、コミュニティ版）のパターン:**

```typescript
import { WebMCPProvider, useWebMCPTool } from 'react-webmcp'

// _app.tsx でプロバイダーをラップ（ポリフィルをインストール）
function App({ Component, pageProps }) {
  return (
    <WebMCPProvider>
      <Component {...pageProps} />
    </WebMCPProvider>
  )
}

// コンポーネント内でツールを宣言
function SearchPage() {
  useWebMCPTool({
    name: 'searchProducts',
    description: 'Search the product catalog',
    inputSchema: {
      type: 'object',
      properties: { query: { type: 'string' }, category: { type: 'string' } },
      required: ['query'],
    },
    execute: async ({ query, category }) => {
      const results = await fetchProducts(query, category)
      return { content: [{ type: 'text', text: JSON.stringify(results) }] }
    },
  })
  // ...
}
```

### ③ なぜ効果的か

- React のライフサイクルと完全統合。コンポーネントがマウントされた瞬間にエージェントからアクセス可能になり、アンマウントで自動解除される。
- API が存在しない古い環境では no-op として動作するため、プロダクションに安全に組み込める。
- DOM 解析不要のため、動的コンテンツや SPAでも AI エージェントが正確・高速に操作できる。
- Chrome Canary では既に `chrome://flags/#webmcp-api` で有効化可能。

## 付録: TanStack Table V9 メモリ改善の仕組み

**リンク:** https://tanstack.com/blog/tanstack-table-v9-memory-performance

### 技術的背景

V8 では行・列・セル・ヘッダーのすべてのインスタンスにメソッドが直接コピーされていた（Object.assign パターン）。100 万行 × 10 列 = 1,000 万のセルオブジェクトがそれぞれ同一のメソッドを保持していた。

V9 では共有プロトタイプチェーンにメソッドを置き、各インスタンスはデータのみを保持する。JavaScript のプロトタイプ継承の仕組みを活用した古典的な最適化だが、大規模データでは劇的な差が生まれる。

| テーブル規模 | V8 のメモリ | V9 のメモリ | 削減率 |
|---|---|---|---|
| 100 万行 | ~限界 | ~対応可 | — |
| 1,000 万行 | 非対応 | 4GB 未満 | — |
| Vercel ダッシュボード（50 ルート） | 21.5GB | 2GB | 約 90% |
