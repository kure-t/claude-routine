## 1. Projecting React — Tanner Linsley（メイン特集）

**リンク:** https://tannerlinsley.com/posts/projecting-react  
**関連リポジトリ:** https://github.com/TanStack/redact

### ① 目的・問題意識

TanStack Start を開発する中で、React 19 のクライアントバンドルが **約 60 KB（gzip）** にのぼることが障壁になっていた。アプリコードが 1 行も実行される前にこのサイズのランタイムが必要となる。Tanner Linsley はこの問題に対し、「React の公開 API を維持したまま、TanStack Start が必要とするものだけに絞った実装を AI エージェントに生成させたらどうか」と発想した。

### ② 具体的な技術詳細

**パッケージ名:** `@tanstack/redact`

| 指標 | 値 |
|---|---|
| gzip サイズ（フル互換） | **9.07 KB**（React 19 の約 45 KB と比較） |
| gzip サイズ（nano preset） | **6.75 KB** |
| テスト | 707/707 パス |
| 本番稼働 | tanstack.com（2026-04-20 より） |

**サブパス exports（ドロップイン対応）:**

```
@tanstack/redact
  └─ react
  └─ react-dom
  └─ react-dom/server
  └─ scheduler
  └─ react/jsx-runtime
```

ユーザーコードの import 文は変更不要。バンドラーレベルで差し替えを行う。

**Vite プラグイン設定:**

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import { redact } from '@tanstack/redact/vite'

export default defineConfig({
  plugins: [
    redact(), // React → @tanstack/redact へのエイリアスを自動適用
  ],
})
```

**実装されている機能:**
- Fiber ベースのリコンサイラー（キー付き子要素の差分検出）
- ホスト DOM のマウント・更新
- 標準 Hook サーフェス（`useState`、`useEffect`、`useRef`、`useMemo`、`useCallback`、`useContext`、`useReducer` 等）
- SSR + ストリーミング Suspense + ハイドレーション
- `use(promise)` / `React.lazy` の遅延ハイドレーション
- 同期的 endHydration 中のカーソル保持

**意図的に省略された機能:**
- コンカレントレンダリング・タイムスライシング・レーンベーススケジューラ
- React DevTools
- `useTransition` / `useDeferredValue` は**同期実行**（スケジューラは microtask ラッパーの noop）

### ③ なぜ効果的か

React の公開 API を 100% 維持したまま、コンカレント機能など TanStack Start のユースケースで不要な複雑機能を削ぎ落とすことで、**バンドルサイズを約 80% 削減**し、かつ 2〜3 倍の実行速度向上を実現している。ユーザーコードへの変更が不要なため、既存の React アプリも設定一つで切り替えられる。AI エージェントを活用して難解な実装（リコンサイラー順序、エフェクトクリーンアップタイミング、遅延ハイドレーション等）を解決したことも注目点。

## 2. From Latency to Instant: Modernizing GitHub Issues Navigation Performance

**リンク:** https://github.blog/engineering/architecture-optimization/from-latency-to-instant-modernizing-github-issues-navigation-performance/  
**公開日:** 2026年5月14日

### ① 目的・問題意識

GitHub Issues のナビゲーションは、課題トリアージや複数 Issue 間の移動が多いにもかかわらず、ページ遷移のたびにネットワーク往復コストが発生し体感速度が遅かった。「ラテンシの削減」ではなく「遷移をインスタントに感じさせる」という目標を立て、クライアントサイドキャッシング・スマートプリフェッチ・サービスワーカーを組み合わせたアーキテクチャ改善を行った。

### ② 具体的な技術詳細

**基本戦略:** "ローカルデータから即座にレンダリングし、バックグラウンドで再検証する"

#### React ソフトナビゲーションの活用

React ランタイムはすでに起動済みなため、ソフトナビゲーション時の支配的なコストはアプリ起動ではなくデータフェッチレイテンシ。これを排除することで大量のトラフィックを「インスタント」バケットに移行できると判断。

#### コード分割（React.lazy + 動的ルートプリロード）

```jsx
// ルート単位でコード分割
const IssueEditor = React.lazy(() => import('./IssueEditor'))

// 編集モード突入時のみエディタバンドルをフェッチ
// hover などのインテントに基づくプリフェッチでレイテンシを隠蔽
```

#### IndexedDB 永続キャッシュ

インメモリストアを IndexedDB 永続キャッシュで拡張。タブ閉鎖やブラウザ再起動後も生存する耐久ストレージを実現。

```
[インメモリホットキャッシュ]  ← 同期アクセス可能
        ↓
[IndexedDB 永続キャッシュ]   ← インデックス付きオブジェクトストア、キーベース高速参照
        ↓
[ネットワーク（再検証）]
```

ユーザーが Issue を繰り返し開く行動（トリアージ・コラボレーション中）を分析し、Issues ビューの推定キャッシュヒット率は **約 30%** と見積もり。

#### プリヒーティング戦略

- **トリガー:** Issue リスト、ダッシュボード、プロジェクト、依存関係ビューなど高インテントサーフェス
- **スロットリング:** 低優先度ワーカーで実行、レート制限あり、サーキットブレーカーで保護
- **優先度:** ユーザー操作は常にスペキュラティブフェッチより優先

#### インメモリレイヤリング

```
アクティブインメモリストア（最速）
    ↓ キャッシュミス時
IndexedDB 永続ストア（非同期読み取り不要のホットデータ用レイヤ）
    ↓ キャッシュミス時
ネットワーク
```

### 結果

| 指標 | 改善前 | 改善後 |
|---|---|---|
| 200ms 以内の Issue ビュー率 | 2% | 35% |
| インスタント React ナビゲーション率 | 4% | 22% |
| 全リクエストに占めるインスタント比率 | - | 約 15% |

### ③ なぜ効果的か

「速くする」のではなく「すでに持っているデータを即座に見せる」というアプローチが肝。React ソフトナビゲーション＋IndexedDB の組み合わせでネットワーク往復ゼロを実現しつつ、プリヒーティングで「まだキャッシュにない」ケースも前もって解消している。インメモリホットレイヤーが IndexedDB の非同期読み取りコストさえ排除し、同期レンダリングを可能にしている。

## 3. Waku 1.0 (beta) — The Minimal React Framework

**リンク:** https://waku.gg/blog/waku-v1-beta  
**公開日:** 2026年5月12日

### ① 目的・問題意識

Daishi Kato（`jotai` や `zustand` の作者）が開発する Waku は、React Server Components を Next.js のような大規模フレームワークなしで使えるミニマルな React フレームワーク。マーケティングサイト・ブログ・ドキュメント・軽量 EC など、「ほぼ静的でいくつか動的ルートがある」サイトに最適化されている。1.0 Beta はプロダクション対応に向けた互換性と安定性の転換点。

### ② 具体的な技術詳細

**技術スタック:** Vite + Hono をベースに構築、React 19 のサーバーコンポーネント・サーバーアクションをフルサポート。

#### バージョンスキュー（Version Skew）対応

再デプロイ後、古いビルドを読み込んでいたクライアントが壊れずにリカバリーするグレースフルなハンドリングを実装。これまでデプロイ後のクライアントエラーが課題だったが解消。

#### Vite 8 + Rolldown バンドラー

```
Waku 1.0 beta
  └─ Vite 8（Rolldown バンドラー採用）
       └─ Rust 製の高速バンドラーで build パイプライン高速化
```

#### ルーター強化

```
新機能:
- slug スライス（例: [...slug] で複数セグメント取得）
- プレフィックス付き slug（例: post-[id]）
- trailing-slash ハンドリング
- layout の slug props
```

#### その他の新機能

| 機能 | 詳細 |
|---|---|
| ブラウザ DevTools パフォーマンストラック | サーバーコンポーネントのパフォーマンス可視化 |
| Content-Security-Policy サポート | CSP ヘッダー生成・設定の組み込みサポート |
| Node 26 サポート | 最新 Node.js バージョン対応 |

**基本的な使用例（サーバーコンポーネント）:**

```tsx
// pages/index.tsx (Server Component)
import { Link } from 'waku'

export default async function HomePage() {
  const posts = await fetchPosts() // サーバーで直接データ取得
  return (
    <main>
      {posts.map(post => (
        <Link key={post.id} to={`/post/${post.id}`}>
          {post.title}
        </Link>
      ))}
    </main>
  )
}
```

### ③ なぜ効果的か

Waku はシンプルな API と Vite によるクイックな開発サーバーにより、RSC の恩恵（サーバーサイドデータフェッチ、バンドルサイズ削減）をエンタープライズ向け機能の重みなしに享受できる。Rolldown（Rust 製）採用によるビルド高速化と、バージョンスキュー対応による本番環境の堅牢性向上が、プロダクション利用の障壁を大幅に下げている。

## 4. My Thoughts on AI, Part 1: Fears, Opinions, and Mental Journey — Mark Erikson

**リンク:** https://blog.isquaredsoftware.com/2026/05/ai-thoughts-part-1-fears-opinions-journey/  
**公開日:** 2026年5月7日  
**著者:** Mark Erikson（Redux メインテナー、Replay.io シニアフロントエンドエンジニア）

### ① 目的・問題意識

Redux メインテナーとして知られる Mark Erikson が、AI コーディングツールに対する自身の考えの変遷を率直に公開。AI への過度な楽観（e/acc）も終末論（P(doom)）でもなく、「ソフトウェアエンジニアとして現実を把握しようとしている」立場から、AI ツールの実際の有用性と限界を記録した。

### ② 具体的な技術詳細

**Erikson の技術的バックグラウンドと価値観:**
- 決定論・純粋関数・予測可能でテスタブルなシステムへの信仰が Redux 設計に反映
- 「システムは注意深い分析で理解・解決できる」という信念

**初期 AI 体験から現在まで:**

1. **GitHub Copilot（VS Code 拡張）** が最初の本格的な AI コード生成体験
2. **2026年2月の事例（転換点）:** React インスツルメンテーションレイヤーの拡張作業でエージェントを使用。エージェントが React の fragment ファイルを読み込み、さまざまな ReactDOM バンドルを解析し、React の異なるバージョンを比較・検討できたことに驚き
3. **AI エージェントの活用例:**
   - DB マイグレーション作業（初期 ChatGPT を使用）
   - CLI でのコマンド実行の監視・確認
   - ハンズオン開発フローの維持

**スタンス（「混在した体験」の内実）:**
- AI の能力に驚く場面がある一方、過度な依存には批判的
- コードの予測可能性・テスト可能性という価値観と AI 生成コードの特性のギャップを認識
- Part 2 では具体的なセットアップ・ワークフロー・ツールを公開予定

### ③ なぜ注目されるか

フレームワーク作者やフルスタックエンジニアとは異なる視点—**長年 Redux のような「状態管理の正しさ」を追求してきたエンジニアが AI ツールをどう評価するか**—は貴重。AI 万能論でも拒絶論でもなく、実体験に基づいた段階的な受容のプロセスが記録されており、AI ツール導入を迷うエンジニアへの参考になる。
