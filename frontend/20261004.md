## 1. Signals come to React-Redux — React-Redux 9.4 alpha の `useSignalSelector`

### ① 目的・問題意識

Redux では、`dispatch` が発生するたびにマウント済みのすべてのセレクターが再実行される。大規模アプリでは不必要な再レンダリングが積み重なりパフォーマンスのボトルネックになる。この問題を Signals ベースのパス追跡で根本的に解決する。

### ② 具体的なコードと技術詳細

React-Redux v9.4.0-alpha に `SignalProvider` と `useSignalSelector` が追加された。

**基本的な使い方（既存コードのドロップイン置換）:**

```tsx
// 既存の Provider / useSelector をそのまま置き換えるだけ
import { SignalProvider, useSignalSelector } from 'react-redux/signals'

// App.tsx
function App() {
  return (
    <SignalProvider store={store}>
      <TodoList />
    </SignalProvider>
  )
}

// コンポーネント
function TodoText({ id }: { id: number }) {
  const text = useSignalSelector((state: RootState) => state.todos.byId[id].text)
  return <span>{text}</span>
}
```

**仕組み:**

1. `useSignalSelector` がマウントされると、`state` はプロキシでラップされる。
2. セレクターが `state.todos.byId[3].text` にアクセスすると、プロキシがそのパスをシグナルとして記録する。
3. `dispatch` 後、`SignalProvider` は旧 state と新 state をツリー全体で diff し、変化したパスのシグナルだけを発火する。
4. 依存パスが変化したセレクターだけが再実行され、変化していないセレクターは完全にスキップされる。

**インストール:**

```bash
npm install react-redux@alpha
```

`react-redux/signals` エントリーポイントは `Provider` を `SignalProvider` に、`useSelector` を `useSignalSelector` にそれぞれ re-export しているため、既存のサードパーティライブラリも `react-redux` からインポートしていれば自動的に新実装に切り替わる。

### ③ なぜ効果的か

- **選択的な再実行**: 変化したパスに依存するセレクターだけが実行されるため、不要な再計算が根本からなくなる。
- **後方互換性**: `useSelector` と同じシグネチャ・オプションを持ち、既存のテストスイートをそのままパスする。
- **ベンチマーク**: 各種シナリオで総スクリプト時間が 20〜30% 削減。RTK Query ベンチマークでは `dispatch` あたりの処理時間が約 20〜30% 低下。

## 2. TanStack Redact / "Projecting React" — Tanner Linsley による小さな React ランタイム実験

### ① 目的・問題意識

React 19.3 本体は gzip で約 **69,162 bytes** あり、TanStack Start のような軽量フレームワークにとって無視できないペイロードになる。コンカレントレンダリングなどの高度な機能を使わないアプリでも全体を読み込む必要があるのは非効率。

### ② 具体的なコードと技術詳細

Tanner Linsley が 1 日分の AI エージェントアシスト作業で構築し、`@tanstack/redact` として公開した。

**バンドルサイズ比較:**

| ランタイム | gzip サイズ |
|-----------|------------|
| React 19.3.0 | 69,162 bytes |
| TanStack Redact (Vite デフォルト) | 23,311 bytes (**66.3% 削減**) |

**Vite での切り替え方 (1 プラグインで完結):**

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { redact } from '@tanstack/redact/vite'

export default defineConfig({
  plugins: [
    react(),
    redact(), // React, ReactDOM, scheduler, JSX ランタイムを Redact に置換
  ],
})
```

**サポートする API (コアは ~7.08 KB gzip):**

- `useState`, `useReducer`, `useEffect`, `useLayoutEffect`, `useInsertionEffect`
- `useMemo`, `useCallback`, `useRef`, `useId`, `useSyncExternalStore`, `use`
- Fragments, JSX ランタイム, キーによる子ノード diffing, ホスト DOM マウント/更新, ネイティブイベントバインディング

**未サポート (意図的に除外):**

- コンカレントレンダリング / タイムスライス / レーンベーススケジューラー
- React DevTools
- Flight クライアントデシリアライザー
- `useTransition` と `useDeferredValue` は同期実行、`startTransition` は `fn()` のラッパー

### ③ なぜ効果的か

- 実際の TanStack Start アプリで **2〜3 倍の描画速度向上** を確認。
- すでに `tanstack.com` 本番環境で稼動しており、既知のリグレッションはゼロ。
- コンカレント機能を必要としないアプリ (多くの SPA や SSR アプリ) では完全な代替として機能する。
- ただし Tanner 自身は「実験」と位置づけており、TanStack Start への組み込みは現時点で予定なし。

## 3. Shopify が React Native をやめてネイティブへ移行 — LLM エージェントが理由

### ① 目的・問題意識

Shopify は 6 年以上 React Native を使ってきたが、コーディングエージェントの登場によって「iOS と Android で同じ機能を 2 回実装するコスト」が劇的に低下した。それにより、コード共有のメリットよりもプラットフォームネイティブ実装のメリット（パフォーマンス・UX・将来性）が上回ると判断した。

### ② 具体的なコードと技術詳細

**移行規模:**

- Shop アプリ（1 億人超のユーザー）を React Native から Swift / Kotlin へ移行
- 6 名のエンジニア + AI コーディングエージェントで **12 週間** でプロトタイプ→App Store 公開を達成

**Helix — LLM 向け移行ツール:**

Shopify は内製ツール **Helix** を構築。エージェントが React Native コードを Swift/Kotlin に変換する際、細かいチェックポイントと厳格な品質ゲートを設けて常に「shippable な状態」を維持する。

```
React Native コード
    ↓  Helix (iOS版を参考にAndroid版を生成、逆も可)
Swift / Kotlin ネイティブコード
    ↓  品質ゲート (自動テスト、クラッシュ率チェック)
本番デプロイ
```

**エージェントの能力:**

- iOS 版を参照して Android 版を実装（逆も可能）
- 自分のメインスタック外の言語へのランプアップを支援

**移行結果:**

| 指標 | 改善 |
|------|------|
| クラッシュ率 | **90% 削減** |
| アプリサイズ | **109 MB 削減** |

### ③ なぜ効果的か

- LLM エージェントがコンテキストとして iOS 実装を参照することで、Android 実装の品質と一貫性が保証される。
- Helix の小さなチェックポイント設計により、エージェントが部分的に失敗しても全体が壊れないリスク管理が実現されている。
- 「コード共有」という React Native の最大のメリットが AI エージェント時代には相対化されることを示す事例。

## 4. "Props Are Not a Design System" — プロップ渡しスタイリングへの批判

### ① 目的・問題意識

多くの UI ライブラリは `radius`, `size`, `color` などのスタイルをプロップとして直接渡すことを許している。この「柔軟性」こそが問題であり、コンポーネント呼び出しのたびに一時的なスタイリング判断が行われ、同じアプリ内でさえ同一コンポーネントが異なる見た目になる。

### ② 具体的なコードと技術詳細

**アンチパターン（スタイルをコールサイトで決定）:**

```tsx
// ❌ 問題: 同じ Button が呼ばれるたびに異なるスタイルになる
<Button color="blue" size="md" radius={4}>Submit</Button>
<Button color="primary" size="large" borderRadius="8px">Send</Button>
<Button className="text-blue-500 px-4 py-2 rounded">Action</Button>
```

**3 つの根本的な問題:**

1. **視覚的一貫性を保証できない** — 同じファイル内でも呼ぶたびに外見が変わる
2. **セマンティクスがない** — そのスタイルが何を意味するかコードから読み取れない
3. **システムがない** — 変更時にどこを修正すべきか分からない

**推奨パターン（バリアントとモディファイアで管理）:**

```tsx
// ✅ 推奨: バリアントに意味のある名前をつけ、一箇所で定義する
const buttonVariants = {
  primary: 'bg-blue-600 text-white px-4 py-2 rounded-md font-medium',
  secondary: 'bg-gray-100 text-gray-900 px-4 py-2 rounded-md',
  danger: 'bg-red-600 text-white px-4 py-2 rounded-md font-medium',
} as const

type ButtonVariant = keyof typeof buttonVariants

interface ButtonProps {
  variant: ButtonVariant  // スタイルはバリアント名で指定
  children: React.ReactNode
  onClick?: () => void
}

function Button({ variant, children, onClick }: ButtonProps) {
  return (
    <button className={buttonVariants[variant]} onClick={onClick}>
      {children}
    </button>
  )
}

// 呼び出し側: variant 名だけ指定、スタイルの詳細は知らない
<Button variant="primary">Submit</Button>
<Button variant="danger">Delete</Button>
```

### ③ なぜ効果的か

- バリアント名（`primary`, `danger`）は意味を持ち、スタイルの実体が変わってもコード全体を変更せず一箇所の修正で済む。
- コールサイトが「スタイル」ではなく「意図」を表現するため、コードの可読性・保守性が向上する。
- インライン化（プロップ渡し・ユーティリティクラス直書き・style 属性）はすべて同じ問題を引き起こすと著者は指摘しており、Tailwind の class 直書きも例外ではない。

## 5. pdfcn — shadcn スタイルの React PDF コンポーネントライブラリ

### ① 目的・問題意識

React で PDF を生成する従来のアプローチ（Puppeteer + Chrome 経由のヘッドレスレンダリング）は遅く、サーバーリソースを大量消費する。また既存の PDF ライブラリはデザインシステムとの統合が難しい。

### ② 具体的なコードと技術詳細

`shadcn-labs/pdfcn` は shadcn/ui と同じレジストリ形式を採用し、CLI 一発でコンポーネントのソースをプロジェクトに追加できる。

**インストール:**

```bash
npx pdfcn add invoice
# → コンポーネントのソースがそのままプロジェクトに追加される（ejectスタイル）
```

**基本的な PDF 生成:**

```tsx
import { Invoice, InvoiceHeader, InvoiceItems, InvoiceTotal } from '@/components/pdfcn/invoice'
import { renderPDF } from '@tanstack/forme'  // or Takumi

const invoiceData = {
  from: { name: 'Acme Corp', address: '123 Main St' },
  to: { name: 'Client Name', address: '456 Oak Ave' },
  items: [
    { description: 'Service A', qty: 1, price: 1000 },
    { description: 'Service B', qty: 2, price: 500 },
  ],
}

// PDF バイナリを生成（Chrome 不要）
const pdf = await renderPDF(
  <Invoice data={invoiceData}>
    <InvoiceHeader />
    <InvoiceItems />
    <InvoiceTotal />
  </Invoice>
)
```

**デュアルレンダリングバックエンド:**

| エンジン | 特徴 |
|---------|------|
| **Takumi** | 高速、ウォームレンダリング **26 ms** |
| **Forme** | TanStack エコシステム統合 |
| Puppeteer (Chrome) | 従来手法、**198 ms** |

**スペック:**

- コンポーネント数: **24**
- 請求書・レポートブロック: **20**
- テーマ: **9**
- ライセンス: MIT

### ③ なぜ効果的か

- Chrome を不要にすることで、インフラコストとレイテンシを大幅削減（Puppeteer 比で **7.6 倍高速**）。
- shadcn 方式（レジストリからソースをコピー）により、コンポーネントを自由にカスタマイズ可能。
- 既存の shadcn/ui デザインシステムとシームレスに統合できる。

## 6. React Live v5 — ブラウザ内リアルタイム React コードエディタ

### ① 目的・問題意識

ドキュメントサイトやプレイグラウンドで React コンポーネントをブラウザ内で編集・即時プレビューしたい。既存の React Live が React 19 や TypeScript の新しい型と整合していなかった。

### ② 具体的なコードと技術詳細

`FormidableLabs/react-live` v5 の主な変更点:

**型安全性の向上:**

```tsx
// v4 以前: withLive が注入する live プロップが Record<string, unknown> だった
// v5: Context の型に合わせた明示的な型になった
import { LiveProvider, LiveEditor, LiveError, LivePreview, withLive } from 'react-live'

interface LiveProps {
  code: string
  error: string | undefined
  element: React.ComponentType | undefined
  onError: (error: string) => void
  onChange: (code: string) => void
}

// withLive は LiveProps 型を正確に注入するようになった
const MyLiveComponent = withLive<LiveProps>(({ code, error, element: Component }) => (
  <div>
    {error && <p style={{ color: 'red' }}>{error}</p>}
    {Component && <Component />}
  </div>
))
```

**基本的な使い方（変更なし）:**

```tsx
import { LiveProvider, LiveEditor, LiveError, LivePreview } from 'react-live'

const code = `
function Counter() {
  const [count, setCount] = React.useState(0)
  return (
    <button onClick={() => setCount(c => c + 1)}>
      Count: {count}
    </button>
  )
}
`

function Demo() {
  return (
    <LiveProvider code={code}>
      <LiveEditor />
      <LiveError />
      <LivePreview />
    </LiveProvider>
  )
}
```

**v5 の他の変更点:**

- `Editor` の `prism` プロップが `prism-react-renderer` に正しくフォワードされるようになった（v4 では無視されていた）
- トランスパイル後のコードから React デバッグ用の `__self` と `__source` プロップが除去された

### ③ なぜ効果的か

- `withLive` の型が正確になったことで、TypeScript ユーザーが型エラーなくカスタムコンポーネントを構築できる。
- カスタム Prism インスタンスが正しく反映されるようになり、シンタックスハイライトの柔軟なカスタマイズが可能に。
